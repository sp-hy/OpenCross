# OpenCross engine architecture

This document is a map of the engine for a developer who is new to the code base. It says what each module owns, how modules call each other, and how a frame, a room load and a battle move through the code. It names real files, classes and functions. Anything that could not be confirmed from the source is marked "(unverified)".

OpenCross is a from-scratch C++20 engine. It plays Chrono Cross from the data files of the Radical Dreamers Edition (RDE) install. One executable, `opencross.exe`, holds the game and the developer tools. The data formats are described in `docs/formats/*.md`; this document links to them and does not repeat them.

## 1. Modules and dependencies

Each module is a static library `oc_<name>`. The comment in `src/CMakeLists.txt` says dependencies point downward. The link edges read from the `CMakeLists.txt` files (public edges only; the platform, miniz and SDL3 links are left out):

```
 opencross (exe) ---- oc_tools
      |
 oc_flow    oc_menu_model    oc_movie              application tier
      |
 oc_keymap -> oc_title
      |
 oc_battle_view -> oc_battle_fx -> oc_battle_anim  battle presentation
      |
 oc_game  (field world, actors, autosave, routes)  integration
      |
 oc_ui   oc_script   oc_effects_gpu -> oc_effects  screens, field VM, effect engine
      |
 oc_render   oc_audio   oc_battle   oc_data        engines and rules
      |
 oc_text   oc_stage   oc_import   oc_save          importers, save
      |
 oc_assets   oc_platform   oc_net   oc_vfs
      |
 oc_core
```

Each tier links the ones below it, not strictly the next one down (`oc_ui` links `oc_save` and `oc_data`, `oc_menu_model` links `oc_game`). The edges as a list (each library also reaches `oc_core` through the ones below it):

Rules of thumb that the link lines enforce:

- `oc_script` links only `oc_core`. The field VM reaches the world through the `script::FieldHost` interface (section 4.3).
- `oc_battle` links `oc_core` and `oc_data`. The battle rules have no rendering, audio or file access and run headless in tests and in `ocbattle`.
- `oc_import` links `oc_core` and `oc_assets`. Importers take byte spans and return asset structs; they never open files.
- `oc_game` (`src/game/*.cpp`: the field) is the integration library for field play. The battle presentation is three sub-libraries under `src/game/battle/` (`oc_battle_anim`, `oc_battle_fx`, `oc_battle_view`) that sit above `oc_game`; the effect engine is in `src/game/effects/` (`oc_effects`, `oc_effects_gpu`).
- `oc_title` holds the title screen, name entry and slot list. `oc_flow` (`src/game/game_flow.*`, `game_session.*`, `party_editor.*`, `title_backdrop.*`, `debug_tools.*`) binds them to a state machine.

## 2. Process lifetime

### 2.1 Entry point

`src/main.cpp` is 18 lines. `run_tool(argc, argv)` (in `src/tool_main.cpp`) checks `argv[1]`; if it names a tool, the tool runs and its exit code is returned (a negative code becomes 1). If the arguments are not `--config <file>` / `--profile <dir>` pairs it prints the usage and returns 2. Otherwise it builds `oc::app::App`, calls `init(argc, argv)` and `run()`, destroys the App and ends with `platform::finish_exit()`. When the main loop ends, `run()` hides the window and calls `platform::begin_exit(exit_code, restart)`, which arms a 10-second watchdog: teardown (GPU, audio, Steam, library unloading) can stall under Proton, and the watchdog then ends the process. `finish_exit()` ends the process without unloading libraries, with the exit code given to `begin_exit`. For the Update tab's "Restart now" it first starts the new exe with the same command line and waits, windowless, for it to exit, then ends with its exit code: RDE's launcher waits for the game it started and would otherwise come back over the new one. `--config <file>` selects another ini (routes use it; such a run never connects, applies no mods and never rewrites the ini). `--profile <dir>` gives a normal run its own `opencross.ini` in that folder (created when missing), with its log, shots and a relative `[Paths] SaveDir` there: a second copy of the game on one machine gets its own multiplayer `PlayerId`.

| `app_run.cpp` | `run()`: main loop, hotkeys, per-frame settings, mode dispatch (`simulate`) |

Members are declared in creation order and destroyed in reverse: every GPU resource goes before `ctx`, the voice player before the mixer.

### 2.3 Boot

`App::init()` runs, in order: `init_config` (exe folder, `opencross.ini`, `--profile` or `--config`, `platform::Config::load`, log, `bind_cheats`; a first launch writes defaults), `init_window`, `init_gpu` (`GpuContext::init` then `set_msaa` / `set_anisotropy` from `[Video] Msaa` / `Anisotropy`, `ImGuiLayer`), `init_source` (the game data and the save folder, section 3.7; the not-found screen and the version picker run here, and a quit there ends the run before anything else starts), `init_vfs` (`Vfs::open` for an RDE install, `ModManager::scan` and `apply`, `texture_registry::bind`, the texture-dump hooks for the Mods tab; then, when `font.dat` is there, the menu's `kb_70` font face, about 190 MB, starts reading on a worker so that `init_menus` finds it parsed), `init_render` (`CrtPass`, `SpriteBatch`, `MeshPipeline`, the ImGui Mods, Cheats and Update tabs, the 320x224 `field_rt`), `init_audio` (`VoicePlayer`, `SfxBank`, `Mixer::open_device`), `init_routes`, `init_flow` (`GameTables::load`, `GameFlow::init`), `init_saves`, `init_collection` (`collection.dat` beside the OpenCross saves), `init_dialogue_log` (`dialogue_log.txt` there), `init_menus` (with the dialogue log window, `ui::DialogueLogView`), `init_field` (`FieldWorld::init`), `init_randomizer` (its field hooks, the Mods tab page's hooks, the scan when it is on), `init_battle` (`BattleView::init`, `BattleResults::init`), `init_oc_achievements` (the menu's Achievements page rows, the element table for the rules, `achievements.txt`), `init_title`, `init_start_state`, `init_route_state`, `init_debug_tab`, `init_multiplayer` (the Multiplayer tab). It returns a non-zero exit code if the window (1), the renderer (1) or the route file (2) fails.

A missing piece sets a `*_ok` flag false and the App skips that mode. The steps that need game data test `App::data_ready()` (the VFS serves `cdrom`); without it the world and battle are never created.

After a fresh boot to the title, `GameFlow` shows a boot logo (`ui::BootLogo`) before anything of the game runs: `ui/logo.png`, or in Japanese `ui/notice.png`, `ui/notice2.png`, `ui/logo.png`, in both art modes. Each image lasts 180 ticks over black: alpha ramps in over the first 30, holds, and ramps out over the last 30. Any key, click or pad button ends the current image at once (no fade-out); the logo is skipped entirely for routes, replays, `[Debug] Screenshot` runs and a return to the title, and does not run while the settings overlay (other than its Debug tab) is open. A missing image drops the whole logo. Played from the PS1 discs (no `ui.dat`) there is none: the game starts with its own logo movie.

### 2.4 Time: 60 Hz logic, interpolated drawing

`App::run()` loops while `window.pump(input)` is true. The simulation runs at a fixed 60 Hz; drawing runs once per presented frame.

- `platform::FrameTimer::tick()` gives the real seconds since the last frame.
- `[Game] FastMode` / `SlowMode` are RDE's speed modes and change only the field loop and the battle loop (below, Fast and slow mode).
- `platform::FixedStep::advance(dt)` (`window.cpp`) accumulates time and returns `{ticks, alpha}`. One tick is 1/60 s. `dt` is clamped to 0.25 s and at most `kMaxTicks = 5` ticks run per frame, so a stall drops time instead of spiralling. `alpha` (0..1) is the remainder. Drawers use it to interpolate between the last two simulated states.
- `platform::FrameLimiter::wait(config.frame_cap)` sleeps at the end of the frame. Routes, replays and sweeps skip it. VSync is a swapchain setting (`ctx.set_vsync`).
- In borderless and exclusive fullscreen the mouse pointer hides after `platform::kPointerIdleMs` (3 s) without mouse motion, button or wheel input, and returns with the next such input. It stays visible while the settings window is open and in windowed mode (`platform::pointer_hidden`, `ImGuiLayer::set_pointer_hidden`).

The field takes the tick count: `FieldWorld::update(in, ticks)` calls `sim_tick()` once per tick. `BattleView::update(dt, in)` ignores the tick count and runs its own `stepper_`. Both interpolate at draw time.

What the field blends by `alpha`: the scroll (`RoomView::scroll_at`; each tick's value is the integer scroll plus a display-only offset from `ScrollSmoother`, in every art mode: a critically damped position + velocity filter (gain 0.15, velocity gain 0.15² / 1.85) on the eased scroll before the shakes are added, aimed while moving 0.75 px behind the scroll, fading to the scroll itself as the average step rate (gain 0.2) falls below 0.25 px per tick; it never passes the scroll in its direction of travel, trails it by at most 2 px (held there, it takes the average step rate as its speed), never moves against that direction, settles exactly on the scroll, takes a jump over 6 px at once and is reset on room entry, so a camera stepping whole pixels at a fractional rate glides at a steady speed and stops at a pan limit without overshoot), actor position and yaw (`Actor::pose`, with the segment smoothing and the party followers' 8-tick mean of `docs/rules/field_actors.md` 6.9), clip time, the script-set model axes (pitch, model yaw, roll of ops 27 / 28 / 29 / AA and the per-axis scale of op 82, `Actor::axes_at`: a step over 512 units or a scale jump over x1.5 or through 0 is a reset and drawn at once, as is the first tick of a new actor), effect objects (position, angles, scale, colour, UV scroll and morph phase; `emitter_collect.cpp`; the room effects step once per 2-tick field frame like the PS1, so they blend over the whole frame step by `(ticks since the step + alpha) / 2`, `docs/formats/room_effects.md` 3.2.1) and the 8F screen ripple (`FieldWorld::wave_view(alpha)`: phases and ramped values; the grid lines move by sub-pixel amounts where the PS1 steps whole pixels). Also blended from their value at the start of the tick (`FieldWorld::snapshot_drawn`, at the top of `sim_tick`, the end of a room load and the return from a battle, which the host makes between ticks and draws in the same frame: a blend from the last tick before the battle would show the field, and the foe just fought, through the return's black): each actor's colour multiplier (ENTITY_RGB and the eased floor light) and shadow strength, the background group tint (C2, `RoomView::snapshot_group_tint`), the screen fog (68), the sequence screen colours (2B / 2C), the room fade, the sequence post pass (3E / 40: zoom, shift, colour) and the back colour of lit actors; the model y offset of ops B0 / B1 (with the script-set axes, a rise over 512 units drawn at once); and the matrix (angles and scale) and colour of effect mesh objects (types 14 / 19 / 20, as the effect sprites; an object that faces its velocity keeps the tick's matrix). A fade the host sets outright (`begin_entry_fade`, `fade_in_from_black` after a menu or a movie, `clear_screen_fade`) is drawn at its new level at once. Nothing in the field picture steps at the tick rate on a display faster than 60 Hz. While a frozen-capture exit fade runs, `alpha` is 1.

#### Fast and slow mode

RDE's fast and slow modes (F2 / F1, pad RT / LT, the Cheats tab; `App::update_loop_speed`, `game::speed_factor`) do not speed up the whole program. As in RDE they change only how many logic steps the field loop and the battle loop run per frame:

- The field runs on its own `FixedStep` (`App::field_stepper`) fed with the frame time times the field factor: 4 with fast mode (`FastRate` 0; 2..5 = that many), `SlowRate` percent with slow mode, with one 1/30 s stretch at full speed after every 299 slow field frames (`game::SlowFieldCycle`). The factor is 1 whenever `FieldWorld::speed_allowed()` is false: on the title and ending maps 8 and 9, while variable 0x36 is non-zero, during a room load or room change, while a movie runs and during the input locks: the pad lock that follows a room load or a field movie (24 field frames) and the one after a menu screen (4 field frames) or the key-item list (8 field frames; `docs/rules/field_actors.md`). The field is drawn at its own stepper's `alpha`.
- A battle advances by the frame time times the battle factor: 2 with fast mode, `SlowRate` percent with slow mode, but only while `BattleView::speed_allowed()` holds. That gate opens at the end of the intro (when the `bti0` layer stops) and closes when the outro brings `bti0` back; a pack's op 0x60 opens it and op 0x5F closes it, and while an overlay that holds the speed runs (the Time Devourer's end `lasdes2`, `miyademo`; `BespokeEffect::holds_game_speed`) the gate counts as shut. The battle load, intro and outro therefore run at 1x in either mode; the toggles still flip there and their icons show. The results screen runs at normal speed.
- Everything else keeps the real step: the main menu, shops, name entry, the party screens, the key-item list, the pause screen, the title, the results screen and movies. Play time counts real ticks in every mode.
- Message windows in the field keep the real clock (`FieldWorld::set_text_clock`) at RDE's text pace (`game::text_pace`): fast mode reveals 2.25 times as fast and divides every `{wait(n)}` pause and `{wend(n)}` countdown by 8; slow mode reveals at half speed and doubles them. `FastRate` and `SlowRate` do not change the text pace.
- The SFX sequencer ticks as fast as the loop that runs (`Mixer::set_sfx_tempo`): 4x in a fast field, 2x in a fast battle (after the intro), half speed in slow mode, the normal rate on every other screen and while the field's factor is 1. Music keeps its tempo.
- Both modes do nothing in room 386 (zel_a12i) and in the battles launched from it (`App::speed_locked`): RDE tests the room id, the field's own while the field runs and the room register (the room the battle was launched from, which a battle never changes) during a battle. A battle id plays no part, so the Radius tutorial (battle 386, launched from alu_a04f) runs at the chosen speed; a standalone battle (`[Debug] Battle`, `ocbattleview`) has no launching room and is never locked.
- The five play-time toggles (fast, slow, encounters off, battle boost, auto battle) are session-only: every launch starts with them off (`Config::clear_session_toggles`) and the ini never stores them. A `--config` ini may set them for tests; a route then runs the field and battle at the ini's speed per route tick. A replay runs 1:1 (it holds the field ticks of the recorded session).

### 2.5 Sim and draw

`App::simulate()` picks one mode per frame: `route_frame()`, `replay_frame()`, the boot logo, a battle, `sweep_frame()` or `field_frame()`. All reach `App::advance(in, dt, ticks)` (`app_sim.cpp`), a priority chain where the first branch that applies consumes the frame: play-time counter, load fades (`flow.tick_fade`), the open pause screen (`pause_modal`), the dialogue log window (`dialogue_log_step`: its key or chord opens it over the field, and while it is open it takes every frame, so nothing below runs), a standalone battle (`battle_ok`), a playing movie, the title scene, flow screens, a field battle (`battle_in_field`), the main menu, party screen, the open key-item list, then the key-item and pause openers, a shop, script-requested menus and movies, the menu key, and last the normal field (`world.update(in, ticks)`, autosave, battle request checks). `App::draw_frame()` never changes game state; it reads it (section 6.3).

### 2.6 Hooks for routes and debugging

`[Debug]` ini keys (`platform::Config::debug_*`) select a room, flow state, seed, route script, input record or replay, a standalone battle and the sweep. A disabled flow (`[Debug] Battle`, the sweep, a replay) draws nothing of its own, except the screens a field script opens (FE 4A name entry, the party screen, the New Game+ list), which run in it too. `route_frame()` runs `ScriptSpeed` route steps per frame, each followed by `advance(in, 1/60, 1)`, so a route is tick-exact and independent of real time. With `[Debug] Control` the frame goes to `control_frame()` instead: it takes the controller's lines from stdin (a reader thread), runs the same route steps up to the tick asked for (600 per frame at most, nothing drawn between), then asks `GpuContext::request_capture` for that frame and writes it; a seek behind the run restarts it in place (`control_restart`: the `[Debug] Room` start of `init_start_state`, `FieldWorld::reset_clock`, the seed and the route reloaded). `docs/formats/routes.md` section 8.1 has the protocol. About 110 `OC_*` environment variables are read with `getenv` (none are ini keys); they are developer switches and the route runner sets them per run from a route's `.env` file. The ones that shape a run: `OC_QUIET` (test window takes no focus and opens behind every other window, mixer gain 0), `OC_AUDIO_DUMP` (write the mix of a scripted run to a wav file), `OC_FRAMETIME` (log slow frames during a field to battle hand-over), `OC_NO_WARP` (draw the screen ripple unwarped), `OC_EXIT_KIND` (force the room-change fade kind), `OC_STUCK_TICKS` (softlock limit of the field watchdog), `OC_SWEEP_ROOMS` / `OC_SWEEP_FROM` / `OC_SWEEP_COUNT` / `OC_SWEEP_SCENARIO` (narrow the room sweep), `OC_SLOT_DUMP` (prefix for the route `request slotdump` output), and for battles `OC_BATTLE_SEED`, `OC_BATTLE_FIELD`, `OC_BATTLE_INTRO`, `OC_BATTLE_MISS`, `OC_BATTLE_NORUN`, `OC_BATTLE_AUDIT`, `OC_ROUTE_ELEM`, `OC_ROUTE_GAUGE`, `OC_RESULTS_HURT`, `OC_RESULTS_HEALER`, `OC_CAM_KEYS`, `OC_CAM_PICK`. The rest are trace and override switches grouped by prefix: `OC_*_TRACE` / `*_LOG` / `*_DBG`, `OC_FX_*`, `OC_FXDBG*`, `OC_STAGE_*`, `OC_SFX_*`, `OC_SEQ_*`, `OC_DEV_*`, `OC_FIND_*`. The tools add their own (`OCC_*`, `OCPRD_VERBOSE`, `OCSTAGE_*`, `FXA_*`, and `OPENCROSS_GAMEDIR` for `ocbattleseq`). F8 opens the Debug tab (`game::DebugTools`; using a tool locks saving for the session). F6 cycles the art mode (Original, Hd, Modded), F7 toggles widescreen, F9 toggles the battle camera debug overlay (`BattleView::handle_input`; F3 as well in `ocbattleview`); PageUp / PageDown cycle through the room list in `field_frame`, only when the game flow is disabled (a `[Debug] Room` start) and no movie is open; `ui/keymap_screen.*` is the New Game user-guide screen (two baked images with the key and pad glyphs drawn on them), not a rebinding UI: keys are fixed by `platform/keymap.h`; F1 / F2 (slow / fast), F3 / F4 / F5 (No Encounters, Battle Boost, Auto Battle) toggle RDE's play-time modes, which show as feature icons (`App::rde_toggle_keys`).

## 3. Data access

### 3.1 The VFS

`src/vfs/vfs.h`: `oc::vfs::Vfs` knows archives and paths, not what the bytes mean.

- The shipped archives come from a backend (`vfs/backend.h`: `has_archive`, `contains`, `read`, `list`, thread-safe). `open(game_dir)` uses `RdeBackend` (`vfs/rde_backend.*`), which mounts `<GameDir>\data\*.dat` lazily, each a ZIP read through miniz (`class Archive`). Archives used: `cdrom`, `cdrom2`, `hd`, `lang`, `font`, `ui`, `movie`. See `docs/formats/rde_archives.md`. `open(backend, game_dir)` installs another backend; a source with only the PS1 file tree serves `cdrom` and reports the others absent (`has_archive`), and the overlay and `cdrom2` rules below work unchanged over it (no `cdrom2` = every read goes to `cdrom`).
- `set_disc(1|2)` / `disc()`: the disc in the drive, passed to the backend with every read; a backend whose files depend on the disc (the PS1 discs) answers from that disc, RDE's archives ignore it.
- A path is `<archive>/<member>`, for example `cdrom/map/mapbin/alu_a01f.bin`. `normalise_path` lower-cases and maps `\` to `/`; `split_archive_path` splits off the archive.
- API: `read`, `read_disc`, `exists`, `list`, `loose_file`, `has_archive`, `open_reader` (a `vfs::Reader` over the same lookup as `read`, for reading a file in parts: the disc backend reads only the sectors asked for, every other source reads the file whole into memory first). Reads are thread-safe; the loaders use worker threads.
- `read` order: mod overlay file, then `cdrom2` for `cdrom/...` paths when `cdrom2_first(member)` is true, then the archive.
- `read_disc` skips the `cdrom2` override, for original-art screens that need the files RDE blanks there.

### 3.2 Art selection: SD, HD, Modded

`platform::ArtMode` is `Original`, `Hd` or `Modded`. `App::apply_art_mode()` applies it:

1. `mods.apply(files, render::mod_art(mode))` rebuilds the overlay and bumps `Vfs::generation()` if it changed.
2. `files.set_hd_mode(platform::art_is_hd(mode))`. In HD mode `cdrom2_first` is true for every member. In Original mode only a fixed list goes to `cdrom2`: `map/etc/openfont.tim`, `menu/title/cmptitle.tim`, `map/mapbin/ending.ctd`, and anything under `map/window/`.
3. Each consumer rebuilds its art in place, without touching the simulation: `FieldWorld::set_art_mode(hd, force)` runs `swap_art()` (`RoomView::reload_art`; every model an entity shows rebuilt on its own worker thread at once, then handed over through `Actor::swap_model_art`; effect atlases), then `BattleView`, `BattleResults`, `PartyScreen`, `GameFlow`, `MainMenu` and `ShopScreen` follow.

`Overlay::enhance`, read through `Vfs::enhanced()`, is true only for `Modded` (`ModManager::apply`). In the source its one reader is `render/model_tiles.cpp`; other improvements are separate `[Enhancements]` config keys (section 6.4). The code comments state the rule: HD art is exactly what RDE draws, and upgrades exist only in Modded.

Path-keyed texture caches use `Vfs::cache_key(path)` (path plus overlay generation), so a mod switch loads the new file.

### 3.3 Mods

`src/vfs/mods.h`, `docs/formats/mods.md`. `ModManager::scan` walks `<GameDir>\mods\<name>\**`, plus the bare `.dat` files there and the members of `.zip` / `.7z` / `.rar` files, read live (`mod_archive.*`), and resolves each loose file to a shipped member by matching trailing path components, or adds it as a new member when it matches none and sits below a folder named after an archive. `apply` builds an `Overlay`: `files` (member replacements: loose files, or `OverlayFile` members read in place from a packed mod or a mod's `<archive>.dat`) `textures` (replacement PNGs, see `render/texture_registry.*`) and `models` (replacement `.glb` files by `<classic|hd>/<member stem>`, below). A mod's `text\<member>` and `tables\<table>.txt` are row files merged over the game's text member / battle table instead of replacing it, lowest priority first so the first mod wins (`import::TextMod`, `data::TableMod`, handed over in `App::init_vfs` before the text and tables are read; `docs/formats/mods.md` 1.2, 1.3). Each mod has a `ModLoadOn` (Modded, Sd, Hd, All) and a priority from list order. Game data (`vfs::is_game_data`) ignores `ModLoadOn` and is fixed by the first `apply` until the next launch. Voice packs are read by `audio::VoicePlayer` from the enabled mod roots, not through the overlay (`ModManager::packed_voice` finds a packed mod's lines). A `mod.ini` at a mod's root is its manifest (`Mod::manifest`, `core/features.h`); `feature_inputs` hands the enabled ones to `features::resolve`, whose result `App::features` holds for the run.

**Model export** (`src/game/model_export.*`): `model_to_glb` writes a decoded `assets::ModelAsset` as a `.glb` (joints as nodes under a `root` node that turns +y down into glTF's +y up, skin with inverse bind matrices, one node per construct, embedded PNGs, one animation per clip named by its script id; layout in `formats/mods.md` 7.1); weapon pack parts go through `weapon_part_asset`. `check_glb` reads a file back and compares its counts, joints and skinned vertices at every keyframe with the engine's pose; `check_import` reads it back as a model replacement (below) and compares the imported corners and faces with the model's at every keyframe (`occ export-models --verify` runs both on every file).

**Model replacements** (`src/game/model_mods.*`, decoding in `src/import/gltf_model.*`; layout in `formats/mods.md` 7.2): `read_model_files` and `read_menu_model` end with `apply_model_mod`, which looks up `Vfs::model_file("<classic|hd>/<member stem>")` (the active mods' `models\` files) and, when there is one, swaps the decoded asset's meshes and textures for the file's, before any texture mod or GPU upload, so the field, battle, the Status screen, the HD models in fields and `ocmodelview`'s modded copy all draw it. `import::load_gltf_model` matches the file's `joint_NN` nodes to the skeleton by name (refusing a missing, extra, doubled or re-parented joint), skins every vertex in the file's rest pose (scene transforms, skin joints and inverse bind matrices), keeps its two heaviest joints (the engine's two-joint vertex; a third or fourth influence is dropped and counted) and stores per kept joint the position relative to that joint's rest transform, with the normal in the space of the joint the skinner turns it with. Each construct keeps its index (`mesh_NN`), so shading entries, part flags and scripts still address it. Images are decoded with `render::decode_image`; one named after a model texture (`clutK`, `overlayK`) replaces that texture through `ModelAsset::mod_textures` only where its pixels differ (with the original's STP bits), so an unchanged file draws the HD image, the eye blinks and any texture mod as before; other images become textures of their own. `ModelAsset::mesh_mod` names the file; `resolve_model_textures` then leaves its images alone. The skeleton, clips, attach points, mounts, shading entries and extent are the model's. A character's all-uses file (`character/<name>`, `formats/mods.md` 7.3) is applied where a use has no file of its own: `read_menu_model` takes it after its own `menu/player` file (`MenuModelMods::Status`), or alone (`MenuModelMods::AllUses`, what the field and battle read); `read_model_files`, for a battle player model up to the last menu model with no file of its own, reads the Status-screen model wearing it and `wear_character_model` swaps in its meshes and textures: the meshes as they are when the two skeletons are one (every shipped pair), else bound once onto the battle skeleton (`battle_joint_map`: joint for joint with the same joints and parents, else `match_menu_rig` with the battle model in the field model's place; `rebind_meshes` keeps each vertex's rest place and normal). `read_character_textures` reads the shipped battle model, so the Status screen's character textures never read the mod. In the field, `FieldWorld::dress` dresses a character's own field model in the all-uses file through the HD models in fields' rig when those are off (`MenuBody::all_uses`) and no file replaces the field model. A refused file is logged and listed among its mod's issues (`vfs::report_file_problem`, cleared by the next scan). `ModelExportJob` runs `run_model_export` (every field, battle, Status-screen model and weapon part, classic and HD art) on a worker thread for the Mods tab's "Export all models"; `occ export-models` runs it blocking. Like the texture dump it opens its own `Vfs` (no mods) and touches no GPU state.

### 3.4 Importers and assets

`src/import/` turns bytes into `src/assets/` structs. Callers read the bytes through the VFS and pass them in.

- `container.*`, `lzss.*`, `tim.*`: cpt / drp lumps, LZSS, TIM images and a 1024x512 VRAM model (`rde_archives.md`, `room.md`).
- `room.*`, `chip2.*`: `assets::RoomScene` (camera, layers, walk mesh, models, script bytes) and RDE HD backgrounds (`room.md`, `fieldscript.md`).
- `room_effects.*`: `assets::RoomEffects` (sprite sheets, emitters, sequences) for rooms and battle packs (`room_effects.md`, `battle_effects.md`).
- `model.*`: `assets::ModelAsset` for field and battle models (`model.md`). `battle_stage.*`: `assets::StageAsset` (`battle_stage.md`).
- `gltf.*`: glTF 2.0 binary (`.glb`): a JSON value with double numbers (reader and writer), the GLB chunks, typed accessor reads and node transforms. It knows no game format; the model exporter builds its documents and reads them back (section 3.3).
- `gltf_model.*`: a model's glTF layout both ways: the export's axes and scale and the skeleton's rest transforms, and `load_gltf_model`, which reads a mod's `.glb` as replacement meshes on a model's skeleton (joint matching by name, rebinding to the engine's two-joint vertices; images left encoded) (section 3.3).
- `text.*`, `spritefont.*`: `lang.dat` tables and message blocks as rich text; `font.dat` and `ui.dat` fonts (`text.md`).

`oc_assets` is an INTERFACE library of plain float structs with no PS1 types. Renderers and the world consume them.

### 3.5 Game tables

`src/data/tables.*`: `data::GameTables::load(vfs)` fills one struct with the battle and menu tables: `enemies` (`StatRec`), `char_sets`, `elements` (`ElemRec`), `growth`, `scenes` (`SceneRec`), `symtbl`, `drops`, `gear`, `item_info`, shop and trade lists, plus names from `lang.dat`. Records keep raw bytes with accessors. `scene_for(battle_id, variant)` maps an encounter id to a scene (ids from 0x200 are scene numbers). See `docs/formats/battle_data.md`. `battlefields.h` and `battlefield_rooms.inc` (generated by `occ battlefields`) and `area_names.inc` serve the Debug tab. Other tables sit beside their users: `battle/dopple_table.h`, `audio/bgm_table.*`, `import/text_tables.inc`, the two opcode `.inc` files, `game/disc_index.*`.

### 3.6 The disc file index

`src/game/disc_index.*`: `game::DiscIndex` loads `cdrom/cdrom.fnd` (disc 1) and `cdrom/cdrom2.fnd` (disc 2) through the VFS; when disc 2's index is missing both discs share disc 1's, and when `cdrom.fnd` is missing (the PS1 discs, which do not carry the names) it takes the built-in copy of both indexes. A record is 0x40 bytes, a NUL-padded path; record number = file number. The loader lower-cases the path and maps `\` to `/`, and `record(disc, index)` returns "" outside the file. The game does not open files by name: the index plus the disc in the drive says which file answers.

- **Map ids.** Room id `n` owns three records starting at `kMapBase + 3 * n` (368): `.bin`, `.prd`, `.ctd`. `room_stem(disc, id)` takes the stem from the `.bin` record under `/map/mapbin/`. Several records name another room's file (`FieldWorld::load_room` reads the `.prd` through the record, section 12.2), and a record may differ between discs, so a room id can be a different room on disc 2.
- **Movies.** A movie number `m` is record `kMovieBase + m` (6035), an `.stv` path under `/movie/` whose stem is the `movie.dat` member (`newop` maps to `a01op`). The `PLAY_MOVIE` operand is not the number: it indexes a parameter table (`movie_row`: frame range, mode, number, volume), disc 1 using rows 0 to 23 and disc 2 rows from 24.
- **Dummy records.** Files that exist only on disc 1 appear on disc 2 as a placeholder path (`dummy.dat`, a 24-byte text file); `room_stem` and `movie_name_of` return "" for a record that is not the expected kind. 80 rooms are named only by the disc 1 index and 80 only by the disc 2 index; 52 ids hold a room on disc 1 and the placeholder on disc 2. A map jump resolves its id through the current disc only (`FieldWorld::room_stem_for_id`): a placeholder record gives no room and the jump is refused (the PS1 would read the placeholder as the room); the `lang.dat` room table is used only for an id the index has no record for. A scan of every 5A / DC with a literal room id in the rooms the disc 2 index names finds 39 sites aiming at a disc-2 placeholder; 20 of them sit behind a scenario test below 184 (the scenario at the disc change in bak_a14e), the other 19 (in blk_00, dem_11, gal_b13i, jac_b16i, jac_b17i, mis_b01f, sui_a10e, tel_b09i, tel_b25f, tel_b28e, wld_b00, wld_b01, you_b08f) behind room flags and cutscene state that the static scan does not resolve. If one of them is taken on disc 2, the PS1 reads the placeholder as a room; OpenCross stays in the room and logs the refused exit.
- **Debug starts.** `[Debug] Room`, the route `load` and the debug menu's teleport call `FieldWorld::select_disc_for_room`: a room that only the other disc's index names switches to that disc and sets variable 0x42 to match; a room on both discs keeps the current one.
- **Switching disc.** Script variable 0x42 holds disc number minus one. Op `FE 65` (`CHANGE_DISC`) goes through the menu request path: `FieldWorld::request_menu` stores the operand in variable 0x42 and calls `set_disc(operand + 1)`, which swaps the index at once, even while another screen request is pending. `step_transition` re-reads variable 0x42 before every room jump and `restore_vars` after a load, so a save made on disc 2 continues on disc 2. Starting a new game resets to disc 1. Playing from the PS1 discs, a disc that is not mounted is asked for by the insert-disc screen (section 3.7); RDE and two mounted discs swap at once.
- **Built-in names and path lookup.** `vfs/disc_names.*` holds both indexes as a generated table (`disc_names.inc`, written by `occ disc-names src/vfs/disc_names.inc` from an RDE install: disc 1's records, then disc 2's where they differ) and parses index files for `DiscIndex` (`parse_disc_records`), so both sources normalise the same way. `vfs::DiscNames` maps a logical `cdrom/...` path and a disc to the record holding it on that disc and on the other one (the fallback for a file the disc in the drive lacks), and lists every named member for `list("cdrom")`; the naming rules are in `docs/formats/rde_archives.md` section 5. A backend that reads files by record uses it.

### 3.7 Data sources and disc mode

`App::init_source` (`app_source.cpp`) decides where the game data comes from before anything reads it; the search and the opening of a disc set are `app/data_source.*` (library `oc_source`), shared with the dev viewers (below). `[Paths] Source` (`docs/formats/config.md` 2.1) sets the search:

1. `auto` and `rde`: an RDE install, `platform::find_game_dir` (`[Paths] GameDir`, else the exe folder and its parents). `rde` stops here.
2. `auto` and `disc`: the images `[Paths] Disc1` / `Disc2` name and the image files directly inside `[Paths] DiscDir`;
3. the image files directly inside the folder of `opencross.exe`;
4. the discs in the optical drives (`app::optical_discs` over `import::disc::scan_optical_drives`).

The first step that finds a Chrono Cross disc gives every disc it holds; the steps after it are searched only while no build has both discs, and they add only a disc number that a build already found lacks (`import::disc::merge_place`), so disc 1 named by `Disc1=` and disc 2 lying next to the exe make one set, while a set of another build further down the list is not taken. Folder scans take files by extension only as a filter (`import::disc::image_files_in`: `.cue .bin .img .iso .ccd .mds .mdf .m3u .pbp .chd`, the files that name others first); every file is opened and identified by its content (`add_image_file`, `docs/formats/disc.md` section 6), never by its name, and a file found unusable is not opened again until its size or time changes. `group_discs` gathers the discs by build (the known build's name, or the executable's hash for an unknown build); `choose_set` prefers complete sets over single discs, a known build over an unknown one, then the order found, and `[Disc] Region` picks between the regions.

While nothing can be played, the "no game files found" screen (`render/imgui_data_screen.*`, ImGui with its own font, no game assets) lists what was searched, the files found but not usable and the formats read, with Retry, Browse... (`SDL_ShowOpenFileDialog`; each picked file holding a Chrono Cross disc goes to `[Paths] Disc1` or `Disc2` by its disc number and the ini is saved) and Quit, and searches again every 2 seconds. When Japanese and USA sets are both found and `[Disc] Region` names neither, the version picker asks which to play and saves the answer to `[Disc] Region`. `[Debug] Screenshot` / `ExitAfterScreenshot` work on both screens.

**Disc mode.** A set of discs is opened as `import::disc::DiscBackend` (`src/import/disc/disc_backend.*`) through `Vfs::open(backend, <exe folder>)`. It serves only `cdrom`: a path is looked up by name in the disc indexes (`vfs::DiscNames`, section 3.6) and read from the record of the disc in the drive that holds data (an empty slot of the same name is skipped), else from the other disc when it is mounted and its index names the same file; `cdrom/#record/<n>` reads record `n` of the disc in the drive only; `list("cdrom")` is every named member a mounted disc holds data for. Discs can be mounted while the game reads (`DiscBackend::mount`). The other archives are absent, so every `cdrom2` rule falls through to `cdrom`. An unknown build runs as its closest region (Japan when its boot file says nothing) with a warning in the log and as a toast on the first screen.

**Console font.** Once the discs are open, `app::open_discs` looks for the player's PS1 BIOS image directly inside the exe folder and the folders of the opened images (`import::find_console_font`, recognised by content, `docs/formats/text.md` 7.15) and keeps the font for the run (`import::set_console_font`); the JP menus and shops and name entry on both builds draw it, and without one their stand-in.

`platform::disc_mode()` is the one query for it. `App::apply_disc_mode` (through `app::apply_disc_settings`) fixes the settings that need RDE's data: classic art (`[Video] ArtMode`, F6 does nothing), `[Audio] BgmSource=original`, the language of the build (`jp` for the Japanese discs, `en` for the USA ones) and the 1999 portraits (`[Game] Portraits`); the settings window greys those rows out, and `App::save_config` writes the ini's own values of them back, so the player's RDE choices survive. The UI screens keep their PS1 layout and resolution in either state of `[Video] Ps1ResUi` (`App::ps1_ui_pass`: the pass runs whenever disc mode is on); there the setting only moves the menus' 3D models (the Status screen's character) out of the PS1-sized target to window resolution (`ui::ps1_menu_models`). Mods live in `mods` next to `opencross.exe`; they were made for RDE's data and may not match the USA discs' files (logged, not blocked). The texture dump needs an RDE install. Saves go to `%LOCALAPPDATA%\OpenCross\saves\jp` or `\usa` (`platform::disc_save_dir`) unless `[Paths] SaveDir` is set.

**Dev viewers.** `ocbattleview`, `ocflow`, `ocmenudemo` and `ocshopdemo` open their data through `app::open_game_data`: the same search, then on discs the same mount, console font and fixed settings, so `[Paths] Source=disc` in their ini runs them on the discs (original art only, F1 does nothing, the text of the build). They have no not-found screen or version picker: nothing found, or sets of both regions without `[Disc] Region`, logs why and exits.

**The disc in the drive.** Every disc change of the field (`FE 65`, the disc check before a room jump, a loaded save's variable 0x42, a new game, `select_disc_for_room`, the route `disc`) goes through `FieldWorld::set_disc`, whose hook (`set_on_disc_change`) calls `App::disc_changed`: `Vfs::set_disc` follows, and the drives are searched for a disc that is not mounted. Every frame `App::disc_prompt_frame` compares the disc the story names (variable 0x42 of the running field, or of the save a Continue / Load is loading) with the mounted discs; a missing one opens `ui::DiscPrompt` (`src/ui/disc_prompt.h`: the PS1's veil and "insert disc" line, layout by build), and while it shows nothing of the game runs (no simulation step, the picture frozen under the veil). Its host tries to mount the disc when something changed: a drive's media, the image files where the search looks (checked every 2 seconds), a file picked with F9, or F10; the right disc of the played build lifts the screen and the game goes on in the same frame; the other disc or another build's disc shows the screen's "wrong disc" line. While both discs are mounted the change is silent, as in RDE. A disc read from an optical drive is watched every frame (`App::poll_drive_discs`, `DriveSource::media_changed`): when it leaves the drive it is unmounted (its files then come from the other disc where that names them), and the drives are searched every 2 seconds until a disc of the same build arrives, which is mounted by its own disc number, so one drive serves both discs.

## 4. The field

### 4.1 Pieces

`game::FieldWorld` (`src/game/field_world.h`, split across `field_world*.cpp`) is the field game mode. It owns:

- `RoomView view_` (`room_view.*`): loads a room, uploads background layers, owns the `RoomScene`, the walk mesh (`walk_mesh.*`) and the projection camera.
- `std::vector<Ent> ents_`: one per script entity. An `Ent` holds an `Actor` (model, skeleton pose, clip playback, position on the walk mesh; `actor.*`), a `Motion` (script-started movement), the party slot and visual state.
- `script::FieldVM vm_`, `FieldCamera camera_` (scroll, scripted target, follow ease, limits; `field_camera.*`), `FieldInput input_`, `FieldWatchdog watchdog_`.
- Dialogue: `ui::DialogueDemo dialogue_` plus `extra_win_` for more windows.
- Effects: `effects::EmitterSystem`, `effects::SequencePlayer`, `GpuEffects` (section 5.5).
- `BattleHandoff handoff_` (`field_battle_handoff.*`): the pending encounter.
- `DiscIndex discs_`: the game's two file indexes (disc 1, disc 2). The disc decides which file answers a map record or movie number.
- `ui::GameState* gs_`: the shared game state (wrapper over `save::SaveSlot`), owned by `GameFlow`.
- `RemoteParties remote_` (`remote_parties.*`, `field_world_remote.cpp`): other players' parties in the room (multiplayer, `formats/multiplayer.md` section 5). Never entities: their own `Actor`s outside `ents_`, with no script, collision or trigger; their models come from the character-model cache through its workers.

`FieldWorld` is `final : public script::FieldHost` and implements every world effect a script can ask for.

World maps are ordinary field rooms whose scripts do the work: they load through `load_room` and run on the same VM, camera and walk mesh, and no separate world-map module exists under `src/game/`. Encounters are script-driven: scripts run battle ops `A3` and `C9`.

### 4.2 The field script VM

`src/script/`:

- `field_script.*`: `FieldScriptModule` parses the room's script bytes into a code area and per-entity script pointers (`kScriptSlots = 32`). The opcode table is `field_opcodes.inc`, one `FS_OP(key, lengths, spec, name, confidence)` row per opcode; `find_op`, `op_table` and `decode_insn` (disassembler) read it. The extended page is keyed `0xFE00 | sub`; `is_extension_op` marks its extension range `FE C0`-`FE FF`, where a size byte frames every instruction. Format: `docs/formats/fieldscript.md`.
- `field_vm.*`: `FieldVM`. Handlers are split across `field_vm_ops_core.cpp`, `_scene.cpp`, `_game.cpp` and `field_vm_ext.cpp` (extended page), `field_vm_extension.cpp` (the extension range: engine features for mods, always stepped over by the size byte; the mod UI ops keep their elements in `mod_ui.*`, `FieldVM::mod_ui()`, drawn by `FieldWorld::draw_mod_ui` and `sync_mod_ui_windows`; FE D1 runs `game::ButtonPanel`, RDE's button panel, which `FieldWorld::key_latch` / `keys_held` answer through and `sync_panel_window` draws). `exec(op)` tries `exec_core`, `exec_scene`, `exec_game`; an opcode in the table with no handler is counted in `VmStats::unimplemented` and skipped by its table length.

**Entity threads.** Each entity has `kRecordsPerEntity = 8` `ScriptRecord`s (pc, priority class `state`, script id, wait counter, handshake `phase`) and a 4-entry call stack. The `state` is the priority class: 0xF idle, 7 the default UPDATE loop (script slot 1), 4 ON_COLLISION, 3 ON_ACTION, 2 touch trigger. The lowest class runs; the others stay suspended. Script slot 0 is INIT.

**Scheduling.** `FieldVM::tick()` calls `run_entity(ent)` for every entity in index order, then `host_.end_of_tick(*this)`. `run_entity` picks the live record with the lowest class (`pick_record`), or restarts UPDATE in record 0 when all are idle. `dispatch()` runs at most `budget_ = 8` instructions per entity per tick (some ops grant extra; `OC_VM_TRACE=1` logs every executed instruction with its tick and the budget). A handler yields by setting `yield_` without advancing the pc; the same instruction is retried next tick. Every wait works this way: `WAIT_DIALOG`, `WAIT_MOVIE`, battles and motion waits poll a host method (`dialogue_open()`, `movie_playing()`, `battle_active()`, `motion_busy()`) and yield while it is true.

**Variables.** 16-bit slots addressed by byte offset (`kVarSlots = 0x400`). Below `kGlobalVarSlots = 0x200` they are global and saved with the game; the rest are room-local and cleared by `load()`. Known ids are in `namespace script::var` (`kScenario`, `kRoomParam`, `kMapId`, `kBattleResult`, ...).

**Loading.** `FieldVM::load(module, flag_table)` resets entities and room-local variables, then runs each entity's INIT to completion (`run_init`, capped by `kStepCapInit`) before the first tick.

**Triggers.** `trigger_action`, `trigger_collision`, `trigger_touch` start the matching script slot. `FieldWorld::step_triggers()` (`field_world_collide.cpp`) tests the player against each entity's talk and touch range or box and gives the action button to the nearest talkable entity.

### 4.3 The host interface

`src/script/field_host.h` defines `script::FieldHost`: everything the VM needs from the rest of the engine, one virtual method per op family. Conventions from the header:

- `ent` is an entity index of the current room, already resolved from the script's character reference; -1 means none.
- Methods named `*_busy`, `*_active`, `*_playing`, `*_open` are polls behind wait forms. A `NullHost` answers "done" (the VM unit test `tests/test_script.cpp` uses it).
- Coordinates are script integer units; angles are 12 bit (4096 = full turn).
- Headings cross the host boundary rotated by half a turn: `to_internal(h) = (h + 0x800) & 0xFFF` on the way in (SET_ROTATION, move headings, entrance records) and `to_script(h) = (h - 0x800) & 0xFFF` on the way out (GET_FACING, the facing variables), both in `field_world_internal.h`. An actor's model yaw is its facing minus a further `kModelYawBias` (0x400); the yaw query reports the yaw plus the bias through `to_script`, so it equals the facing query once the model has finished turning.
- Host methods run inside `FieldVM::tick()` or `load()`. A host may call `set_var`, never `tick` or `load`.

Families: entity setup, position and facing, animation, motion (`start_motion`), camera, formation walks, dialogue, layers and screen colour, music and sound, named effects, movies, battle, map jump, menus, party and roster, items and money. Globals that a script writes but the VM does not model itself (control yaw, camera y offset, push strength, pad mask, exit transition, footstep registers, ...) are named by `script::Global`; the VM stores every value (`FieldVM::global`) and forwards it through `set_global`, where the world applies the ones it models and logs the rest as stubs.

### 4.4 Windows and dialogue

Ops `E0 DIALOG`, `E1` (choice) and `E2 WAIT_DIALOG` call `open_dialogue`, `dialogue_choice`, `dialogue_open`, `dialogue_result`. `FieldWorld::open_dialogue` (`field_world_dialogue.cpp`) uses window 0 if free, else the first free extra window, resolves the portrait from the speaker entity and opens a `ui::DialogueDemo` (`ui/dialogue_box.*`, layout in `ui/typewriter.*`, data in `docs/formats/text.md`). `FieldWorld::update` routes confirm and direction input to the open window; `modal_window_open()` decides whether the action key reaches the world or the window. The dialogue log (`[Game] DialogueLog`, `rules/menus.md` 17.7) hooks in here: `open_dialogue` hands every window it shows the host's `FieldWorld::set_dialogue_log` hook as `DialogueDemo::on_logged` (and, through the voice `on_page` hook, the voice file each page found, `VoicePlayer::take_found`); the window gathers the entry at `show()` (speaker, text as shown) and sends it from `update` / `close` once it has closed (portrait, picked option). In battle `BattleView::set_story_log` does the same for the event window: `smsg_open` gathers the pages, `tick_window` sends them when the window has closed. `App::add_dialogue_line` appends to `save::DialogueLog`.

### 4.5 Pending transitions

A script never changes the host mode itself. It records a request in the world and waits; the App polls it in `advance()`.

| Request | Script op | World state | Handler |
|---|---|---|---|
| Room switch | map jump (`SET_NEXT_ROOM`, ...; `MAP_JUMP_DC` only records a jump that the movie end takes, `set_movie_jump`) | `request_map_jump` sets `jump_`; `begin_jump` starts a fade (none for a movie-end jump); `step_transition` calls `load_room` once the screen is dark | inside `FieldWorld` |
| Battle | `A3`, `C9` | `request_battle`; `handoff_.battle_state`: `None, Intro, Hold, Ready, Running` | `App::field_battle_load_step`, `start_field_battle`, `finish_field_battle` |
| Menu or shop | the screen ops FE 4A / 5B / 5E / 67 / 68 / 72 / 75 / 84 / 85 open it; the `FE 61` after each waits while it is pending or open | `request_menu`; `menu_state_`: `None, Requested, Open` | `App::handle_script_menu`; `menu_closed(result)` lets the FE 61 step on |
| Movie | `7E`, `D4` | `play_movie`; `movie_state_` and a `MovieRequest` | `App::start_movie`; `end_movie` calls `movie_finished()` |

The App asks `menu_pending()`, `movie_pending()`, `battle_ready()` and takes the request with `take_menu()`, `take_movie()`, `take_battle()`. Room-switch fade kinds come from op `FE 02`: 0 fades to black, 2 to white; 1, 3, 4, 5, 6 capture the shown frame (`ctx.request_capture`, `set_captured_frame`) and dissolve or slide it over the new room (`step_capture`).

### 4.6 One field tick

`FieldWorld::sim_tick()` (`field_world_tick.cpp`): the hold-to-ready check of a pending battle; fades and exit handling (`step_fade`, `step_transition` while the room-exit fade runs); `step_capture`; `actor.begin_tick()`; `step_cull`; **`vm_.tick()`**; `step_watchdog`; then the world steps that realise what the scripts asked for and run the player: `step_motions` (the WANDER steps, the turn rates, the scripted motions), `step_player` (pad movement on the walk mesh), `step_status`, `step_followers`, `step_triggers`, `step_visuals`, then `step_push`, `step_bone_emitters`, `step_sound_emitters`, `step_wave`, `step_sfx_slides`, `step_camera`; the effect systems (`emitters_->tick()`, `step_wakes`, `step_shadows`, `sequences_->tick()`); the encounter timeline; `actor.end_tick()`; and last the pending room jump. After each `sim_tick()`, `update()` runs `step_remote()`: the remote parties take the tick's received poses, move and animate. It reads the room and writes none of it.

Followers are not entities driven by the walk mesh: `step_followers` replays two position rings of 0x80 entries (ring 0 the leader, ring 1 the first follower) and writes the member's position directly toward an entry. An entry is appended only on a tick where that member actually moved (the leader's pad step records the spot it stood on before the move; a scripted move appends once the leader is more than half a unit from the last entry, and only while the leader's script runs the update op; a leader on a push tile appends its spot every tick). An entry on a push tile is walked to and then replayed entry by entry (`rules/field_actors.md` 4.2, rule 4). The turn-rate and scripted-turn bookkeeping (`step_turn_rates`) and the water wake spawn run only on every second tick (odd tick counts), the engine's per-frame cadence. After a room load `step_cull` skips its off-screen test for 4 ticks.

### 4.7 The room-script scan

`script/script_scan.*` (`script::scan_script`) reads one room's field script without running it and lists what it can do: gives and takes of items, elements and key items (op BB, ids in its numbering: items below 0x200, elements 0x200 + id, key items 0x400 + number), gold (BD), battles (A3 with the battle id, C9 with the scene + 0x200), party joins (7B), roster bits set and cleared (96 / 97), story sets (6C), room changes (5A / DC) and flag writes (a single bit of a global variable by 71 / 15 / 1A, a literal value by 10 / 11; only variables from 0x50 count, the ones below are the engine's scratch). `game/room_scan.*` runs it over every room the VFS holds (`scan_rooms`: the script as the field runs it, subfile 3 decoded with the room's script corrections; one room per worker thread, the result in room order), groups the treasures (`treasures`) and turns a battle id into its encounter groups (`battle_scenes`: the distinct scenes of the eight `symtbl` variants, the one scene for an id from 0x200). The game itself does not run it; `occ scan` writes it as tables (`docs/tools.md`). It reads and decodes every room's script, so a caller runs it once, off the main thread, and keeps the result.

**The walk.** Every script slot of every entity is walked on its own, depth first over both sides of every branch, through gotos and CALLs (a four-entry return stack, as the VM keeps). Each event carries the tests that hold on every path to it: at a position more than one path reaches (a script entry, a jump or call target, the position after a CALL) only the tests common to all arrivals are kept, and the position is walked again while that set shrinks; pending paths are taken in code order so that most arrivals come before the code after the meeting point. A test is a comparison of a variable with a literal (IF_JUMP, the story ops 69 / 6A / 6B / CD / CE on variable 0, the bit test 73), a character in the party, recruited or carried over (94 / 95 / E5 / E6 / E8), the leader (9A), an item owned (B4), gold (BC), the dialogue choice (variable 4, dropped at the next MULTI_CHOICE) or a held button (50 / 51). A write to a variable drops the tests on it. Only a branch between two literals is decided; path constants decide nothing (a loop counter set before its loop would close the loop's exit). The side of a held-L1 / R1 test (op 50, masks 4 / 8) is not walked: it opens the developers' menus (room warps, party and story setters) that nearly every room carries, whose entities the rooms also make inactive at load (`fieldscript.md` 10.8, variable 0x34). The walk reaches every BB, A3, C9, 7B, 96, 97, 6C, 5A and DC the disassembler lists as reachable except those menus' 5,588 room changes, party, roster and story sets.

**Operands.** An operand that reads a variable takes the value the path last wrote to it (the literal kept where all arriving paths agree), else the one literal the entity's INIT writes to it, else every literal the room writes to it, when the room never writes it a computed value. Several values remain where a room picks among literals (kji_b01i's code machine: Rainbow Shell, Nostrum or Hot Shot). A give also lists where its id is written in the code (`value_sites`, the code offsets of the literal words): its own operand when that is a literal, else every SET (10) of a literal to the room variable it reads whose literal is one of its values (each operand knows its code offset, `Operand::pos`).

**Flags and treasure.** A give's flag is the first flag write after it, following the fall-through side of each branch, gotos, CALLs and the scripts a RUN_SCRIPT starts on an entity of the room, for 48 instructions. `flag_guarded`: a test on the path reads that flag; `flag_at_load`: an INIT of the room tests it, so the room shows the thing taken when it loads. A treasure site (`is_treasure`) is a give of an item, element or key item with a flag some INIT tests; a treasure (`Treasure`) is every site that sets the same flag (the same chest in the copies of a room, a pickup that gives a key item and an item), keyed by the flag (`flag_key`: `var * 8 + bit`). `chest`: a site runs the chest routine, whose path compares the stock with 99 first (`capacity_check`). Whether a save has a treasure is the flag's bit in the slot's variables (`ScanFlag::is_set` over `save::SaveSlot::var`). Stable ids: an event is `<stem>:<entity>:<code offset>` (`event_id`), a treasure its flag key.

**Entities.** Each entity's role is the first of 0E (party slot), 0F (room model), D1 (field monster) its INIT reaches; `inactive_when` lists the tests on each INIT path where the entity makes itself inactive (36 with b = 0 on itself). `inactive_at` holds the story values and entrances at which the INIT certainly leaves it inactive: the INIT is run once per pair of candidate values (0, the largest, and each literal its tests read the story counter or ROOM_PARAM against, with its neighbours), those tests decided until the INIT writes the variable, every other test taken both ways; a pair counts when every way ends with the entity inactive. `reactivated`: some walked 36 with b != 0 names the entity. The room also lists the global variables its walked instructions may write (`written`; `writes_any` when a bit write's number is a variable), and an exit its entrance (`entrance`, the literal ROOM_PARAM of 5A / DC).

**Story drops.** `game::story_drops` (`records_info.*`) follows a game over the scan: a state is a room, the entrance it was entered by, the story counter on entry and the counter now, starting at the first room of a new game (entrance 0, story 0), never through the title room. An exit or story set is taken when no test on its path is known to fail and its entity is not known to be inactive. Known are the story counter; the entrance, in a room none of whose scripts writes ROOM_PARAM; a global variable that no script and not the engine writes (below 0x80 and from 0x300 the engine writes), which stays 0; and the entity's `inactive_at` at the entry state, for an entity that is not a party slot and is not `reactivated`. Every other test may pass, so the drops it reports (a set that writes a value below the counter it runs at, with both values) are a superset of what a game can do; the record pages never call a window closed that a drop can reopen (`rules/menus.md` 17.6).

What the scan does not know: the tests of a script that starts another one through RUN_SCRIPT are not carried into it; which side a variable test takes; whether a room can be reached at all, and when (apart from the story drop search).

**In the game.** `game::ScanService` (`scan_service.*`, `App::scan_service`) runs the whole scan once on a worker thread, started at boot when `[Game] OpenCrossMenu` or the randomizer is on and when either is switched on; the record pages read `ready()`, which stays empty until the scan has finished and then keeps the result for the run; the randomizer's plan blocks on `wait()` the first time it is built. The worker reads the unmodified game: a `vfs::Vfs` of its own opened on the same game folder (no mod overlay, the PS1 file tree as in original art), or the app's VFS when that folder is no RDE install (the game played from its discs), so what the pages derive from the scan is the same for every player. With the scan it loads that game's battle tables and numbers the enemy species in story order (`game::bestiary_order` over `battle_sites`, `data/bestiary.*`; `rules/menus.md` 17.1.1) with the world each story area's name is shown with (`data::area_worlds` over the scan's rooms; the world rule is `rules/menus.md` 17.1.1), read through `bestiary()`. Nothing is written to disk. `game/records_info.*` turns the result into what the Characters, Elements, Key items and Treasure pages know (`ui::RecordsInfo`, `ui/menu/records_info.*`, `docs/rules/menus.md` 17.6); `App::update_records_info` builds it once and hands it to the menu. A story range (`story_range`) is only what the randomizer's plan blocks on `wait()` the first time it is built.

## 5. Battle

Three layers: the rules (`src/battle/`, headless), the enemy script VM (`src/battle/pac_vm.*`), and the presentation (`src/game/battle/`, `src/game/effects/`).

### 5.1 The rules

`battle::Battle` (`battle.h`, `battle.cpp`). `kPcSlots = 3`, `kEnemySlots = 6`, `kUnits = 9`; units 0..2 are the party, 3..8 the enemies. It is constructed with `GameTables`, an injectable `Rng` (`rng.h`; tests script it) and an `EnemyBrain`.

- `start(party, scene, options)` builds the units, calls `brain.begin_battle`, then runs enemy turns and time until a party member can act.
- `apply(Command)` is the one entry for player input. A `Command` is `Attack` (a chain of strengths 0, 1, 2), `Element` (grid cell and target), `Defend` or `Run`. After `validate` it resolves the action (`do_weapon_attack`, `cast_element`), `post_action`, `check_end`, then `run_reactions` (script counter-attacks) and `settle()` (enemy turns and `time_advance()` until a party member can act or the battle ends).
- `open_menu(pc)` is the host's report that a PC's top command menu came up (the menu passed to it, an L1 / R1 switch, a re-entry); it ends that PC's Defend guard (`docs/rules/battle.md` section 2.2). `BattleView` calls it every tick its top menu is up and not script-locked, from the first tick after the menu entry (the PC's command window opening, `docs/rules/battle.md` section 3.4: `begin_menu_entry`, `tick_menu_entry`); input reaches the top menu only from then on.
- `rules.*` holds the pure formulas (hit chance, damage, heal, status rolls, stamina, growth, loot). Statuses are bit sets in `namespace st`. Every random term goes through the `Rng`.
- Every resolved effect is appended as an `ActionEvent` (kind, actor, target, `hp_before`/`hp_after`, hit code, crit, KO, ring state, the element-trap block (`TrapHud`, drawn by the HUD), text, `action` id); `drain_events()` hands them over. `outcome()` is `Ongoing, Victory, Wiped, Fled, Scripted, Stalled` (`Stalled` ends a `settle()` that used up its step guard; the view's outro and the field hand-off treat it like a flight); `result_code()`, `rewards()` and `growth()` carry the after-battle data. `set_cheats` and `set_invincible` take the cheat flags.

Pip's evolution is `Battle::evolve(unit, form)`, run by the form-change element (pgdat mode 45): it sets the innate colour to the one with the most colour points in the battle script variables (the last of equal ones), zeroes the six counters, sets the unit's kind, AP and countdown, rewrites the form's tech cells and growth column on the unit and the party record, and marks the member `evolved`. `apply_battle_result` (`game_session.cpp`) persists it into the save record: the model id, the tech cells and (through the growth column) the growth.

The Dopplegang pool is a 256-bit mask held in 16 script variables of the field. `app_battle.cpp` passes it to `Battle` at the start (`options.dopple_mask`); `Battle::dopple_credit` sets the bit of a defeated enemy when the last acting party member is Sprigg (character 26) or wears accessory 0xFC and the enemy's record allows it, i.e. the enemy is not flagged uncopyable; `finish_field_battle` writes `Battle::dopple_mask()` back with `FieldWorld::set_dopple_mask`, into both the variables and the save header. Variables 0x3D0..0x3DE (Pip's colour points among them) take the same path as the battle's script variables 0x00..0x0E: `options.saved_vars` from `FieldWorld::battle_saved_vars`, back with `FieldWorld::set_battle_saved_vars`.

`Battle` resolves an action instantly. The presentation decides when each result becomes visible. That split lets the same class run in `ocbattle sim`.

Versus battles (`docs/rules/versus.md`) run in the same class. `start_versus(side_a, side_b, battlefield)` takes two `VersusSide`s (party, summon stars, Dopplegang pool) into units 0..2 and 3..5, with no scene and a `VersusBrain` (no script). `side_of(unit)` and `player_unit(unit)` replace the index tests: targeting, auto-targets, sweeps, the gauge, double and triple techs, stamina recovery (an action of one side recovers the other side as a teammate's would; the turn side gets nothing from its own actions, and a Defend ends the defender's turn: `done(unit)`), upkeep, traps, stars, the pool, Pip's tech colour and the Dopplegang backup are per side; enemy-cast reductions, rewards and the cheats are off. `can_act` adds the turn: only `turn_side()` acts. `acting_side()` is the side whose command comes next: the side that owes a Dopplegang pick (`form_owed()`, also after its cast ended its turn), else the turn side; `validate` takes a versus command only from a character of the acting side, and while a pick is open only that pick, and an `Element` command it refuses leaves the units as they were (the element menu its `apply` opened first included); hi status 0x20000 waives no stamina in a versus battle (`costs_waived`). The menu state that a normal battle's view sets directly travels as commands through `apply` like any action, so two games apply it at the same point: `EndTurn` (with `timeout`), `Focus` (`open_menu`), `ElementMenu` (`open_element_menu`) and `Form` (the pick of a Dopplegang cast). `settle_versus` runs the scheduled turns (confused or frozen characters), passes the turn of a side that cannot act and advances time for a side whose turn starts stuck. `outcome()` reads from side A (`Draw` added), `versus_end()` says how it ended, `winner()` which side won. `state_hash()` digests every rules field and the generator's position (`Rng::fingerprint`), not names or log text; `encode_versus_side` / `decode_versus_side` (`versus.h`) are the versioned exchange format, `legal_versus_side` refuses a received side no real game could send (`rules/versus.md` section 1.1), `versus_battlefield(tables, seed)` the stage pick, and `data::battle_data_fingerprint(tables)` the data check (it includes `data::kVersusRulesVersion`). `ocbattle versus` plays a battle twice in lockstep and compares the hashes after every command; `ocbattle versus-net` plays battles between two clients over a running server.

### 5.2 The PAC enemy-script VM

`src/battle/pac_vm.h`, namespace `oc::battle::pac`. Scripts are `battle/event/evtNNN.pac`, resolved by `game::DiscIndex::battle_script` from the scene's file-index record (fallback `evt0000.pac`); `BattleView` supplies the loader. Format: `docs/formats/battlescript.md`.

- `pac_opcodes.inc` is the opcode table, `PAC_OP(code, length, name, confidence)`; `pac_vm.cpp` includes it to build `op_info(code)`. Opcodes not listed get the default stall handler.
- `Module::parse` reads the entity count, an `[entity][slot]` pointer table (`kSlots = 32`) and the code. `Vm` interprets frames per entity; `tick()` makes one pass over all entities; `launch(unit, slot)` pushes a slot frame; `run_slot(unit, slot, out)` launches and ticks until it returns, collecting attacks queued with op 67 as `QueuedAttack`.
- Slots as `ScriptedBrain` uses them: 0 init, 1 idle loop, 2 the unit may act (`plan_turn`), 3 the unit was killed (`on_killed`), 4 the unit was attacked (`on_attacked`).
- An idle loop can queue an attack itself (Mama Komodo's arrival: self-cast, wait, reveal). `Vm::settle` moves such entries to a list, `ScriptedBrain::take_idle_plans` turns them into actions and `Battle::run_idle_plans` executes them as their own action after the one that woke the loop, so the cast and its camera play before the reveal.
- The VM reaches the battle only through `pac::Host` (`alive_mask`, `read_field`, `write_field`, `rnd`, `pick_element`, ...). `ScriptedBrain::BattleHost` implements it over `Battle`, so the VM is testable alone.
- Presentation requests (dialogue, camera shots, poses, effect starts) are not performed by the VM. It appends `pac::Event` records stamped with a virtual time; `BattleView::collect_events()` moves them into `script_stream_` for replay.
- `ScriptedBrain` implements `EnemyBrain`; with no script it falls back to `RandomBrain`. `Battle` asks it `hidden`, `untargetable`, `death_owed`, `forced_result`, `no_drops`, `menu_locked`.

### 5.3 How an action is resolved

1. The player confirms in the HUD; `BattleView::execute(Command)` (`battle_view_action.cpp`) calls `Battle::apply`. HP is final inside `Battle` at this point.
2. `BattleView::collect_events()` moves `drain_events()` into `queue_` (grouped by `ActionEvent::action`) and the PAC events into `script_stream_`.
3. `BattleView::tick()` (60 Hz) calls `tick_action()` (`battle_view_sequence.cpp`) to play one group: `begin_engage`, `start_hit`, `start_return`, `start_release`, `end_group`. The motion follows the models' animation-sequence scripts (`battle_seq.*`): approach, attack, reaction, return. Displayed HP, damage numbers (`battle_numbers.*`) and KOs change on the script's events (`on_script_event`, `on_damage`, `spawn_pop`), not when `apply` ran. Within one tick the camera timelines run first (`tick_camera`), then the units' scripts (`tick_units`: the monsters, units 3-8, before the party, units 0-2, so a PC's hit reaches its target's reaction script on the next tick), the action, the effects and the anmseq tick (`anm_tick`), then the camera's shot list (`BattleCamera::tick_shots`, `formats/battle_effects.md`) and the battle-script stream (`script_pump`).
4. Element casts start an effect pack (`battle_view_fx_cast.cpp`); hits are queued behind the effect's timing.
5. When the actor's own action is over (before any enemy actions in the queue) the next party member's command window starts opening (`begin_menu_entry`); with the queue empty and the window open its top menu takes over, or `begin_finish` / `tick_finish` ends the battle and sets `finished()`.

### 5.4 Presentation

`BattleView` (`src/game/battle/battle_view.h`) is split by concern: loading (`battle_view.cpp`, `battle_model_cache.*`), camera (`battle_camera.*`, `battle_view_camera.cpp`), unit animation (`battle_pose.*`, `battle_seq.*`, `battle_view_units.cpp`), action playback (`battle_view_action.cpp`, `battle_view_sequence.cpp`, `battle_view_script.cpp`), effects (`battle_fx.*`, `battle_fx_textures.*`, `fx_mesh_tiles.*`, `battle_spell_lights.*`, `battle_view_fx*.cpp`, the trail and pseudo-actor files), the stage (`stage_scene.*`), HUD and menus (`battle_view_ui.cpp`, `battle_view_hud.cpp`, which also draws the element-trap block), results (`battle_results.*`), sound (`battle_audio.*`) and the swirl (`battle_transition.cpp`). `BattleView::set_select_held` (Select held during a cast hides the HUD), `set_autohide_cast` (`[Enhancements] AutoHideCastHud`: the same hiding on every cast) and `set_keep_intro_layer` (`[Enhancements] RetainBattleScenery`: the stage's intro scenery layer is not stopped when the intro ends) are pushed by the App every frame. `texture_dump.*` is the headless "Dump all textures" job used by the Mods tab and `occ dump-textures`.

A versus battle (`StartOptions::versus`, a `VersusSetup`: the seed, both sides, the side this game plays, the opening stamina and the battlefield) is drawn by the same view (`battle_view_versus.cpp`). The rules start with `Battle::start_versus` on a `VersusBrain` and the shared seed (the environment's seed is not read); the scene given to `start` is a carrier (`battle::versus_carrier_scene`: the lowest ordinary scene of that background) that lends its stage and party spots only. Each game shows its own player's party in units 0..2: the game that plays side B swaps units 0..2 with 3..5 between the rules and everything the view keeps (`rules_unit`, `bunit`, the query wrappers, `map_event` for the events' actor, target, aim, group and trap block, `rules_command` for the commands), so the menus, targets, camera and HUD keep their party = 0..2 logic. The other party stands on the party's spots mirrored in x, turned half a turn, and spawns as enemies do. The menu state the view sets directly in a normal battle goes through the rules as commands (`Focus` when a PC's top menu takes over, `ElementMenu` when its grid opens, `Form` right after a Dopplegang cast), and the view never settles the rules: the turns run on by themselves. The other side's commands come through a `VersusLink` (`versus_link.h`, library `oc_versus_link`: `send` this game's accepted commands, `poll` the other side's in the order its game applied them, `send_hash` the state hash after every command, `status` open / desync / closed / conceded / forfeited, `away` who is out of reach and for how long); `versus_pump` applies them one action at a time while the view is idle and the other side acts (`Battle::acting_side`; the view's `can_act` keeps this game's menus shut while the other side owes a Dopplegang pick), with the state commands that go with it, a refused one (or one naming a character of this game's side) ending the battle with no result; a conceded or forfeited link ends it with `Battle::concede`, as does the other side overrunning its turn on this game's own clock (its 60 s of idle time plus 15 s, or 5 minutes in all, not while it is known to be away). `LocalVersusOpponent` is a link that plays the other side in this game (`battle::VersusAutoPlayer` without early End Turns, timeouts or Run), and under `set_auto` the same player commands this game's side. `NetworkVersusLink` (`versus_net_link.*`) is the other player's game over `net::MultiplayerClient` (`formats/multiplayer.md` section 8.4): commands as text (`versus_command_text` / `parse_versus_command`), each of the other game's checked to be the next of the stream, the hashes compared both ways, the server's word on the other player (away, gone) and the 90 s silence limit, counted from the last message that moved the battle on (a next command, a check of one of this game's); more than 1024 commands waiting close the link. The view adds the End Turn row, the turn banner and 60 s clock (the banner says "Waiting for <name>... N" or "Reconnecting... N" while the link reports a player out of reach), the Run confirm, and the outcome plate in place of the results; `versus_result()` tells the host how it ended.

`BattleResults::open(battle, scene)` returns false when there is nothing to show (result codes 1, 3 and 4, scene 0x1DD, or an outcome other than victory, flight or scripted end); the host then calls `finish_field_battle` at once, otherwise after the screen's `done()`. Pages, each advanced by Ok: the star-up message first when the battle raised the star; then one page per member who gained a stat; then the heal-item menu, only if a member is hurt and the grids still hold an unused healing element (Cancel or "do not heal" skips it); then the spoils; then the white exit fade. A member's HP gain is added to their current HP (cap 999) when their page is first shown, so the screen's HP is the final one. After `done()` the host reads it with `take_final_hp()` (per party slot, -1 for no member; false when no screen ran since the last call) and writes it over what `apply_battle_result` stored, clamped to 1..max HP.

### 5.5 The effect engine

`src/game/effects/` (`oc_effects` headless, `oc_effects_gpu` GPU glue). The same engine runs room effects, battle effects, the battle stage and the title scene.

- `EmitterSystem` (`emitter_*.cpp`) instantiates type-0x0A emitters from parsed `RoomEffects`, steps them per tick and turns live objects into `DrawQuad`s with the ordering-table depth rule and blend modes. No GPU or audio dependency.
- `SequencePlayer` (`sequence_player.*`) runs type-0x10 sequence tasks: each command has a wait in ticks; emitter control, ambient colour, shake, rumble and sound ops run here; scene ops (actor show/hide, camera records, flashes) go out through `SequenceHooks`.
- `effect_slots.*` maps an effect id to its pack files. `gpu_effects.*` uploads sprite sheets as atlases and draws quads through `render::ParticleBatch`; every sprite sits in its own cell inside a one-texel border that repeats its edge texels (`pad_sheet_atlas`), so bilinear sampling at a sprite's edge never reads the sprite stored next to it. `soft_raster.*` is a CPU twin for `ocprd preview` and tests. `room_meshes.*` draws effect mesh objects; `light_extract.*` serves the spell lighting of the optional `[Enhancements] Lighting` setting; `strip_smooth.*` smooths the ring / tube effect meshes; `fx_math.*` holds the fixed-point and matrix helpers.
- `effects/bespoke/` holds hand-written overlays for individual techs that the generic engine cannot express; `bespoke.cpp` is the registry (`BespokeRegistry::instance()` registers every family, the later model-steer ports replacing older stand-ins of the same name). The selection rule: an effect slot's overlay file (`EffectSlot::prg`) is matched by its lower-cased file stem against the registered names (`find`, tolerating a leading authoring index such as `46black` for `black`); `bind_slots` binds each matching slot's element id, and `find_element(eid)` returns the overlay that `BattleFx` creates (`create`) when that element's pack runs.

The field starts effects by name through `named_effect`; `FieldWorld::build_effects()` creates a room's emitters and sequences and starts the pack's `loop` sequence. `game::TitleBackdrop` plays the title scene's effects. Formats: `docs/formats/battle_effects.md`, `room_effects.md`, `battle_stage.md`, `title_scene.md`.

### 5.6 Field and battle hand-off (`app_battle.cpp`)

The App owns the hand-off because it owns both objects. `BattleView` is initialised once; each encounter loads a scene into it.

- `make_field_battle_args(rq)`: `tables.scene_for` gives the scene; `world.party_chars()` and `game::party_member_from_state` build the party (the Relief Charm swaps in); `game::battle_setup` adds growth and the bench; the A3/C9 battlefield operand picks the stage.
- `field_battle_load_step()`: from the fourth frame after the request, loads in 3 ms slices (`BattleView::begin_load`, `load_step(3.0)`, `prepare_fx_targets`) behind the field's encounter swirl. The steps: rules, stage files, stage scene, the shared `battle.prd`, the effect sheets and meshes every attack draws from (the resident `battle.prd` set and the particle library, uploaded in slices here instead of at the battle's first hit), one unit model each, the HUD fonts (kb_70, kt_70, ch_100 and bn_70, the element list's and the cast title's face outside Japanese: each face is built here, not by the first text that asks for it in the fight).
- `start_field_battle()`: `world.take_battle()`, `battle.start(...)`, `battle.begin_transition(...)`, sets `battle_in_field`. An invalid scene is reported as "fled" (`world.end_battle(2)`). `take_battle` drops the extra animation packs as the original's field snapshot does (`Actor::drop_ex_pack`): every entity that holds a pack (a C1 or BF not yet followed by C0; `Actor::holds_ex_pack`) loses it and its current animation becomes its stand slot, whatever it was playing, a base clip included; a stand slot that names a pack clip (0x80 and up) is set to 1 for good. Entities without a pack keep their animation. A script can reach a battle op with a pack loaded (gal_b16e, hid_a04f, jac_b01f and mis_b02e run C9 after a C1 with no C0 / BF in between; mis_b02e's Kid plays pack clip 0x80 into battle 390).
- `finish_field_battle()`: maps `battle.outcome()` to a code (Victory 0, Wiped 1, Scripted = `result_code()`, else 2), calls `game::apply_battle_result` (`game_session.*`), copies the results screen's final HP back, and calls `world.end_battle(code)`. The original rebuilds the field after a battle: every model starts afresh (no clip, no blend, no sequence) and every entity with a 3D object (`EF.14` clear) has its current animation submitted again, so a model with an animation-sequence table runs that id's sequence from the top and the sequence cuts its clip in at frame 0, and any other model cuts the clip in at frame 0; the anim-done bit is set. No entity holds a pack then, so a pack id plays the stand slot. `end_battle` does this with `Actor::restart_anim`. A frozen clip after the return is not a kept frame: a monster beaten by its own fight is made inactive and hidden (`D2`), and a hidden or culled entity runs no animation (fieldscript.md section 8.1). The original's fresh model has no previous clip, so its first sequence clip blends in from an undefined pose for the sequence's blend length (16 ticks for the party's stand); that blend is never seen: it ends about 30 frames before the return's fade-in lights its first frame, and the first lit frames show only the stand sequence's own loop blend (stand into stand, below a quarter of full brightness). OpenCross cuts the clip in, as at a room load. A wipe in a fight that is not losable loads the game-over room (map id 9) (`enter_game_over`; the rule is `game::wipe_ends_game`, `rules/battle.md` 7.5).
- Retry lost battles (Quality of life, `rules/battle.md` 7.6): `start_field_battle` keeps an `App::RetryPoint` for every field battle that starts (not a versus battle): the `game::BattleSnapshot` (`game_session.*`: the whole `SaveSlot` and the field VM's variable array), the field's `BattleRequest`, the scene it resolved to and the `ext_save.dat` battle counter. When the view finishes on a wipe that ends the game and the cheat is on, `advance` calls `open_retry` instead of `finish_field_battle`: `ui::RetryPrompt` (a `DialogueDemo` showing an engine-built message with a line choice) runs in the `battle_in_field` branch through `retry_step` while the field stays in its battle state (`BattleState::Running`, nothing of `end_battle` has run). Retry restores the snapshot (`restore_battle_snapshot`, the counter) and `restart_field_battle` builds the arguments again from the request (`make_field_battle_args`: new seed, the party from the restored state) with the kept scene, takes a new `RetryPoint` and calls `BattleView::start` plus `begin_transition` with no field picture; Retry after changes opens `MainMenu::open_limited` first and restarts when it closes (`world.state_edited()` rebinds the field party); Give up calls `finish_field_battle`. A battle's end (`finish_field_battle`) or a restart drops the point.
- A versus battle (`start_versus_battle(setup, link, net)`: from a free field, refused while a battle dev switch of the environment is set) takes the same path: `versus_next` makes the next field battle request (battle flags 0, the regular battle music) a versus battle, and `make_field_battle_args` then gives only its carrier scene, battlefield and setup (no Relief Charm write, seed variable, party swap or Dopplegang setup). At the end `finish_versus_battle` writes nothing back (no `finish_field_battle`, `apply_battle_result` or results screen): `FieldWorld::end_sandbox_battle` restores the music and fades in as `end_battle` does, with `BATTLE_RESULT` and the last result code as they were, so the save is unchanged; a server's battle sends its `pvp_end` (`desync` when the link ended out of step). Pause, fast and slow mode (`speed_locked`) and the Debug tab's casts are off while it runs.

`app_feedback.cpp` joins the pictures: the field's last output and the battle's first frames share one previous-output feed-back (`fb_rt[]`), so no black frame appears. `encounter_strips.h` holds the curve both sides evaluate.

## 6. Rendering

### 6.1 Backend

`src/render/gpu_context.*`: `GpuContext` wraps SDL_GPU. `init(window, vsync, driver)` takes an optional driver name (`vulkan`, `direct3d12`, `metal`) and falls back to SDL's choice. Shaders are GLSL in `src/render/shaders/` (`sprite`, `mesh`, `stage`, `particle`, `crt`), compiled at build time and embedded as SPIR-V, DXIL and MSL (`shaders.h`, `embed_shader.cmake`; without shadercross only SPIR-V is embedded); `create_shader` picks what the device accepts. `set_msaa(samples)` (1, 2, 4 or 8, lowered to what the GPU supports; very large render-scale targets get fewer samples) and `set_anisotropy(level)` (1 to 16) take `[Video] Msaa` and `Anisotropy` and apply live: a change releases the multisampled images, and the 3D pipelines bind `filtered(sampler)`, the anisotropic twin of a linear sampler. `begin_overlay()` moves the rest of the frame onto the resolved image for ImGui. `hold_depth()`, `suspend_rendering()` and `resume_rendering()` keep a rendering's colour and depth across passes drawn in between (`render::PostFx`).

`begin_frame(Frame&)` starts a render pass into colour and depth images and returns false when the window is minimised or resizing. `end_frame()` presents. Each frame records two command buffers: `upload_cmd()` (copies, run first) and `cmd()` (draws). `begin_target` / `end_target` render into a `RenderTarget` and nest. `request_screenshot` and `request_capture` read a frame back. `kFramesInFlight = 2`.

### 6.2 Batches and pipelines

- `SpriteBatch`: 2D textured quads in a caller-chosen virtual space; blend modes Alpha, Multiply, Add, Subtract, Average, Premultiplied, AddAlpha. `TextBatch` draws text over it (RDE spritefont faces, the PS1 bitmap font). A spritefont face's glyph atlas (a fill, a backdrop and an outline texture, 2048 texels wide) holds the glyphs asked for so far: the face's first build packs them tallest first and leaves 64 spare rows; a glyph asked for later is placed after them and uploaded as the rectangle it covers, and only a glyph that no longer fits under the 4096-row cap packs the whole atlas again.
- `MeshPipeline`: skinned, alpha-tested 3D meshes (palette of up to 128 joints) for field actors, battle units and the Status model. `DrawParams::opacity` below 1 draws a model see-through (a depth pass, then its solid pass alpha-blended); only the multiplayer `Translucent` option uses it.
- `StagePipeline`: battle stage and title scenery packet meshes as instances placed by object scripts (colour, blend, ordering-table bias per instance). With nearest sampling the fragment shader picks the texel from the interpolated packet texel coordinate and reads it through the face's page origin and texel size, so a face shows the same texels from a raw atlas and from a baked object image of any layout or scale (`formats/mods.md` section 6.2); bilinear draws sample the normalised coordinate.
- `ParticleBatch`: effect quads, depth-tested against room layers and actors. `set_texels` switches the following quads to the same texel pick (the room meshes' faces).
- `ScreenPass`: the optional full-screen shaders (`[Shaders] Fullscreen`, `Grade`), also the pause screen's colour ramp. `PostFx`: `[Shaders] Ssao` and `DepthOfField` on the battle 3D picture. `RenderTarget`: off-screen colour and depth. `ImGuiLayer`: Dear ImGui over SDL_GPU.

HD images that RDE ships per language (`<stem>_<en|fr|it|de|es|jp><ext>` beside the plain `<stem><ext>`: the battle results UP marker, the HIT% leader line, the party-change frame, the menu panel shapes) are read through `ui::localized_path` (`src/ui/localized_path.h`): the suffixed name of the game language when the file system holds it (a mod's copy counts), else the plain name.

Textures that are not whole files (stage atlases, effect meshes, effect sheets, room-model pages) are managed by `texture_registry.*`, `stage_tiles.*` and `model_tiles.*`: they are cut into content-hashed tiles that can be dumped to PNG and replaced by mods. Replacement does not stall the frame: stage tiles are replaced with `parallel_for` on worker threads (`stage_tiles.cpp`), their textures are created from a worker with `Texture::create_blocking` (upload in bands on separate command buffers), and field and battle models resolve their texture mods in the CPU half of a load on a worker (`render::resolve_model_textures`, `Actor::make_model`, `battle_model_cache.*`). A character model's files are found and decoded by one reader, `game::read_model_files` (`src/game/model_files.*`: the field pairing `.tim` + `hd/` 4x `.tim` + `fieldobj/ex` pack, the battle pairing `.ltd` / `.ltc` + `at0.prd`), used by the field, battle, the texture dump and `ocmodelview`. The playable models' status-screen and battle textures share one replaceable pair, the character textures (`render/character_texture.*`, `formats/mods.md` 6.1.1).

### 6.3 What draws what in a frame

`App::draw_frame(frame)` (`app_draw.cpp`): pause handling (freezes battle, movie, mixer) and CRT begin; `apply_frame_options()`; then one of movie (`movie_player.draw`), boot logo (`flow.draw_boot_logo`), a flow screen (`flow.draw`) or the scene (`draw_scene`); then veils (`movie_player.draw_held`, `flow.draw_overlay`), CRT end, feature icons, pause screen.

The model matrix gains the ratio of the two models' body heights: feet (y = 0) to the highest vertex of the head (the head above and its menu partner), its chain down to the root and what hangs from them (hair, hats, collars), skipping whatever hangs under a paired joint off that chain (arms, legs and held props such as Marcy's shield, which would make a whole-mesh measure wrong). The ratios run from about 1.5 (Turnip) to 2.2 (Leah); `kBattleModelFieldScale` (1.97, the field-to-battle ratio a battle model on a field entity is drawn with) stands in when there is no head to measure. The menu model's own S3 part flags replace the field model's (`FieldWorld::menu_parts`), for the actor, its reflected copy, its silhouette shadow tile and the remote parties' members. The field actor's own part visibility still counts: its sequences show and hide constructs (a Porre soldier's rifle is hidden while he stands and shown while he runs or aims; Turnip's arms and sword are hidden under the closed cape), so every menu joint is shown with a field construct (`MenuRig::shown_with`: the construct holding every vertex of its field joint, a held prop's field piece, its parent's for a joint without a partner; none when the field joint's vertices lie in several) and `menu_rig_palette` takes the actor's hidden constructs. A piece that is not drawn (hidden with its construct, or `kHiddenJoint`) has its vertices collapsed onto its joint, or onto the topmost joint above it that is not drawn. The cache (`menu_bodies_`, one entry per battle model and, for a story NPC, per field mesh: the Dragoon private's two field meshes differ in height, so each has its own draw scale) is dropped with the character models (art switch, shutdown, remote models leaving) and rebuilt when the field model or the texture registry generation changes.

### 6.4 PS1-style quirks, widescreen, scale, post-processing

- **Layer space.** `render/camera.h`: a 320x240 layer space; the field is a 320x224 buffer with a 2-unit crop (`kFieldRows`, `kFieldCrop`, `kPresentRows`). `Letterbox` (`fit`, `field`, `wide`, `identity`, `veil_rect`) maps it to the window. The room's camera block gives the view matrix and an off-centre perspective.
- **Ps1Jitter** (`ps1_jitter.h`): the 3D pipelines snap projected vertices to whole PS1 pixels and interpolate UVs screen-linearly.
- **Ps1ResGraphics / Ps1ResUi**: two independent switches. Ps1ResGraphics draws the field picture, battle 3D and title sea into a PS1-sized target (`field_rt` 320x224); Ps1ResUi draws the UI screens, battle HUD, results, pause screen and field windows into PS1-sized targets (`ui::LowRes`, `ps1_pass_43`, `ps1_pass_wide` in `app.h`). Both scale up with nearest sampling. `cull_frame(wide_cols)` scales the PS1 packet-culling limits with the picture width.
- **Widescreen.** `render::wide_extra()` is the number of extra layer columns per side, set each frame in `App::frame_settings` from the window shape. Layer space and script units do not change. The title room's 4:3 layers compose with 0 extra columns. The parchment screens (main menu, party screen, shops, name entry) take the columns through `set_wide_columns` and continue their backdrop over the widened frame (`ui::ps1::parchment_grid`; `ui::Canvas::wide` for the flow's draw lists), and with 0 columns cut their draws at the sides of the 4:3 picture (`ui::ps1::picture_clip`); the screens that are 4:3 pictures (title menu, slot lists, user guide) stay centred between black bars (`rules/menus.md` section 16). `[Video] WideHud` limits how far the battle HUD, the main menu and the shops spread their layout. `[Video] FovDeg` sets `render::fov_scale()` for 3D pictures not tied to painted backgrounds (battle, title sea).
- **Render scale.** `[Video] RenderScale` draws the 3D pictures into `scene_rt` at scale times the window size (`scene_extent`, at most 16384 per side), then `composite_scene` filters it down. HUD, menus and veils stay at window resolution. With Ps1ResGraphics the PS1 target is used and the scale does not apply.
- **Post and enhancements.** Full-screen shader pass, damage-floor jolt blur (`jolt_rt[2]`), encounter feed-back and the FE 14 frame echo (`fb_rt[2]`), screen ripple. The `[Enhancements]` keys (Lighting, EdgeBlend, AutoHideCastHud, RetainBattleScenery, FullPrecisionEffects) are applied in `apply_frame_options`; with them off the output is the PS1 picture. `Lighting` covers the cast shadows of battle units, field actors and the title's models (`render::ShadowPipeline`; `battle_view_shadows.cpp`, `FieldWorld::prepare_shadows`, `TitleBackdrop::cast_shadows`), the model key light and the spell glow; the older names `EnhancedLighting`, `SpellLights` and `SeamBlend` are still read and mapped to `Lighting` and `EdgeBlend` (`config.cpp`).
- **Shaders.** The `[Shaders]` character keys make one `render::CharacterShading` for the field actors', the battle units' (and weapons'), the status screen model's and the title's models' mesh draws (`FieldWorld::set_character_shading`, `BattleView::set_character_shading`, `StatusModelView::set_character_shading`, `TitleBackdrop::set_character_shading`, from `apply_frame_options`); every other mesh draw (the title's scenery, Grand Slam picker, effect models, shadows) stays unshaded. The normal is the skinned VDDM normal, or a rigid mesh's smoothed normal; the light `k` is the camera-relative key light of `Lighting`, except in battle, where every unit, weapon and effect actor takes the stage's sun (`game::key_light`, `BattleView::unit_shading`; the `Lighting` key light of unstyled units too), so the shading stays put as the camera moves and falls the way the cast shadows do; `d = n . k`, and the shaded colour is the PS1 colour `C` (texel x light multiplier) scaled per pixel:
  - realistic: `C (0.6 + 0.5 (d / 2 + 1/2)) + L 0.22 max(n . h, 0)^16`, `L` the light multiplier, `h` the unit halfway vector of `k` and the direction to the eye;
  - toon: `C mix(0.55, 1, smoothstep(-0.05, 0.2, d))`;
  - cel: `C (0.5 + 0.6 b)`, `b = (floor(4 t) + smoothstep(0.42, 0.58, fract(4 t))) / 4`, `t = d / 2 + 1/2`;
  - matcap: `1.6 C M`, `M` the matcap texel at the normal in the key light's frame (camera right, model up, toward the camera; the built-in looks are all lit by the key light) (`MeshPipeline::matcap_index`: the built-in `clay metal ink`, made at init, then the mods' own, `App::load_shader_looks`).
  A normal pointing away from the viewer is turned toward it first. `StyleStrength` `s` blends the styled colour with the unstyled one, `mix(C, S, s)`. `Rim` adds `0.4 L rim k (1 - f)^3` (`k` = `RimStrength`) (`f = n . v`, `rim` white, or with `SpellRim` the hue of the summed spell light, `BattleView::unit_shading`); `CastGlow` mixes in the casting element's colour, `mix(C, 1.5 C g, 0.35 a) + g a (0.12 + 0.5 (1 - f)^2)` (`BattleView::cast_glow_tick`).
  On a shaded draw the `Lighting` key-light term is not added; the spell lights and the scene ambient are. `Outlines` adds a pass before the opaque pass, its depth written one ordering slot (16 units of camera z) behind its own, so the model covers it inside its silhouette and a model drawn later behind it does not paint over the line: the opaque one-sided parts with the back-face test inverted and made per triangle (the PS1's whole-quad test would drop the quads straddling the silhouette), every corner moved along its projected normal by `MeshPipeline::kOutlinePx` PS1 pixels on screen times `OutlineWidth`, coloured `0.15 C`; parts without normals are not extruded. With `OutlineDepth` the width is also scaled by the model's size on screen (`MeshPipeline::outline_depth_scale`): the extent of its posed joints projected into PS1 pixels (the larger of width and height), full width from `kOutlineFullSize` (36) pixels up, in proportion below it, never under `kOutlineMinScale` (a quarter). Field characters span about 14 to 75 PS1 pixels of joints, battle units about 30 to 180, so only small or distant ones thin out. A battle weapon takes its unit's factor (`BattleView` draws it after the unit with the width already scaled). With every `[Shaders]` key off the mesh output is unchanged. The full-screen keys go to `render::ScreenPass` (`App::screen_look`): the whole frame before the ImGui overlay is drawn into its target, then through `screen.frag`: the filter (`crt` with its mask, curvature and glow; `composite`: YIQ with the chroma blurred over about three PS1 pixels, a dot crawl and a ghost), and the grade (built-in curves or a mod's LUT).
  **Ambient occlusion and depth of field** (`Ssao`, `DepthOfField`; `render::PostFx`, `BattleView::draw_post_fx`) work on the battle 3D picture between the units and the effect sprites, so the effects, HUD, menus and windows are never touched; they are off under `Ps1ResGraphics`. The picture's depth buffer holds ordering-table slots (a stage packet has one value over its whole area), which give no positions, so a view depth is drawn for them: `draw_scene_3d` calls `GpuContext::hold_depth` before the stage, and after the units `PostFx::begin` suspends the picture and begins a target at the output resolution (the picture's size, at most the window's: with a render scale the passes run at window size). The stage (opaque faces only: no seam strips, drop shadows or floor shadow) and the units, weapons and showcase models (opaque texels only) are drawn into it again with `set_view_depth`: the stage and mesh shaders then write the camera z per pixel, in 1/256 units as 24 bits of colour, with z / 65536 as the depth. At half that resolution:
  - SSAO: the view position is rebuilt from the view depth and the projection (`x = (ndc_x - cx) z / ax`), the normal from the neighbouring depths (on each axis the side with the smaller step, so silhouettes do not bend it); 12 samples spiral out to `PostFx::kAoRadius` (220 world units, projected to pixels) and are turned by a fixed per-pixel noise; a sample at offset `v` occludes `max(n . v / |v| - 0.2, 0) (1 - |v|^2 / R^2)`, and `ao = 1 - 3 sum / 12`; the far clear (sky) stays 1, and with `SsaoRange` `k` > 0 the occlusion fades to 1 (smoothstep) between camera z `k f` and `1.25 k f`, `f` the focus below, so the line where the floor meets a distant backdrop or sky dome does not darken. A 9-tap blur across, then down, weights the taps by depth similarity.
  - DoF: the blur amount of camera z is `c(z)`: with `d = (z - f) / f`, `smoothstep(0.25, 1.15, d)` behind the focus and `smoothstep(0.3, 0.75, -d)` in front of it (every bound times `DofFocusRange`), 1 for the sky. The picture is filtered down to its 2 x 2 view-depth texels' colours weighted by their `c`, with the largest `c` of the four (a texel on a silhouette holds only the blurred side's colour, so a sharp unit does not bleed into the blur around it), then gathered over a 32-tap disc of radius `c R`, `R` = 0.8 % of the output height times `DofStrength`, where a tap counts only as far as its own blur reaches, so a sharp unit does not smear into the blurred background. The focus `f` is the camera z of the unit in the picture whose depth is nearest the camera's look-at point's, eased 12 % of the way per game tick; while no unit is in the picture (an intro sweep, a close-up of the scenery) `R` and the mix ease to 0 at the same rate, and back when one returns.
  Both are upsampled to the output resolution with weights that drop texels more than 5 % of z away in depth (for the blurred picture, the farthest of a texel's 2 x 2 depths, the depth its colour comes from); a pixel's `c` is scaled by the share of the 5 x 5 pixels around it that are not a nearer surface with a smaller `c`, so the blur fades in over two pixels from a sharp unit's silhouette instead of switching per pixel along its stair-stepped edge; the picture's rendering then resumes with its colour and depth, and the result is drawn over it inside the battle scissor as `src + dst (1 - src.a)` with `src = (ao a B, 1 - ao (1 - a))`, `a = min(c(z) R, 1)` and `B` the blurred picture, so the picture becomes `ao (a B + (1 - a) C)`. With a render scale that result is made at the output resolution and drawn over the larger picture bilinearly. Effect sprites draw afterwards, depth-tested against the kept depth: they are neither occluded nor blurred, since they write no depth to blur them by. With both keys off nothing is allocated or drawn and the picture is unchanged.

## 7. UI

Menus draw on a fixed 1280x960 canvas fitted into the view. The same layout code serves both art modes; original art swaps textures and fonts (`ui/menu/ps1_art.*` decodes disc art). `ui::LowRes` renders a screen into a PS1-sized target when Ps1ResUi is on (always in disc mode). With `ui::ps1_menu_models()` off the main menu ends the pass before the Status screen's 3D model, draws the model at window resolution over the target's rectangle, and starts the pass again for the sprites above it. The target is cleared transparent and composited premultiplied; Subtract and Multiply quads (window bases) change only its colour and are drawn again into two more targets of the same size (subtracted amounts on black, factors on white) that are applied to the frame before the composite, so windows stay see-through as at window resolution. Text goes through `ui/ps1_font.*` and `render::TextBatch`.

**Element colour icons.** `core/element_icon.*` holds the six icons as polygons (ear-clipped once into triangles) and the `[Enhancements] ElementSymbols` flag every drawer reads (`element_symbols()`); `render/element_icon_draw.h` draws one through the sprite batch. The menu, the shops and the battle HUD each queue an icon op and expand it at draw time (`docs/rules/menus.md` section 18, `docs/rules/battle.md` section 12).

Screens: boot logo, title, name entry and slot list in `ui/title/`; the user guide in `ui/keymap_screen.*`; the main menu (Status, Elements, Equip, Key Items, Settings, Save, and the OpenCross row with its pages in `main_menu_opencross.cpp`) in `ui/menu/main_menu*.cpp` with one `Impl` in `main_menu_impl.h`; `ui::GameState` (`ui/menu/game_state.*`: party, roster, inventory, element grid, options word); the Status 3D model in `ui/menu/status_model.*` and the Bestiary page's creature in `ui/menu/enemy_model.*` (`oc_menu_model`, because `oc_ui` cannot depend on the mesh pipeline); the Elements page's spell in `game/battle/spell_preview.*` (`ui::SpellView`, a `BattleView` of its own, made with `init(..., hud = false)` so that it reads no battle scripts, HUD art, HUD fonts or enemy names, in preview mode: `BattleView::set_preview` before `start` runs the battle without its script, both sides invincible, the lead PC casting the element as soon as the view ticks and again a second after each cast has ended (`preview_recast` swaps the element of a battle that is not presenting a cast), and `draw_preview` draws only the effects, without the stage, units, shadows or HUD, into a render target of the box's size that is then laid over black in the box); shops in `ui/shop/`; party screens (`ui/party_screen.*`, rules in `game/party_editor.h`), pause (`pause_screen.*`: the PAUSE bar over the colour-ramped picture, with Vibration and World Names rows; the vibration option is stored in the game's options word and World Names in script variable 0x52) and key-item list (`keyitem_popup.*`); dialogue (`dialogue_box.*`, `typewriter.*`, `ps1_window.*`) and the dialogue log window (`dialogue_log_view.*`, over the field and as the OpenCross row's DialogueLog page); RDE's feature icons (`feature_icons.*`: the speed, No Encounters, Battle Boost, Auto Battle and AUTO SAVE marks) and world name (`world_name.*`). The battle HUD and results live in `src/game/battle/`.

**Game flow.** `game::GameFlow` (`game_flow.*`) binds `FlowMachine` (a pure state machine; `FlowState` is `Title, SlotSelect, NameEntry, Opening, Field`) to the title screens. Events (`on_title`, `on_name`, `on_slot`, `on_load`, `new_game_plus`, ...) return a `FlowAction` (load room, restore position, movie row, quit, stop music, open settings) that `App::apply_flow_action` obeys. New game and New Game+ transforms are pure functions in `new_game.*` and `new_game_plus.*`. The title scene is the field room `opening` (`kTitleRoom`) with `TitleBackdrop` drawing the 3D sea. Flow states: boot and Restart enter `Title`, which loads the title room with ROOM_PARAM 0 and runs it with no input while the title screen reads the buttons (`GameFlow::scene_mode`); New Game goes `NameEntry` -> `Opening` (the dream rooms `opn_*`) -> `Field`, Continue `SlotSelect` -> `Field`. During play the game ends by a jump to the title room with ROOM_PARAM 0 (after a game over or the credits): its INIT runs FE 2F, which resets the state to the boot state as the original does, and the field reports it (`FieldWorld::take_game_reset`); in `Field` or `Opening` the host then calls `GameFlow::return_to_title`, which enters `Title` over the room already running (no boot logo, no reload; the room plays its own logo FMV), so the title after a game is the boot title. FE 2F at the boot title itself changes nothing.

**Settings and debug overlay.** `render::ImGuiLayer` draws a tabbed window opened with Esc (or a long pad Start press). General (order 0; Game, Audio and Controls sections) and Graphics (10) are built in; others register with `add_tab(name, fn, order, highlight)` (`highlight`, when given and true, draws the tab label in green with a small red dot at its top-right): Mods (30, `imgui_mods_tab.*`), Cheats (40, `game::draw_cheats_tab`), Achievements (45, `game::draw_oc_achievements_tab`), Multiplayer (50, `imgui_multiplayer.*`, `App::init_multiplayer`), Update (80, `imgui_update_tab.*`), Debug (90, `App::init_debug_tab`). `options_window(config, file)` edits the `platform::Config` and returns an `OptionsChange`; `App::apply_options_change` applies it (VSync, MSAA, anisotropy, window, art, audio, BGM source, portraits, language). `toast(text, seconds)` shows a notice (1.8 s unless given). The open window pauses the field (ticks = 0) except on the Debug tab.

Keyboard and pad navigation (`render/imgui_nav.*`). Each tab's body is a child window flattened into the window's navigation (`ImGuiChildFlags_NavFlattened`, as are the Mods tab's list and detail panes), so Down from a tab lands on the body's first control and Up from the top control returns to the tab bar; no confirm press is needed to enter a pane. Content laid out side by side (the General and Graphics tabs' two columns, the panes of `ImGuiLayer::begin_panes` / `next_pane` / `end_panes`, the Mods tab's list and detail) is wrapped column by column in nav columns: while a move is scored, the other columns of the cursor's group are not navigable, so Up / Down walk the cursor's column and stop at its end, and Left / Right take the control level with the cursor in its own column (ImGui's scoring would otherwise prefer a control of the other column a few pixels off the row to the one beside the cursor). When the column has none that way, the move is carried on for up to three frames as a scan of the neighbouring column down from the cursor's top and up from its bottom, and the nearer control wins. When the window is too narrow for columns the sections stack and are not wrapped. The pad's LB / RB select the previous / next tab (wrapping) with the cursor on its first control. A bumper acts when it is let go and only if the other bumper was not down during its press (`render::BumperTap`), so the LB + RB chord of the guide overlay switches no tab; nor does a bumper press while a slider is held (LB / RB are its fine and coarse steps) or a list is open.

**Guide overlay** (`render/imgui_guide.*`, content in `net/guide.*`, browser in `platform/web_page.*`). With `[Guide] Enabled` the General tab's Quality of life table gets the Guide row (`ImGuiLayer::quality_rows`): a picker over the game's GameFAQs guide list, grouped by game and category, and a status line. The list and the guides come from the hidden browser: `net::guide_list_script` and `guide_page_script` run in the loaded page and answer in the JSON schema of `guide.h` (the list's entries; a page's header, page list and blocks: headings, paragraphs, list items with depth, preformatted text, table rows, rules). A text guide is one preformatted block; an HTML guide is walked in document order; a guide of several pages ("Page N of M", or the named pages of its table of contents) is read page after page and merged. Every page is read from the site once and then only from the cache: a guide when it is picked and the cache has none of the current format; the list when the row is drawn without a cached list (one try a session) and each time the Guide Overlay box is ticked. Nothing reads a cached guide again; raising `net::kGuideFormat` (the scripts' and the cache schema's version, written into every cache file) makes the next run read each list and guide it needs from the site once more. The cache is `%LOCALAPPDATA%\OpenCross\guides` (`platform::local_data_dir`; the exe's folder when `LOCALAPPDATA` is unset), never the OpenCross folder: `list.json`, `<guide id>.json` (the merged guide), `reading.json` (per guide, the block and line at the top of the view when it was last closed) and `browser\` (the WebView2 profile). `App::guide_hotkeys` toggles the overlay on `` ` `` or the pad's LB + RB together (`game::MenuChord`), and Esc closes it. While it is shown `App::simulate` runs nothing (render alpha 1, no field ticks) and `draw_frame` holds the battle view, the movie and the mixer as under the pause screen. The overlay draws over the dimmed frame, centred, 86% of the display height and 80% of its width but at most 1.3 times the height (an ultrawide display gets the reading width of a 16:9 one): the title, author, version line and a link to the page; a Contents list (pages, and headings down to two levels below the guide's top level); a search box that finds the next or previous line holding the text; and the body, laid out into one-line rows for the body width (word-wrapped UI text, preformatted lines unwrapped in Consolas, built by `ImGuiLayer::mono_font` on first use, with a horizontal scrollbar when they are wider) drawn through a list clipper. The pad (sticks, d-pad, shoulders) and the keyboard (arrows, PageUp / PageDown, Space, Home / End) scroll it from the frame's input; a paging button turns a page on the press and, held for a second, one every 0.08 s. The place read is written to `reading.json` when the overlay closes and when the game quits, and restored the next time that guide is shown, in this run or a later one. Without the WebView2 runtime (Proton) the pages are read in Steam's own browser instead (below); with neither the runtime nor a running Steam nothing is loaded and the row says so; cached guides still open.

## 8. Audio and movies

All in `src/audio/`; output is 48 kHz stereo float.

- `Mixer`: opens an SDL audio stream; `render()` is the device-independent core, also called by tests and tools. Buses: `Master, Bgm, Sfx, Ui, Movie, Voice` with atomic gains. One BGM channel driven by a thread-safe command queue (`play`, `play_akao_bgm`, `stop`, `fade`, `pause`, `resume`, `hold`). `hold(true)` freezes music, voice and movie under the pause screen.
- **Remastered music**: `HcaStream` decodes the HCA stream inside a `.sab` (`sab.*` parses the container; `clhca_unit.c` decodes) at the stream's own rate; `StreamResampler` converts a stream that is not at 48 kHz (a replacement track) in the mixer. `bgm_table.*` maps a song id to its file and loop points. `FieldWorld::start_song` reads the file through the VFS and calls `Mixer::play`.
- **Original music**: `AkaoPlayer` is a sequencer plus SPU model (24 voices with ADSR, 240 Hz update clock, Gaussian interpolation). `akao_seq.*`, `akao_bank.*` (instrument banks, SPU ADPCM in `adpcm.*`), `akao_tables.*` and `spu_reverb.*` support it. `Mixer::play_akao_bgm(song, volume)` starts a song. `bgm_switch.h` maps positions so `[Audio] BgmSource` can switch sources live.
- **Sound effects**: the `Sfx` interface (`sfx.h`) serves the field host (op `C6`) and the battle sequencer. `LogSfx` only logs; `AkaoSfx` plays original effects from `SfxBank` on the AKAO SFX channel pool. Field sounds carry channel masks so a room change or battle can evict them (`Mixer::evict_sfx`).
- **Voice**: `VoicePlayer` decodes MP3 lines on a worker thread (Windows Media Foundation) and feeds the voice bus; it searches enabled mod folders.
- **Mono**: the options word's Sound row (Stereo / Monaural) is pushed to `Mixer::set_mono` every frame; with it on, every SPU voice (original music and effects) takes the centre pan and the voice line is folded to L = R = (L + R) / 2; the remastered stream and the movie sound stay stereo, as in RDE (`formats/audio.md` 6.3).
- **Battle sound** (`game::BattleAudio`): sounds are named by tag and looked up in a list of sound groups, newest group first. A group is `Resident` (opened for the whole battle: `battle.prd`, the stage), `Actor` (the acting unit's file, one at a time, opened at its action's start and closed at its end) or `Pack` (a spell's effect pack, closed at the pack's end). Closing a group cuts the sounds it started: each group kind adds its own channel mask bit to the battle mask, and `stop_sounds` cuts all of them at the end of the battle. A play with a non-zero mask first ends the sounds carrying it, so the cast chant (mask 0x100) replaces the previous chant; `fade_chant` fades it out when the pack opens. The battle theme is ducked only around element casts (`duck_cast` at the cast start, `restore_cast` at the effect's end); while effect op 0x7B's flag is set (`BattleView::fx_bti_gate_`, until op 0x60 or the next battle) neither runs, so a pack's own music fade (op 0x54) stays (`formats/battle_effects.md`).
- Formats: `docs/formats/audio.md`; voice layouts: `docs/formats/mods.md`.

**Movies** (`src/movie/`). `movie::Decoder` wraps librempeg: Bink 2 (and HEVC / H.264 in mp4 or mkv for mod movies) to RGBA video and 48 kHz audio. `movie::Player` opens a `movie.dat` member by name, decodes on a worker thread, paces frames against the mixer's movie PCM clock, and exposes the frame as a texture. `App::start_movie` sets `movie_open` and the movie's sound level (the row's volume; the BGM keeps playing); `advance()` calls `movie_player.update(dt)` until `finished()`; `end_movie` keeps the last frame over the resumed field, held for 10 frames or faded out over 160 by the movie's flag 8 (`movies.md` section 6). `DiscIndex::movie_range` gives the frame range of excerpt rows. See `docs/formats/movies.md`.

## 9. Save

`src/save/`; format: `docs/formats/save.md`.

- `cc_save.*`: `SaveSlot` (the 0x2000-byte slot block) with `decode_block` / `encode_block` (exact inverse; unknown fields survive; element ids past 511 go through the slot's side file in the store `set_wide_store` names, `formats/save.md` section 16). `SaveDat` wraps `save.dat`, a ZIP of `memcard1.mcr`, `memcard2.mcr`, `rd_save.dat`, `achievement.dat`, `ext_save.dat` (`load`, `save` via temp file and rename, `create_empty`, `ensure_cards`, `card(n)`).
- `memcard.*`: the 128 KB PS1 card image. `encrypted_zip.*`, `crypto.*`: WinZip AE-2 AES-256 reader and writer with local AES, SHA-1, HMAC, PBKDF2.
- `ext_save.*`: per-slot language, battle counter, 44 custom names (`ExtHost` is the live source). `oc_saves.*`: the OpenCross page, an auto-save plus 100 files in an `OpenCross` folder next to `save.dat`. `collection.*`: the collection file in the same folder (`docs/formats/save.md` section 13.1), what the record pages read. `dialogue_log.*`: the dialogue log file in the same folder (section 13.2).
- `game::Autosave` decides when to write on a location change; `App::advance` writes card 1 slot 0 and/or the OpenCross page.
- The single source of truth in memory is `ui::GameState`. `FieldWorld::capture_state()` writes VM variables into it before a save; `restore_vars()` reads them back after a load. `game_session.*` converts it to `battle::PartyMember` and back. Save and load screens: `ui/menu/main_menu_save.cpp`, `ui/title/slot_list.cpp`.
- Memory cards: both cards are first-class. `SaveDat::ensure_cards` formats a card member that is missing or not 0x20000 bytes, and the load screens (`SlotList::collect(dat, card)`) and the Save menu choose between Slot 1 (`memcard1.mcr`), Slot 2 (`memcard2.mcr`) and the OpenCross page (card 0 in `SlotEntry`); card 1's slot 00 is the RDE auto-save.
- `init_saves` creates `save.dat` with two formatted cards on first boot and loads the OpenCross page from its folder (`OpenCross`, or `<name>_OpenCross` for another `[Paths] SaveFile`); `init_menus` makes a one-time `.ocbak` copy.

## 10. Platform, config, core

- `platform::Window`: SDL3 window, event pump, gamepad. `pump(Input&)` fills `platform::Input` (key and button down/pressed arrays, axes) and returns false on quit. `platform::stick_to_dpad` turns the left stick tilted past half way into the matching d-pad button (held, and pressed on its first frame); `App::advance` applies it to the input of every tick, so every screen, the field's direction bits and its choices take the stick with their own d-pad repeat. Field walking still reads the stick's angle as analog input. Window modes (windowed, borderless, exclusive), size and display (`apply_video`), swapchain resize signal (`take_resized`), rumble (`set_rumble`). The window is never user-resizable.
- **Rumble.** Each frame the App passes `Rumble::flush(vibration option, dt)` to `Window::set_rumble`. The flush adds the sequence players' motor values (small 0 or 1, big clamped to 255) and the test pulse, all zero when the options word's Vibration bit is off. `rumble_map` converts to the pad: the low-frequency motor is `(min(big, 255) * 0.0037255 + 0.05) * 65535` (0 when big is 0), the high-frequency motor is full when small is non-zero. Switching the option on in the pause screen starts a pulse of big 0xE0 that falls by 10 per 1/60 s. `set_rumble` sends zero when there is no pad or the window lacks input focus, and otherwise sends a changed state at once, a repeated non-zero state every 250 ms (each request lasts 400 ms), and nothing for a repeated zero.
- `platform::Config` (`config.*`): `opencross.ini` reader/writer (`class Ini`; comments are not preserved) and the typed `Config` struct; every key is listed in `docs/formats/config.md`. Sections found in `config.cpp`: `[Video]`, `[Game]`, `[Audio]`, `[Enhancements]`, `[Cheats]`, `[Mods]` (texture-dump categories and per-mod preferences), `[Paths]`, `[Ui]` (the settings window's position, size and last tab), `[Debug]`. `[Video]` includes `Driver`, `Msaa`, `Anisotropy`, `RenderScale`, `Ps1ResGraphics`, `Ps1ResUi`, `Ps1Jitter`, `FovDeg`, `WideHud` and `FrameCap`.
- **Steam** (`steam.*`, `game/achievements.*`). `App::update_achievements` connects when `[Game] Steam` (default off) turns on and disconnects when it turns off; runs with `--config` or `OC_QUIET` never connect, and they alone evaluate the rules without Steam. With the setting off nothing is earned. Steam keeps showing the game as playing after a disconnect until the process exits. It sets `SteamAppId` and `SteamGameId` to 1133760 in the process environment, requires a running client (`HKCU\Software\Valve\Steam\ActiveProcess`: non-zero `pid`, then `SteamClientDll64`), loads that DLL, and uses its exports `CreateInterface`, `Steam_BGetCallback`, `Steam_FreeLastCallback`. Through `SteamClient017` it creates a pipe and connects the global user, which is what makes Steam show the game as playing; `STEAMUSERSTATS_INTERFACE_VERSION012` gives the stats and `SteamFriends017` the user's persona name (`persona_name()`, multiplayer's default name; its absence leaves the name empty and changes nothing else). `SteamClient` talks to the stats through `platform::SteamBackend`; the running client is one implementation, tests supply another. No SDK header, library or DLL is involved: only the interface names and the slot numbers in `steam.cpp` are declared by hand. `pump()` runs every frame. Callback 1101 (stats received) makes unlocks possible; `unlock()` queues until then. An unlock reads the achievement first, sets it, then stores; after an unlock that leaves all 37 names achieved, the meta `ach_ps41_all` is set in the same store (`set_meta`); callback 1102 (stats stored) with a failure, or a failed store call, retries every 10 seconds, and failed stats requests likewise. Steam missing at any step leaves the client unconnected and every call a no-op. `App::update_achievements` runs at the top of `advance`: it feeds `game::Achievements` (room rules, the rules in `docs/rules/achievements.md`), passes earned names to Steam unless the debug tools were used, and, unless `[Game] HideAchievementNotices`, shows `Achievement unlocked - <title>` as a toast for each one Steam accepted, with the title in the Steam client's language. The events come from `FieldWorld` hooks (item given, variable bit set), `BattleView::take_cast_elements`, `ShopScreen::take_first_forged` and `finish_field_battle`. Without an overlay in a directly started exe, the toast is the player's only notice.
- **OpenCross achievements** (`game/oc_achievements.*`, the rows in `game/oc_achievement_table.inc`, the menu page's rows (`game::achievement_list`, plain `ui::AchievementList` rows the OpenCross row's Achievements page reads, `ui/menu/main_menu_achievements.cpp`) and the popup in `game/oc_achievements_ui.*`, `app/app_achievements.cpp`; rules in `docs/rules/oc_achievements.md`). `game::OcAchievements` holds no App, ImGui or file access: it takes room samples (`tick` says how many are due, one per 60 ticks outside battle; `sample` reads the room pair, the 44 recruited bits, the party's model bytes and Pip's while he is recruited, gold and script variables), `battle_actions` (the actions `BattleView::take_begun_actions` reports as the view begins to present them: party casts that run, steals that take an item, hits of 9,999 or more, an enemy element caught by a party trap; the field colours a party cast leaves are read from the next action's `ActionEvent::ring` or, at the end, from `Battle::ring`), `battle_ended` (scene, result, the scene record's boss flag, party members above 0 HP), `item_given` (op BB, the same `FieldWorld` hook as Steam's) and `forged` (`ShopScreen::take_forged_count`, every forge). The endings come from its own `game::EndingTracker`, the state machine `game::Achievements` also runs, so they count whatever `[Game] Steam` says. Profile text in and out is `parse_profile` / `serialize_profile` (the `Ini` rules; unknown ids and sections are kept). `App::update_oc_achievements` runs right after `update_achievements` at the top of `advance`: it always drains the battle's begun actions and the shop's forge count, and with `[Game] Achievements` on feeds them (not during a versus battle) and the samples (not on the title scene); with the debug tools used this session (`DebugTools::saving_disabled`) nothing is evaluated or recorded. Each unlock is logged and, unless `[Game] HideAchievementNotices`, queued for the popup (`game::OcAchievementPopup`: `Achievement unlocked` and the title in the top-right corner for 240 ticks, each panel taking every unlock waiting when it opens (up to three titles, then `and N more`), held while a movie plays or the settings window is open, drawn on ImGui's foreground list); every change rewrites `achievements.txt` beside the player's ini (temp file, then rename). A file that does not parse is renamed `achievements.bad.txt`. A `--config` run reads and writes no file.
- **Multiplayer** (`src/net/`, `render/imgui_multiplayer.*`, `app/app_multiplayer.cpp`; protocol in `docs/formats/multiplayer.md`). `oc_net` holds a small JSON value with its reader and writer (`json.*`), the `net::Transport` interface (connect, send, poll opened / message / closed, close) with the WinHTTP WebSocket implementation (`websocket_transport.cpp`: a worker thread connects, upgrades and sends; a receiver thread blocks in the receive call; `close()` aborts both by closing the handles), `net::MultiplayerClient` (the protocol state machine, below) and the records shared with the field (`presence.h`). The client takes its time only from the `now` passed to `update()`, so `test_multiplayer_client` drives it on a fake transport and clock. `App::multiplayer_frame` runs after `simulate()` every frame: with `[Multiplayer] Enabled` on, an address set and the run allowed (not `--config`, `OC_QUIET` or `[Debug] Script`), it makes the client on first use (and a `PlayerId` if there is none), starts it with the name (`Name`, else the Steam persona name, else `Player`) and `game::session_star`, gives it the local player and calls `update()`; then it hands the field the remote parties (without muted ones when `MuteHidesParty`) and the draw options (`FieldWorld::set_remote_parties`). The local player is `FieldWorld::local_presence()` with the room blanked on the title, during a movie or outside a loaded room, and the state raised to Battle during a field battle and to Menu under the main menu, a shop, the pause screen, the key-item list, the party and monster screens, a flow screen or the settings window. With multiplayer off the client is never made and the field is never called. `multiplayer_input` (before the hotkeys) opens the chat on `platform::kChatKey` (T; Enter is the first key set's Ok) and, while the chat is typed in, takes every key from the game (Esc closes it); while a settings text field has the keyboard, every key but Esc. `multiplayer_overlay` (inside the ImGui frame) draws the labels of `FieldWorld::remote_labels()` on ImGui's background list when the field shows them (not under a battle, a menu or a movie) and the chat panel (`render::MultiplayerUi`), then the player menu a click on a label or a chat name opens, the challenge popups (Y / N in `multiplayer_input` answer an incoming one) and the versus screen; `multiplayer_frame` takes the client's `pvp_start` (`App::begin_pvp`: this game's side, `encode_versus_side` of the party as it stands, goes out as `pvp_side` and is kept in `mp_own_side`) and shows the versus screen until the other side has come; then `App::start_pvp_battle` starts the versus battle (section 5.6) from both exchanged sides with a `game::NetworkVersusLink`. The client keeps a battle over a dropped connection and resumes it (`formats/multiplayer.md` section 8.4). The party card a challenge carries is `game::party_card` (`game_session.*`) on the loaded game's party, through the card source `init_multiplayer` gives the UI. Player text is drawn with `ImGuiLayer::chat_font()`: Segoe UI with Latin, Greek and Cyrillic, Meiryo / Yu Gothic / MS Gothic merged for ImGui's Japanese ranges, Segoe UI Symbol for arrows and symbols, rasterised at 24 px into the shared atlas the first time multiplayer is on (the atlas and its texture are rebuilt before that frame); a missing font is left out, and characters outside those ranges draw as `?`.
- **Web pages** (`web_page.*`). `WebPageReader` owns a worker thread with a single-threaded COM apartment and a message loop, one hidden top-level window and the WebView2 controller in it (muted, no dev tools, no script dialogs, new windows refused), with its profile in the folder `start()` names. `load(url, script)` queues a request and returns its id; the worker navigates, and after the page has loaded (an HTTP error status still counts as loaded; no answer at all fails at once) it evaluates the script every 250 ms until the value is not null. The string `"verify"` means the page wants the player: after 4 s of it the window is shown, centred on the work area, until the page answers or the player closes it (the request then fails). Timeouts: 30 s, 3 minutes while the window is shown. Each answer (`take_answers`) carries the value as JSON text or an error sentence; after it the browser goes to `about:blank`. `runtime_version()` names the installed WebView2 runtime (empty when there is none); `available()` is true when that runtime is installed or Steam is running. `GuideOverlay` ends the worker after a minute without requests.
- **Steam's browser** (`steam_browser.*`, the client library's slots and messages in `steam_abi.h`). When the WebView2 runtime is missing, or `OC_GUIDE_BROWSER=steam` asks for it, `WebPageReader` reads its pages in a `SteamBrowser` instead: a hidden page of the running Steam client's HTML surface, on the worker's own pipe to the client (the same app id as `SteamClient`, whatever `[Game] Steam` says, so Steam shows the game as playing while the reader runs). The worker pumps the pipe every 16 ms and runs the client's per-frame work for the process first (the utils interface's private frame call; without it the browser's creation never completes). Every navigation the page starts is allowed and its dialogs are dismissed (the surface does not deliver `alert`), so a script's value comes back through the page title, the one piece of page state the client reports: the wrapped expression keeps its JSON in a page variable named after a random token, escapes `%`, space and `\` as `%XX` (a title collapses spaces), and sets the title to `<token> <run> <part> <parts> <text>` with up to 3900 characters of text (the browser keeps 4096 of a title); each part received asks the page for the next, and after the last the page gets its own title back. About 50 ms a part: a 770 KB guide takes some 15 s the one time it is read. The surface has no window to show, so a `"verify"` page runs into the 30 s timeout with its own error sentence.
- `keymap.*`: RDE's two key sets per action (`platform::Action`; `action_down`, `action_pressed`). `paths.*`: `exe_dir`, `local_data_dir` (`%LOCALAPPDATA%\OpenCross`, for caches), `find_game_dir`, `find_save_dir`. `rumble.*`: the pad motor model. `updater.*`: self-update, below. `process_exit.*`: how the game process ends, section 2.1.
- **Quit and Restart** (General tab). Quit leaves the main loop. Restart is `App::restart_game`, at the top of the next `advance`: it stops the movie, battle, results, menus, shop and pause screen, stops the music, and `GameFlow::restart` clears the flow's overlays and enters the title with the boot logo, in the same process. The title then resets the field as at boot. The battle counter stays until a save is loaded, as it does for a new game.
- **Updater** (`updater.*`, `render/imgui_update_tab.*`). `Updater::check()` asks the GitHub API for the latest release of `sp-hy/OpenCross` (hard-coded in `updater.cpp`; drafts and pre-releases are never "latest") and compares its tag with `OC_VERSION_STRING`. `pick_asset` takes `opencross.exe`, else a `.zip` whose name starts with `opencross`, else a single `.exe` or `.zip`. `download()` fetches it into memory and applies: the asset size, its SHA-256 when GitHub lists a digest, `opencross.exe` at the root or one folder deep when it is a zip, a PE header check (`MZ` and `PE\0\0`), then writes `<exe>.new` and requires its version resource to be newer than the running build. The swap renames the running exe to `<exe>.old` and `<exe>.new` to `<exe>` (a running exe can be renamed, not overwritten; a failed second rename restores the first). The Update tab's "Restart now" ends the main loop and `platform::finish_exit()` starts the new exe with the same command line, keeping the old process until it exits (section 2.1). `init_config` calls `cleanup_after_update()` at the next boot: it deletes a stray `<exe>.new` and, on a detached thread that retries for about ten seconds, the `<exe>.old`; after a restart the old process is still waiting, so its `.old` goes at the following launch. All network work runs on one worker thread and the tab polls `status()`; `update_pending` (a newer exe found, downloading or installed, not `launcher_only`) highlights the tab label. `init_render` starts `check()` at every launch, except for `--config`, `OC_QUIET` and `[Debug] Script` runs; `run()` waits for it to finish and, when a newer exe is available, shows `Update: OpenCross <tag> is available (Esc > Update)` as a 4-second toast. A failed launch check only logs. The tab also links to the Nexus Mods page and its bug list. `pick_launcher_proxy` finds the asset `XINPUT9_1_0.dll` (`docs/formats/launcher.md`). When RDE's launcher is beside the exe and the proxy there is missing or differs from the asset's digest, `check()` includes it, and offers it alone (`Status::launcher_only`) when the exe is current; that is how an install from a bare `opencross.exe`, or from an updater older than the proxy, gets it. It uses the exe's rename swap, since a launcher running behind the game has it loaded. Once the exe is in place a proxy failure only logs, and the next check offers it again.

### 11.2 Deterministic routes

`tests/routes/` holds about 129 routes: `<name>.ini` plus `<name>.txt`. `tests/routes/run.ps1 <name>` starts `opencross.exe --config <ini>` with `OC_QUIET=1` (no focus, no sound), waits, prints the route lines of the log and returns the exit code. An optional `<name>.env` sets environment variables for one run. The ini sets `[Debug] Room`, `Seed`, `Script`, `ScriptSpeed`.

The script language is specified in `docs/formats/routes.md` (and in the header comment of `src/game/route_script.h`): lines of `<when> <command>` with input (`key`, `tap`, `pad`, `walk`, `skip`, `mash`, `choose`, `fight`), waits (`wait room|dialogue|battle|idle|flow|movie|menu|shop|text`), debug warps and writes (`load`, `set var`, `put`, `request`), screenshots and `assert` checks (room, variable, dialogue text, battle events and result, party, position). A failed check logs `route FAILED`, writes `route_failed.png` and sets exit code 1. A route is deterministic because `App::route_frame` feeds a synthetic `platform::Input` one tick at a time and the RNG is seeded. Examples: `alu_chair` (walk-mesh blocking), `art_swap` (live art switch), `battle_hud`. Battle routes are only as deterministic as the battle's seed: a battle started by a field `A3` / `C9` (or a route `request battle`) with `[Debug] Seed` set gets a seed derived from it (`make_field_battle_args` passes it through `OC_BATTLE_SEED`), and a standalone battle (`[Debug] Battle=<scene>`: `battle_chain`, `battle_dash`, `battle_dash2`, `battle_defend`, `battle_harness`, `battle_run`, `results_heal`, `smoke_battle`) takes `[Debug] Seed` itself (`App::init_battle`) unless the run's environment already sets `OC_BATTLE_SEED`. Which of the others still vary with timing cannot be told from the route files (unverified).

Other automation: `[Debug] Record` / `Replay` (`InputRecorder`, `InputReplayer`); `[Debug] SweepTicks` makes `sweep_frame` visit every room, run its scripts, auto-win battles, skip movies and menus, and log VM statistics.

### 12.2 How a room loads

Triggers: a map-jump op (`request_map_jump`, `begin_jump`, `step_transition` once dark), `App::apply_flow_action`, the Debug tab, a route `load`, the game-over path. All end in `FieldWorld::load_room(name, param)` (`field_world.cpp`):

1. `files_->set_hd_mode(hd_)`, `clear_room()` (waits for GPU idle).
2. `map_id_for(name)` and `discs_.record(...)` find the room's `.prd` (some rooms use another room's).
3. `view_.load(name)`: reads `cdrom/map/mapbin/<name>.bin` and `.ctd` through the VFS, `import::load_room` builds the `RoomScene`, HD rooms read the `.chip2` alongside, layers upload, walk mesh and camera are built. The CPU half (file reads, import, 1x and 4x composition, and the room's own models with their texture mods resolved and uploads prepared; with a GPU context also the 4x layer textures and the model textures, made with `Texture::create_blocking` on the worker: `RoomView::prepare`, `game/room_models.h`, `render::prepare_model_textures`) can run ahead on a worker: `begin_jump` starts it for the target room when the exit fade starts, and the host starts it for the saved room during the load fade-out (`FieldWorld::prefetch_room`). `load` takes that result when the room, `.prd`, art mode and VFS generation still match (else it waits for the worker, discards it and loads normally), so only the GPU uploads remain at the black screen; `FieldWorld::room_model` uploads a prepared model on first use (`take_prepared_models`), unless the texture mods changed since. During the load fade-out the host also loads the save's party field models on workers, textures included (`FieldWorld::prefetch_party_models`), and every `load_room` starts the same for the current party before it imports the room. A room loaded without a prefetch still builds its own models in parallel inside the load, not one by one as INIT asks for them. A room on the other disc, and 4x images above 512 MB, are not prepared ahead. An art-mode switch drops a running prefetch before the VFS changes. In a controlled run (`[Debug] Control`, `RoomView::set_keep_same_art`; play always loads a room the usual way) the room on show loaded again with the same art inputs (`import::room_art_key`: the `.ctd` and every `.bin` subfile but zones, script, walk triangles / vertices / attributes and dialogue; plus the `.prd`, the art mode and the VFS generation: an editor's reload after a script, walk mesh or zone edit, a restart, a room entered from itself) keeps its built art (`RoomView::reuse_art`: only the subfiles the key leaves out are read again, `import::reload_room_logic`; the scene's art half, the backgrounds, palettes, HD textures and effects stay; the files `same_art` read are reused), and the world keeps its room models, effect meshes and uploaded effect sheets (`RoomView::same_art`, `FieldWorld::clear_room(keep_art)`). The last BGM file read is kept (`FieldWorld::play_stream`), so a song started again is not read again.
4. `FieldScriptModule::parse(scene->script_bytes)` (the script as `import::load_room` left it, with RDE's per-room corrections applied: `import::apply_script_fixes`, `fieldscript.md` section 13); `sfx_->leave_room` and `set_room(yos0, yos1)` for the room's sound banks.
5. `room_id_`, `map_id_`, `defeated_enter_room()`, `ents_.resize(entity_count)`; the room variables `kRoomParam`, `kMapId`, 0x3C (can-save, cleared), 0x3A (entrance), 0x50 (world name, cleared), 0x34 (set to 1).
6. `sync_party()`, `build_effects()`.
7. `vm_.load(module, attr_flags)` with `in_init_ = true`: clears room-local variables and runs every entity's INIT. INIT calls `setup_pc`, `setup_npc`, `load_model`, `set_position_xz`, ... which bind actors and models.
8. Party members still unplaced take the entrance record (`place_party_spawn`) and the followers are written to the party V (`place_followers`); then `update_input_lock`, `snap_camera_to_player`, `pick_auto_target`.
9. `step_transition` sets the fade-in (black over 0x30 ticks, white over 0x20, by kind). The first `sim_tick()` runs the UPDATE scripts.

What a load resets: every entry runs `clear_room` first, whatever started it (a map jump, a Load from the main menu, Continue, New Game, the title scene's rooms, a debug or route warp, the game-over room), as the original's room init does on every field entry. Besides the room's entities, windows, effects, room sounds and camera it drops every request the room before left pending: the map jump and the movie-end jump, a running exit (the transition state goes back to none, so a load during an exit fade does not leave the new room in the exit state with the controls, the pause screen and every gated op held), the exit's frame capture, a script screen still requested or open (a Load picked from a save point's main menu enters the loaded room with no menu state, so the menu key, the pause screen and the next save point, shop or name entry work), the battle hand-off and the input lock; the entry fade then starts from black. A load keeps the game state (after a Load or Continue `restore_vars` has already copied the save's variables 0..0x3FF into the VM), the disc and the music. A room change checks that its target is a field room before anything is cleared and otherwise refuses the exit (`finish_jump_failed`, the room stays); if the target's files or script then fail to load, the room before is already gone, so the world stops ticking and reports it once (`take_room_lost`) and the App returns to the title.

### 12.3 How a battle starts and ends

Start:

1. A room script reaches `A3` or `C9` (`field_vm_ops_game.cpp`). The op waits for the system gate (`host_.system_ready()`, which a pending battle holds, so a second entity's `A3` waits for its own fight), asks `host_.skip_battle` (No Encounters cheat), then calls `host_.request_battle(id, field, flags)`, steps on and yields; the `FE 10` that follows every `A3` / `C9` yields while `host_.battle_active()`.
2. `FieldWorld::request_battle`: unless flag 1 keeps the field music, saves the song and position, stops the mixer and starts the battle song (`audio::battle_song`: the boss theme with flag 0x40, else the battle theme); ends the field's sounds (`fade_screen_sounds(true)`, then every sound but mask bit 0); sets `BattleState::Intro`; starts the `enct` sequence. The field keeps ticking under the swirl, without its positional sounds (`step_sound_emitters` idles until the battle has ended); `end_battle` starts the live C6 slot records' sounds again (`restart_sfx_records`).
3. `sim_tick` follows the encounter timeline (`kEncounterTearDown`, `kEncounterMain3E`, `kEncounterMainRamp`). When `enct` ends: `Hold`; after `kEncounterHoldTicks`: `Ready`.
4. Meanwhile `App::advance` sees `world.battle_requested()` and, from the fourth frame, calls `field_battle_load_step()`: `make_field_battle_args`, `BattleView::begin_load`, `load_step(3.0)`, `prepare_fx_targets`.
5. When `world.battle_ready()` and the view's load is complete, `start_field_battle()`: `world.take_battle()` (state `Running`, encounter effect torn down), `BattleView::start` (`finish_start` builds `battle::Battle` with a `ScriptedBrain` and calls `Battle::start`), `BattleView::begin_transition`; `battle_in_field = true`.

Play:

6. Each frame `advance()` calls `battle.update(dt, in)`. The view plays the intro camera and spawn scripts, then the command menu. A command goes through `execute` to `Battle::apply`, and the events replay in `tick()` / `tick_action()` (section 5.3).

End:

7. The rules set the outcome; `begin_finish` / `tick_finish` sets `finished()`.
8. `advance()` opens `BattleResults` (`results.open`) and updates it until `results.done()`.
9. `finish_field_battle()`: code from `battle.outcome()`; `game::apply_battle_result` writes rewards, growth and HP into the game state; the Dopplegang mask and the saved variables go back to the world; the results screen's healed HP is copied; `world.end_battle(code)`.
10. `FieldWorld::end_battle` writes `BATTLE_RESULT` (var 0x32), restores the saved song (where the encounter cut it: the remastered stream by position, the original music by the music push, `audio.md` section 2.5; with `[Audio] MusicResume` also a field song that the victory song of a battle keeping the field music cut off, section 2.8), or stops the battle's song when the field had none, and starts a 0x30-tick fade-in (8 ticks later after a results screen) (unless flag 0x20). `battle_active()` is now false, so the blocked script resumes and reads the result; the fade does not hold the system gate (`FieldWorld::system_ready`: only INIT, a room transition, a pending jump or a battle from its request to its end do), so its PLAY_SONG and the ops after it run under the fade-in, and another entity's waiting `A3` / `C9` requests its battle in the same tick. It also opens the room-entry window (`entry_window_`, 4 ticks) as a room load does, since the field restarts after a battle: nothing is culled, the models take their facing at once (`step_turn_rates`), and `3C` / `A9` wait on the first 3 ticks (`FieldWorld::entry_window`).
11. After a wipe in a fight that is not losable (with the Retry battle cheat on, once the choice's Give up is taken), `finish_field_battle` loads map id 9 (`room_stem_for_id(9)`); the title is the fallback if that load fails. That room's script shows GAME OVER and jumps to the title room with ROOM_PARAM 0, whose INIT resets the game (FE 2F); the flow then returns to its title (section 7, *Game flow*).

## 13. Deliberate differences from the original

- The General tab's Restart returns to the boot logo without leaving the process; RDE has no such control.
- Esc opens and closes the settings window on the press; RDE's Esc menu toggles on the key's release. The pad's Start held 500 ms also opens it, and a shorter Start tap opens the pause screen on its release; on RDE, Start goes straight to the game and the pause opens on the press. The LT + L3 chord behaves as RDE's.
- The achievement room rules sample every 60 real ticks in every speed mode. RDE's sampler counts down by a step that depends on the speed mode (4 times as fast in fast mode, half as fast in slow mode).
- A session that used the debug tools earns no achievements. RDE has no debug tools.
- OpenCross shows its own notice for each achievement, since a directly started exe has no Steam overlay.
- OpenCross keeps an achievement set of its own (`docs/rules/oc_achievements.md`), apart from the Steam ones; RDE has none. It only watches the game.
- The 8F screen ripple warps the whole picture; the original leaves the top 32 rows as the unwarped copy.
- Widescreen draws a room's art out to the real extent of its tiles, not to the camera block's pan limits.
- Sound effects keep running under the pause screen so its own sounds play; music, voice and movie audio are held.
- Start over a movie opens the pause screen; the original never pauses a movie, and RDE's Start skips a skippable one.
- The debug free camera bypasses the original's near-drop rules (the GPU's near-plane clip applies instead); a widescreen or wide-FOV picture also clips instead of dropping big stage packets.
- A follower's "too close to the leader" step that would leave the walk mesh or change floor is replaced by a probed slide step, or stands still when blocked; the original writes the position without a mesh test.
- Start-pause is allowed at any point of a battle, including the effects during which the PS1 and RDE refuse it (the Time Devourer ending, the Bunyip transformation, the final-boss stages, bgchng / miyademo and battle song changes).
- Title Continue is greyed (sfx 0x18) when there is no save; the original always opens the save screen.
- First launch starts windowed at 1280x720 with widescreen on, MSAA off and no FXAA; RDE starts in exclusive fullscreen at desktop size, 4:3, MSAA 8x and FXAA on.
- Every movie can be skipped, including every 7E and the D4 movies whose second operand lacks bit 0x200 (RDE plays those to the end). The pad triggers (L2 / R2) and stick clicks (L3 / R3) stay hotkeys and do not skip; in RDE every pad button skips (`movies.md` section 8).
- Movie sound follows the row volume on the movie bus only; RDE also applies the Music slider and a factor of 0.6.
- No key rebinding: the keyboard sets are fixed (RDE's Esc menu offers two rebindable keyboard sets). RDE's Brightness, Screen Type, FXAA and Help options and its Quit confirmation are not offered.
- The selected element plate of a white element glows from its frame 1 to its frame 2 and back, cross-faded, where RDE (and the PS1) step through frames 1, 2, 3, 2, of which 2 and 3 are both near white, so the original reads as a blink (`docs/rules/battle.md`, the element list). The other colours keep their cycle, cross-faded.
- Effect sprites (field, battle and title, every art mode) lose half a 5-bit colour level per channel, the average the PS1 GPU loses by rounding texel x colour down to 5 bits, taken off smoothly without the PS1's steps (`room_effects.md` section 4.3). RDE modulates at full precision with no loss, which is not a choice of its art but the absence of the PS1's rounding: the effects were tuned on the PS1, so its faint additive glows come out about twice as bright and pulse about twice as hard when one object ends and the next grows in (`jac_b05f`'s light patches). This departs from the rule that RDE is the reference where the PS1 and RDE differ; keep it as the default, and do not reintroduce the exact 5-bit rounding, which bands soft glows at modern resolutions (`jac_b08i`'s lamps). `[Enhancements] FullPrecisionEffects` (on by default in the player's ini, off in a `--config` ini) restores RDE's full-precision drawing (`render::ParticleBatch::set_full_precision`, set in `App::apply_frame_options`).
