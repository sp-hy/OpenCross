# Battle stage (battlefield) format

This document covers the battle stage files `battle/bg/bg_NN.prd` (and `kamei.prd`): their drp container, the pre-baked scenery meshes and the ground mesh, textures and the `.ctd` companions, camera tracks, sequence timelines, the emitter/object scripts that place and animate the scenery, the ground object, and the rendering rules (culling, packet rejection, ordering, blending, depth cue). All integers are little-endian. Validate and inspect with `tools/ocstage.cpp` (`ocstage info | objects | envpage | export | validate`) or `python -I tools/py/cc_stage.py validate`. Mesh packets share the format of the weapon mesh in model.md section 7.

## 1. Files

`battle/bg/bg_NN.prd` for NN = 00..99 plus `battle/bg/kamei.prd` = **101 drp files**. Seven stages also have a `.ctd` companion (bg_86..bg_90, bg_99, kamei) with raw VRAM uploads (4.2). Stage N is the battlefield index used by battle setup (battlefield 0 = Lizard Rock = file 2418).

The container is **drp** (model.md section 1, room.md section 2). Entries are not grouped or sorted by type and names are **not unique** (one stage has 9 entries called `far`, 6 `near`, 8 `bti0`, of different types). The entry type is the only reliable key.

## 3. Mesh (types 0x02 and 0x12)

Both types use one container: a static, unskinned mesh of pre-baked PS1 GPU packets.

```
0x00 u32 0x80000001
0x04 u16 nVerts, u16 nFaces
0x08 u32 vertexOffset      == entry size - 8*nVerts: the vertex array is the last thing in the entry
0x0C u32 faceOffset        == 0x14 + 4 + 8*nGroups: faces start right behind the group table
0x10 u32 groupHeaderOffset (always 0x14)
0x14 u32 nGroups;  nGroups x { u16 type, u16 count, u32 offset }     (offsets from the entry start; groups contiguous)
```
`nGroups` is 2..8. Groups are in ascending type order and tile the face area exactly.

**Vertex** (8 bytes): `s16 x, s16 y, s16 z, u16 pad`. **x is first**; the pad is always 0. Units are model units, +y is down (game "up" is negative y). The stage is authored in one shared world space with the arena centre at the origin: `ring` at y = 0 (radius 7240), `near` objects y -10240..1536, `far` up to y -21000 and |x|,|z| ~ 28000, `roof` (sky ceiling) y -31670..-20969. All parts therefore need **no per-part transform** to assemble.

**Face packets.** The group `type` is the GPU primitive code; the packet's own code byte is `type` or `type | 2` (semi-transparent). Bit 4 = per-vertex colours (Gouraud), bit 3 = quad, bit 2 = textured.

| type | primitive | faces (all stages) | bytes | layout |
|---|---|---|---|---|
| 0x34 | GT3 | 26,192 | 28 | 3 colours (`rgb code`, `rgb pad`, `rgb pad`), textured tri, 3 x u16 index |
| 0x3C | GT4 | 45,380 | 36 | 4 colours, textured quad, 4 x u16 |
| 0x24 | FT3 | 7,145 | 20 | 1 colour (`rgb code`), textured tri, 3 x u16 |
| 0x2C | FT4 | 15,903 | 24 | 1 colour, textured quad, 4 x u16 |
| 0x30 | G3 | 1,584 | 20 | 3 colours, 3 x u16 (no UVs) |
| 0x38 | G4 | 3,374 | 24 | 4 colours, 4 x u16 |
| 0x20 | F3 | 1,907 | 12 | 1 colour, 3 x u16, 2 pad bytes |
| 0x28 | F4 | 922 | 12 | 1 colour, 4 x u16 |

Textured block: tri `u0 v0 clutLo clutHi | u1 v1 tpLo tpHi | u2 v2` (10 B); quad adds `u3 v3` (12 B). `clut` / `tpage` are standard GPU words (4.3).
* Quads use **GPU Z-order**: triangles (0,1,2) and (2,1,3).
* **Textured triangle packets pair corner k with vertex idx[(k + 1) % 3]**: idx0 shares a word with uv2, and the draw routine loads (idx1, idx2) then idx0 into the projection while writing the packet's uv / colour words in packet order. The importer rotates the three indices so corner k and idx[k] line up; the cyclic orientation (NCLIP side) is unchanged. (bg_21's ring: its 128 rim triangles only fit the quads' planar tile mapping with this pairing.) **Untextured triangles (G3 0x30 / F3 0x20) keep the natural pairing**: indices in words 3-4; the title's `eff6` glow fan has its bright corner 1 on idx[1] = the centre vertex.
* **Faces are single-sided.** Each builder projects corners 0,1,2, computes NCLIP, and emits the packet only when `NCLIP > 0` (screen-space cross product, x right, y down). A quad's fourth corner is projected afterwards and never tested. Scenery walls therefore show their inside only; cameras placed outside the arena (most `zen0` eyes are 8-11 k from the origin, beyond the 7240 ring) look through the walls' backs. Extended objects (op 35) can reverse (ext bit 4) or disable (ext bit 5) the test; 116 / 1 stage objects do. OpenCross: the importer keeps the packet corner order (`StagePart::indices` = (0,1,2),(2,1,3)); `render::StagePipeline` culls the other side (a PS1 front face is a clockwise triangle under Vulkan's framebuffer area definition; verified on bg_21).
* **Colours** are PS1 modulation values: 0x80 = neutral (1.0), larger brightens up to ~2.0. They are per face corner (the same vertex index carries different colours in different faces), so a renderer must split vertices by (index, colour, uv). Colour k belongs to index k (untextured Gouraud triangles need no colour reordering).

Differences from the character mesh (model.md section 3): no skeleton, weights or VDDM block; indices are plain u16 into the vertex array (no back-references); Gouraud colours exist; each packet carries its own CLUT and tpage words instead of a shared page flag. No mesh in a stage is a mirrored copy of another (14 exact duplicate pairs, e.g. `far6/far7/far8` in bg_29, `nea7` twice in bg_00, one z-negated pair); up to 19 emitters in one stage name the same mesh (section 8).

### 3.1 Packet rejection by the GTE error flag and the GPU size limit
Every builder reads the GTE error `FLAG` after projecting corners 0-2 and after corner 3, and emits the packet only when **bit 31 (error summary) is clear in both**. Bit 31 is the OR of FLAG bits 30..23 and 18..13, so a packet is **dropped whole** (not clipped) when any corner has: camera x or y beyond +-32767 (bits 24 / 23; the z saturation bit 22 is not in the summary), camera z < 0 or > 65535 (bit 18), `z * 2 <= H` (division overflow, bit 17: the divide only runs when `H < SZ3 * 2`), or a screen coordinate outside -1024..1023 (bits 14 / 13; the offset OFX / OFY is added before that test). The packet is also dropped when all corners have negative x or all negative y. The GPU then skips any single triangle whose vertices are more than 1023 apart horizontally or 511 apart vertically (a quad is two triangles, each tested; documented GPU behaviour). Big floor or wall polygons that cross the near plane or reach far outside the 320 x 224 frame vanish instead of being clipped, which is why stage data is cut into small packets.

OpenCross: `render::StagePipeline::set_gte(h, ox, oy)` enables the same tests per packet on the CPU (`packet_passes`; surviving triangles are drawn through the dynamic index ring). `StageScene::draw` turns it on for battle stages; the title scene does not. The all-negative-x/y early-out is a pure screen-side test and is not emulated.
* **Widescreen frame.** The limits above belong to the PS1's 320 x 224 picture; ours is `320 + 2 e` columns (`render::wide_extra()`). `render::cull_frame(e)` scales the x limits and the x span about the projection centre 160 by `k = 1 + e / 160`; y is unchanged. `[Video] FovDeg` needs no factor (it scales H, so the picture's and the limit's tangents shrink together). `H >= 2 * SZ3` and `SZ3 < 0` use the real H / z. e = 0 gives exactly the PS1 constants (`test_stage` `test_cull_frame`). Also used by `EmitterSystem::draw` for effect quads.
* **Wide picture.** The scaled frame does not cover the near-drop rules (a big floor/wall packet with a corner behind the camera, or whose IR / SX saturates far off to the side, is dropped whole and would show at the edges of a wider or higher-FOV picture). Whenever the picture is wider than the PS1's (`render::wide_picture()`: wide columns > 0 or FovDeg > 35) `StagePipeline::set_gte` turns packet rejection off and the GPU's near-plane clip draws them; at 4:3 / FovDeg 35 the PS1 rules stay exact. Effect quads (`EmitterSystem::draw`) keep the widened PS1 rules. Unit models (`MeshPipeline`) have only back-face culling.
* **Free camera.** With the Debug free camera on (`render::cull_bypass()`, `FreeCam::set_on`) none of these rules run: `set_gte` leaves `gte_` off, every packet is drawn whole and the Vulkan clip volume does the work (projection w = camera z, clip z = 0.5 z, so the near plane is camera z = 0). Effect quads are dropped only when all four corners are nearer than z = 16, otherwise a corner behind the plane is slid along a quad edge to z = 16 and the SX / SY clamp and span rule are skipped. The ground-cell rule (8.5) is not a GTE-flag rule and stays.
* Debug: `OC_STAGE_NOREJECT=1` draws everything the GPU would clip; `OC_STAGE_REJECT_LOG=1` logs the dropped-packet count per frame (bg_21 zen0: 512 of ~3,000, none visible).

## 4. Textures

### 4.1 TIM entries (type 0x04)
Standard PS1 TIM. Flag 9 = 8bpp + CLUT block (`256 x 1` entries at `(0, 224+k)`; 2,215 TIMs), flag 8 = 4bpp + 16-entry CLUT (12 TIMs). The image rectangle is the TIM's **VRAM placement**: rows 256..511 and x 0..383 halfwords (= 768 px at 8bpp) in 94 stages, x 448..767 in bg_56/57/58 (their CLUT x = 256), x 0..319 in one. Typical image sizes (halfwords x rows): 64x256, 64x128, 32x64, 20x40 (lens). A stage ships 11..32 TIMs that together tile the area: the **768x256 stitched texture** (3 x 256-px pages across). Animated-looking textures (water, smoke, clouds, walls) are extra TIMs named like `jime`..`jim7`, `kab1`..`ka12`, `nami`, `wave` placed in neighbouring slots with a shared CLUT row; they are not animated by uploads, simply referenced by different faces.

### 4.2 `.ctd` companion (7 stages)
Sector-structured (2048 B). Header sector: `u32 type` (0x1201 = CLUT rows, 0x1200 = image), `u16 n1,n2,n3,n4` (**VRAM x = n1+n3, y = n2+n4**), `u16 halfwordsPerRow`, 3 x u16 (`rowsInFirstSector`, 1, ...), `u32 sectionCount` (whole file), `u32 dataSectors`, `u16 rowsInSector[dataSectors]`, then the data sectors (rows never straddle a sector). bg_86: CLUT rows (0,224) x 6 and (0,239); images (0,384) 384x128, (0,256) 320x128, (320,256) 48x32, (320,288) 16x32. These stages have **no 0x04 entries**; the CLUT rows the packets name live in the ctd.

### 4.3 Packet words to texels
* `tpage`: x base = `(t & 15) * 64` halfwords, y base = `((t >> 4) & 1) * 256`, bits 5-6 blend (abr), bits 7-8 colour mode (0 = 4bpp, 1 = 8bpp), bit 11 = y + 512 (never set). Use the 4-bit x form (a `(tpage<<6)&0x7c0` form leaks the y bit into x). All textured faces here have y base 256 and mode 0 or 1.
* Colour mode 2 (15-bit direct colour, effect-pack meshes): the texel is the VRAM halfword itself, no CLUT. The importer keeps the page origin of such faces per sub-mesh (`StageSubMesh::direct_page`, runs split by page), because the page can hold a copy of the screen instead of pack image data (`battle_effects.md`, miki).
* `clut`: x = `(c & 0x3F) * 16`, y = `c >> 6`. CLUT x is 0 (256 in bg_56..58), y 224..239.
* Texel: `px = tpageX * (2 at 8bpp, 4 at 4bpp) + u`, `py = 256 + v`. A face's UVs may continue into the neighbouring TIM, so the converter decodes one atlas per (mode, CLUT row) from the stage's whole VRAM image (768x256 for most stages; origin/width in `stage.json`). Index 0 / colour 0x0000 is transparent.
* **VRAM is exactly the file.** The stage's TIMs are uploaded as they are and the packets' clut / tpage words are used unchanged (only the abr bits are replaced for a semi-transparent object). No stage script of bg_00 re-uploads or animates a TIM (its 32 TIMs tile VRAM without overlap). Faces may therefore name a CLUT row that is not the one of the TIM whose rect they sample (bg_00 `nea3`, the coral rock: `nami` pixels through the coral CLUT 229; `nea4`: `gak3` pixels through 229; `nea5` / `nea6`: `sang` pixels through the greyscale CLUT 230). That is the authored look, not a decoding error.
* **Semi-transparency and colour come from the drawing object** (section 8). The packet's colour word is OR-ed with code bit 1 when the object's blend mode (op 06 bits 0-2) is non-zero, and then the tpage word's abr bits (5-6) are **replaced** by `(blend - 1) & 3`; the extended-object builders (op 35) take the same abr (`p = blend - 1`, tpage finished with `(tpage & 0xFF9F) | (p * 0x20)`), so blend 2 = B + F and blend 4 = B + F/4. An opaque object (blend 0) leaves the packets as they are, so a packet whose own code byte carries bit 1 is still semi-transparent with its own tpage abr. Every corner colour is multiplied by the object colour (`rgb * obj / 128`, 0x80 = neutral), textured and untextured alike. Stage CLUTs set STP on 559,020 of 565,977 non-zero entries, so a semi-transparent object blends every non-zero texel. Blend modes over the 1,788 mesh objects: 0 x1414, 1 (B/2+F/2) x62, 2 (B+F) x243, 3 (B-F) x23, 4 (B+F/4) x41, 6 x5. OpenCross draws blends 5-7 (add and subtract passes on the PS1) as the add pass, B + F.
* **Sampling.** RDE samples every PS1 texture page with a linear sampler in HD art mode (nearest only for chip2 layers in original mode). No HD replacement exists for stage textures (`hd.dat` and `cdrom2.dat` have no `battle/bg` entries). OpenCross: `render::StagePipeline` samples bilinearly in HD mode and nearest in original mode; the atlases get their transparent texels bled with the mean of their opaque neighbours first (`render::bleed_transparent`), otherwise the filter darkens every cut-out edge (palm fronds, coral strands). The importer addresses texel centres (u + 0.5, v + 0.5), because RDE nudges every polygon u, v by half a texel before its bilinear sampler. A textured packet whose tpage lies outside rows 256..511 (the room effect meshes on the effect page) gets its own 64-halfword one-page atlas instead of the stage atlas. The texture page at halfword x 320, y 256 (8bpp, packet tpage `0x95`) read through CLUT row (0, 239) is also kept as a 256 x 256 RGBA environment page (`ocstage envpage`): the env-mapped parts of battle models sample it, and it is blank when the stage image does not reach it. Mods can replace the stage's textures tile by tile (`mods.md` 6.2: `render::bake_object_textures` cuts the atlases into a tile library and one packed texture per object; the importer's vertex UVs address the atlases, the bake remaps them).

## 5. Lens flare (type 0x15, `lenz`)
Same container as the room "timinfo" (room.md section 6): `u16 0; u16 tableCount (bit 15 = not relocated yet); u16 b4; u16 b6; u16 0; u16 clutRow; u16 off[tableCount]` (7-8 tables). Each table at `off`: `u16 n; u16 0;` then `n x 12` bytes `{s16 x, y, u8 u, v, u16 clut, u8 w, h, 0x95, kind}`. Tables hold 4 + five x 1 + 4 sprites (core, halo, streaks); the pixels come from the stage's `lenz` TIM (8bpp, 60x88 halfwords at x 324, y 260; entry tpage `0x0295` = x 320, y 256, 8bpp). Field names are inferred.

## 6. Camera (type 0x0C)
```
+0  u32 flags       bit 0: compute the shot's anchor frame from `ref` at select time; bits 1-3 select mode (0 cut, 1 queue behind the running shot, 2 dropped while any shot runs); bit 5 model scale; 0 in all 1,029 stage shots
+4  u16 duration    ticks of the shot: progress += 4096/duration per tick, the keys are interpolated over 0..4095
+6  u16 mode        easing of the progress: 0 linear (712 shots), 1 sine ease-out (267), 2 cosine ease-in (47); 3 sine half-steps, 4 cosine S-curve (unused in stages)
+8  u32 w8          low half: the track whose path length times the keys (0 eye, 1 target, 2 projection + roll); 0x01000000 (971), 0x01000001 (44), 0x01000002 (12), 0x00FF0000 (2); the high half is not used by the engine
+12 u8[4] ref       anchors `{type0, attach0, type1, attach1}` of the shot's frame; 0,0,0,0 in 1,027; (7,0,0,0) and (2,18,0,0) once
+16 u32 count       keyframes, 1..10 (2 in 783 shots)
+20 count x 20 B:  u32 0, s16 eye[x,y,z], s16 h, s16 target[x,y,z], s16 roll
```
Size is exactly `20 + 20*count` in all 1,029 shots. Eye/target use the stage world space of section 3 (y negative = up). `h` (352..518, 512/511 typical) is the GTE projection distance H; `roll` rotates about the view axis, `roll << 2` in 4096 = 360 degrees (0 in 1,800 of 1,937 keys). **Evaluation** (`BattleCamera`): with 2 keys the path is a straight line; with 3 or more the eye, target and (H, roll) tracks are each smoothed by a uniform cubic B-spline (windows of four keys, 8 points each, the last key appended; 3 and 4 keys are padded with the last key to 5), so the path approximates the inner keys. Every point of a track is stamped with its cumulative chord length scaled to 0..4096, the `w8` master track lends its stamps to the other two, and the pose is the linear interpolation at the eased progress (capped at 4095/4096). `roll` is in 1/1024 turns. The shot is placed in its frame: the local eye and target are scaled in x / z by the two-anchor distance (distance / (2048 cos pitch)), by the model scale with flag bit 5, rotated by the frame's yaw and pitch and translated to the frame origin. A frame comes from `ref`: one anchor is that reference point's frame (a unit's ground point, top, half height, ground y = 0 or a model attach point, with the unit's yaw); two anchors give their midpoint with local +x pointing from the first to the second; types also name the acting list, the target list and bounding-box centroids of groups. The camera data of battle models and packs uses the same record with flags and `ref` set; stage shots are all in world space.

Names: `zen0` is the default whole-battlefield shot (94 stages; battle.prg looks it up by the u32 `'zen0'`; a typical eye is 8-11 k from the origin looking at the centre); `i01..i22`, `o01..o03`, `p01..p03` are intro/outro/party shots; later stages add `cai*`, `cao*`, `cap*` and digit names.

### 6.1 Where PCs and enemies stand
Not in the stage drp: the 0x0C records are camera tracks only. Combatant slots come from the scene record (`scenedat` bytes 6..14 positions, 0x11..0x19 facing); the stage supplies the floor (`ring`, centre at the origin) and the cameras aimed at it. Unit x/z share the stage's x/z axes.

### 6.2 The command-menu camera
While the command menu is enabled the menu camera runs once per frame in which no camera task and no timeline is alive; a running shot keeps the picture. Its mode: the top menu and the time between actions orbit the menu's PC (eye 2400 from the PC at its height + 0x100, target at 2/3 of its height, H 0x200, the angle advancing 2 per tick from the PC's yaw byte); NORMAL target selection, and any whole-range one, glides once to `zen0`'s first key at 0x40 / 256 per frame; DYNAMIC target selection glides at 0x14 / 256 to the cursor shot whenever the cursor unit changes; a queued action (attack, element, enemy action) leaves the pose alone until the last queued action has ended.

The command-menu steps end every camera task and timeline (and the screen warp), so the menu camera takes over at once instead of waiting for a shot:

* A top-menu command is confirmed (Attack or Element when it opens, Defend, Run). The camera pass of that frame still runs in the top-menu mode and writes the orbit, so the target glide starts from the orbit pose, not from the shot that was running.
* The element list opens (and selects `elm0`), opens its target ring (the glide starts from `elm0`'s pose; `elm0` lasts about 160 ticks), or is left.
* The menu passes to a PC: L1 / R1, after Defend, at the end of an attack turn. The menu's PC changes when the menu passes, not when it reopens: after Defend the defending PC's guard pose plays while the orbit already circles the next PC, whose top menu takes over only after its window has opened (the menu entry, `rules/battle.md` 3.4). Confirming an element's target ends nothing: a `zen0` glide still under way runs on until the charge shot cuts in.
* An engaged attacker goes home. After a cancelled HIT% box the hop runs under a new approach shot (`apr0` / `apr1`, `apr2` / `apr3` in DYNAMIC), which the reopened menu keeps until it ends; when the stamina is spent (or the turn ends any other way) no shot follows, the camera holds through the hop and then orbits the next PC.
* A queued melee attack (an enemy's): before its approach shot, when the attacker arrives (before the hit's own shots) and before its way home.
* Run: no shot of its own. The confirm ends the running shot, the party turns and runs with the camera holding, and the battle loop ends the frame after the confirm (pilfered loot dropped: after the 80-frame hold of `rules/battle.md` 2.7). The battle-end teardown that every ending shares (victory, wipe, Run) then runs 14 + 14 game frames and starts the stage outro `bto0`, whose first shot is the escape camera (bg_00: `o02` or `o03` at random): RDE 31 vsyncs after the confirm (the battle refresh counter, which the first 14 teardown frames still advance, stops 17 after it), the PS1 29 game frames: the battle loop's last frame is the one after the confirm, the shot 28 frames later (59 vsyncs at the PS1's two-vsync battle frame). OpenCross: `Act::Phase::Run` lasts `kRunTicks` (1), the outcome follows, `tick_finish` starts `bto0` `kOutroDelay` (28) ticks later; route `battle_run_camera`.

PS1 measurements (bg00, three PCs): Defend, orbit on the next PC 3 game frames later; Attack confirmed 14 frames into the return shot, the shot ends that frame and the `zen0` glide starts the next; the element ring opened 35 frames into `elm0`, the glide starts from `elm0`'s pose; the stamina spent by a fierce hit, the hit's shot ends at the hop and the orbit is on the next PC 13 frames later. OpenCross: `BattleView::menu_camera`, `end_camera_tasks`, `top_command_camera`, `begin_disengage`; route `battle_camera` checks the hand-over.

## 7. Sequence scripts (type 0x10)
Payload = 0x14 zero bytes, then a command stream. A command is `u32 w = op | len << 9 | jump << 15` (`op = w & 0x1FF`, `len` = bytes incl. the word, bit 15 = pointer variant). The stream ends with `0x21` (`21 10 00 00 00 00 00 00`), sometimes followed by one duplicate terminator.

Ops (counts over the archive): 0x20 start (347), 0x21 end (347), **0x23 select camera by name** (891; name at +0xC, tick at +4), 0x2B / 0x2C screen fade in / out (521 / 4; `s16 frames@+4`, `u8 mode@+8`, `rgb@+9..11`), **0x4C play AKAO sfx by name** (260; name@+0xC, `s16@+0x10`, `s16@+0x12`, `u32@+0x14`), 0x22 run emitter by name (6), 0x3E/0x3F/0x40 **screen afterimage on/off/ramp** (78/74/74, 7.1), **0x73 hold the intro** (33), 0x25, 0x27, 0x31, 0x35 (1 each). Names resolve to camera / emitter / AKAO entries of the same drp (`pli0` -> `p01`,`p02`; `bto0` -> `o02`,`o03`; `bti0` -> `i0x`, `se3x`). Tick values of the individual commands are not otherwise decoded.

**Timing.** The high half of the command word is the wait taken AFTER the command, so a command's tick is the sum of the delays before it. Consecutive 0x23 commands (with the other commands between them) up to the first non-zero delay form one group, of which `BattleCamera` selects one pick at random. The engine also runs 0x2F (start another timeline of the bank by name; stage sequences do not use it) and, in the sequences of battle models and packs, 0x4D (loop back for the next target), 0x50 (stall while the actor is busy) and 0x67 (yield); a stall or yield waits exactly one tick whatever its delay.

**Ops 0x2B / 0x2C** drive two screen colour layers (0 and 1): the colour is ramped from the layer's current colour over `frames`; colour 0 draws nothing; mode 0 opaque, 1..4 = ABR mode - 1, so **mode 3 (ABR 2, B - F) with white is a fade to black**, not to white. Every `bto0` ends so (0x2B mode 3 rgb 0 at 0, rgb 255 over 70 / 71 frames after the 170-tick shot group); scene 409's also has a 0x2C mode 0 rgb 0 (layer 1 clear) in the first group. Examples from a capture of bg_40 `boss`: `2B f1 m2 (137, 189, 255)` is an additive flash (frame minimum (126, 173, 230), back over 10 ticks); `f50 m2 (255, 157, 183)` ramps up to exactly that minimum and `pli0`'s `2B f30 m2 0` takes it down over 30 ticks; `f20 m3 (156, 48, 42)` subtracts (red 130 -> 13). OpenCross: the stage timelines feed the same two screen colour layers as the effect packs (`BattleCamera` screen hook -> `BattleView::fx_screen_colour`, drawn by `fx_draw_screen` also with no pack running).

**Who clears a layer the intro leaves on.** Once per battle, when the first command menu opens (no camera task and no timeline alive), both layers ramp to 0 over 10 ticks (mode kept). ### 7.1 Fog flag and afterimage ops
* **0x24 = fog flag on**; **0x6C = fog flag off**. The flag also makes every unit's draw callback use the lit/depth-cued variant, and is cleared by pack and room teardown. **No stage sequence (type 0x10 of `battle/bg`) contains 0x24 or 0x6C** (scan of all 347: ops 20 21 22 23 25 27 2B 2C 31 35 3E 3F 40 4C 73 only); they occur in the effect packs (0x24 in 373 sequences of `battle/effects`, 0x6C in 9; 323 of the 327 packs that ramp the depth cue with op 0x2D also contain 0x24). So stage objects are never depth-cued during the intro shots; they are only while an element / tech pack runs (8.2).
* **0x3E / 0x40 / 0x3F = frame afterimage** (a full-screen feedback pass, not fog): 0x3E turns it on and zeroes the state (colour 0x808080, rotation / translation / zoom words, offset, abr); 0x40 starts the ramp task (frames s16 +4, target colour / rotation / translation / offset words from the command, abr byte +0x1B); 0x3F clears the flag. While on, the frame loop re-draws the displayed frame as 80-pixel-wide strips of semi-transparent textured quads through a GTE rotation / translation / zoom: a motion-blur / radial-echo of the previous picture. 78 stage sequences use it (the intro `bti0/1/2` shots). OpenCross: `BattleCamera` warp hook -> `BattleView::fx_warp_op` (the effect packs' screen copy warp, battle_effects.md).

## 8. Emitter / object scripts (type 0x0A)
Header as in room_effects.md section 3 (0x18 bytes, then bytecode); stage entries are 172..208 bytes. An op is a `u16 word = op | len << 9` (`op = word & 0x1FF`, `len` = bytes including the word, at most 0x3F) starting at +0x18. The importer keeps, per script: OT_BIAS 0x03 (s16 at +2), SPRITE 0x05 (4-character name at +8, s16 type at +12), FLAGS 0x06 (u32 at +4), POS 0x08 / VEL 0x0A / ANGLE 0x19 / COLOR 0x20 / SCALE 0x12 (three 16-bit values at +2, +4, +6), LIFE 0x0F (u16 at +2), EXT 0x35 (u32 at +4: bit 0 UV scroll, bit 4 reversed cull, bit 5 no cull) and the UV window 0x36 (u8 off_u at +2, u8 off_v at +4, s16 win_w at +6, s16 win_h at +8; the rates at +10 and +12 are run by the emitter engine). `ocstage objects <bg_NN>` prints them. The mesh an object draws is its SPRITE name when it matches a mesh entry, else the first alphanumeric token behind +0x18 that does. Each names, as a 4-character token at a varying offset (+0x64..+0xA0), the **mesh it draws** (found by token search for 1,832 of 2,255 entries; e.g. `far` -> `far1`/`nea5`, `ring` -> `ring`, `roof` -> `roof`, `near` -> `smok`/`nea3`, `bti0` -> `tori`). Roles by entry name: `far` = distant backdrop (largest radius), `near` = nearer scenery, `roof` = overhead dome, `ring` = ground, `sun`/`kumo`/`ki-l`/`ki-s`/`wave` = effects. Up to 19 emitters in one stage name the same mesh with different scale/offset words (4.12 fixed point, `00 10 00 10 00 10` = 1.0).

**The stage is drawn by the generic object engine, nothing else.** A type 0x0A script is the room_effects.md section 3 emitter; its objects' SPRITE op names the mesh with **type 14** (drp type 0x02) or **type 19** (the drp type 0x12 `ring`, 95 objects). The draw callback sets the mesh's OT bias, colour, semi flag and abr from the object, then walks the group table and calls the eight packet builders (section 3). So every rule of room_effects.md sections 3-4 applies: `0x08` POS, `0x19` ANGLE (4096 = turn, Rz*Ry*Rx), `0x12` SCALE (4.12), `0x20` COLOUR (12-bit, draw colour = `>> 4`), `0x06` FLAGS, `0x03` OT_BIAS, `0x0F` LIFE (0 = persistent: one instance that the emitter respawns in place), `0x0A` VEL, and the extended ops `0x35`-`0x37` (UV-window scroll, mesh morph). Static scenery = objects with LIFE 0 and no velocity (1,883 of 2,255 stage objects); the rest are particles (`bti0` bugs with VEL + morph wings, `smok` / `kona` sheets of `effect/particle.prd`, `lenz` flares, `sun0`).

Facts over the 2,255 stage emitters: flag bit 26 (**premul-camera**: matrix = camera x object, a world-oriented mesh) in 1,851; the 103 mesh objects without it (`maru` discs, bg_09 `far3/4`, bg_28 `nea2`, bg_29 `far2/6`) rotate with the object matrix only, in view space (billboards); bit 17 depth-cue in 2,176 (only active while the fog flag is set, 7.1); bit 28 screen test in 1,267 (8.4); bit 24 camera-relative in 13 (particles); bit 23 fixed slot never. All `far` / `near` / `ring` emitters: `start 0, duration 0, period 10` (fires `period + 1` ticks after registration; the stage is loaded behind the white transition).

**Mesh lookup is by sprite type, then name.** bg_34 / bg_90 have a scenery mesh `bg34` (type 0x02, the marsh bank) and the ground `bg34` (type 0x12); the `ring` object names `bg34` with type 19, so it must resolve to the type 0x12 entry (resolving by name alone drew the bank twice and no floor). Among the 14 duplicate type 0x02 names the first entry is used. **A zero name word matches any entry of the type** (first hit from the registry head): bg_72's `ring` object has op 05 = `05 20 01 00 | 00000000 | 00000000 | 13000000` (no name, type 19) while its ground entry is `bg52`; the PS1 still draws the stage's only type-0x13 ground. It is the only stage object in the 101 files with an empty mesh name.

**OT bias is the stage's depth ordering.** Slot = `(avg z >> 4) + bias` (ZSF4 = 0x100, z-shift 2), so a bias of N pushes the object N * 16 world units back in the sort (bias range -693..7999, non-zero in 1,104 mesh objects; bg_21: `far1` sky 400, `far2` buildings 300, `ring` 150, `nea4` 100, `nea1` 50, walls 0). Coplanar pieces (`ring` over `nea5`, floor decals) are resolved by it. A z-buffer renderer must take the depth **per packet** (the average camera z of the packet's corners, `>> 4`, plus the bias): per-fragment z resolved the four coplanar floors of bg_21 (`nea5` 0, `nea1` 50, `nea4` 100, `ring` 150) per pixel, so the far part of the arena showed `nea4`'s small crooked tiles where the PS1 shows the ring (a big ring packet whose centre is nearer than the far tiles outranks them even with its +150). OpenCross: `render::StagePipeline` carries the packet centroid in every corner and writes that slot as the fragment depth.

Untextured faces use the raw colour (`/255`), textured ones modulate (`/128`), both times the object colour (`/128`). bg_21's `bg21` (untextured pale blue, 304 faces, the corridor through the east gate) is a **blend 4 (B + F/4) object with bias 0**, not an opaque sky backdrop: it adds a quarter of its colour over whatever is behind it. Its script (`far` -> `bg21`) has `flags = 0x04020004` (blend 4, depth-cue bit 17, world-oriented bit 26), colour op 0x20 = 0x800 -> 128 (neutral), no colour rate / oscillator; packet colours are (210 230 255) x 317, (0 0 0) x 176, (255 255 255) x 80 corners (a glow that fades to black), 160 faces = 80 position sets each present twice with opposite winding. One layer adds at most 64 per channel, two layers 128, and the render measures exactly that (uniform 64 / 128 bands in the intro shot `cam4` at tick 140, where the camera is inside the corridor). The depth cue is not involved and no colour wrap exists on the stage path. Unknown: a capture of `cam4` (ticks 100-149) has not confirmed the brightness.

**`sun0` is the stage light.** The built-in handler for a sprite named `sun0` copies the object's position (integer parts of +0 / +4 / +8) to a global light vector and draws nothing. That vector is only read by the unit drop shadows; unit lighting does not use it. Stages without a `sun0` object (bg_00, bg_01, bg_21 ...) keep the default (0, -0xC00, 0): a point 3072 units above the arena centre.

**The `bti0` emitters are the intro layer.** Every stage emitter named `bti0` (bg_00: 9 of them - `tori` birds, `nea5` / `nea6` / `nea7` = the sea and its sheen, `fish`, `kona` dust, a second `nea4`) runs from load like the others, but the battle main loop kills the layer when the intro ends (bg_00: present at tick 86, gone at tick 90; the `near` / `far` / `roof` / `ring` layers stay), and the outro brings it back before `bto0`. So bg_00's sea is only on screen during the party intro and the victory pose; the command phase and fights show sand, rock and sky only. `[Enhancements] RetainBattleScenery` (off by default; faithful play cuts the layer) skips the intro-end stop and the stop of the effect packs' op 0x60 (op 0x5F still starts the layer); switching it on after the layer was cut restarts the layer, switching it off stops it again. Sprite / built-in objects take their ABR from a table of `DR_TPAGE` words `0xE1000000 / 20 / 40 / 60`, i.e. the same `abr = blend - 1` as the meshes; the resident `fade` flat (blend 3) therefore subtracts (B - F), matching the luma dip at ticks 18-30 while the flat fades 55 -> 0.

OpenCross: `game::StageScene` runs the stage's emitters in `effects::EmitterSystem` and draws the live mesh objects as `render::StageInstance`s (matrix, colour, blend, bias, cull side, UV scroll); `assets::StageEmitter` keeps the static decode for tools (`sprite` = the op-05 name as written). Camera-timeline op 0x22 is forwarded to the stage emitters (`BattleCamera` emitter hook).

### 8.1 Depth cue of the stage objects
Object flag bit 17 chooses the packet-builder table: the plain table, unless **bit 17 is set and the fog flag (7.1) is non-zero**, then a family of eight depth-cue builders. They run the same projection / NCLIP / colour chain but keep the interpolation factor IR0 left by the last corner and finish with a depth-cue colour step: **every corner colour moves toward the far colour by IR0** (`c + IR0 * (FC - c)`, 0..1) after the object-colour multiply, textured and untextured alike (colour bytes, so the far colour 0x80 is "neutral" for textured packets and mid grey for untextured ones). IR0 is the fog term of that corner's z: `p(z) = far * (z - near) / ((far - near) * z)` clamped to 0..1 (`SetFogNearFar(near, far, H)`; defaults near 0x4000, far 0x5000, far colour (0x80, 0x80, 0x80)); sequence op 0x2D ramps colour and range. The extended path does the same when its flag bit 9 is set. It is up only while an element / tech effect pack runs.

OpenCross: `StageScene::set_depth_cue({active, far colour, near, far})` (BattleView feeds `fog_cur_`; `active` = the far colour left neutral) -> `StagePipeline` push constants `fogc` / `params.w` (A, B of `p = A + B / z`); the vertex shader takes z from the packet centroid (`ot_z`; the PS1 uses the last projected corner) and the fragment shader mixes `cm = min(colour * object, 255)` toward `fogc / (128 or 255)` before the texture multiply. The old whole-stage multiply (`fx_draw_fog`) is skipped while a stage is loaded. Only objects with flag bit 17 are cued (2,176 of 2,255). **Floor banding:** the factor is evaluated once per packet at its OT depth, and for ground cells that depth is the cell's farthest corner, so a darkening far colour shows as a step per cell (PS1-exact, kept in original art mode). In HD art mode (`StagePipeline::draw(linear=true)`) the vertex shader evaluates `p` at each vertex's camera z and the GPU interpolates it (noperspective on ground), so it ramps smoothly and neighbouring cells agree on shared edges.

### 8.2 Extended objects: bg_00 `nea7` sea sheen
`nea7` is an op-35 / op-36 object (ext scroll, window 64 x 64) with blend 2 and colour (39 141 175); its 120 packets are 113 GT4, 5 GT3 (colour 0) and 2 FT4 with corner colour 74 (textured, `enke` 64 x 64, UVs 0..63 over the whole window), tpage `0xB3` (abr 1). Draw colour = `74 * (39, 141, 175) / 128` = (22, 81, 101) per texel. The extended builders use abr = blend - 1 (4.3), i.e. **B + F**. Measured against a no-stage render (zen0, tick 400): a quarter-strength add changes 8,424 pixels by mean +8 (max 34); B + F changes 8,874 pixels by mean +32 (max 136), matching the bright turquoise bands of a retail capture. OpenCross draws B + F by default; `OC_STAGE_EXT_QUARTER=1` (`stage_pipeline.cpp`) selects the alternative look in which a scrolling blend-2 ext object adds a quarter (a title-scene level measurement once suggested that; it was not reconciled with the builder). Unknown: a capture of bg_00's victory outro (`bto0`, shots `o01..o03`) or a `p02`/`p03` party intro would settle it; `nea7` is a `bti0` object alive only until tick ~88.

The op-36 wrap is the GPU texture window (`u' = (u & ~(8 * mask)) | (8 * (off & mask))`, equal to `off + (u mod win)` for the power-of-two aligned windows the data uses) with the phase `(obj+0xA8 << 8) >> 16 & 0x7F` added to the packet u / v bytes first (they wrap in 8 bits). OpenCross: `StageVertex::uv_raw` / `uv_scale` carry the packet texel coordinates and the texel size so the window wraps per fragment (`u' = off_u + (u + phase) mod win_w`, phase = `(obj+0xA8 >> 8) & 0x7F` texels). The mesh morph op 37 lerps the part's vertices toward the target mesh by the eased, bit-12-reflected phase (battle_effects.md; verified on the title's fish).

### 8.3 Sprite sheets (type 3) and lens flares
The object scripts name sheets (sprite type 3) by 4-character name: `smok` (169 uses in 38 stages), `tam4`, `uzu1`, `kona`, `sen`, `64ke`, `cros`, `tama`, `swo2`, `tam1`, `den1`, `hite`, `g28`, `tam3`, `awa1`. No stage drp holds a type-0x03 entry: the sheets are battle.prd's resident packs (`miya` / `chih` / `tana` / `sato`, battle_effects.md) and `effect/particle.prd`. OpenCross: `StageScene::load(..., sprites, libs)` attaches both as libraries of the stage's `EffectBank`; `EmitterSystem::collect_quads` produces the quads of every type-3 object and `effects::GpuEffects` / `render::ParticleBatch` draw them (the same path as the title scene and effect packs). `StageScene::draw_sprites` runs after the units and before the spell effects, depth-tested against the meshes (sprite depth = ordering-table slot / 8192). bg_00 spawns 38 sheet objects over the intro; ~100 quads are live at tick 200.

**Lens flares** (`lenz`, drp type 0x15 / sprite type 21) are timinfo sheets too: type 0x15 is registered exactly like type 3, and section 5's tables are the sheet's frame tables (sprites of one frame share the slot of sprite 0). They are drawn by their own rule, not like type 3: frame k of the sheet flat on the screen along the line from the light through the screen centre, plus an additive full-screen flash (battle_effects.md "Sprite type 21"; `EmitterSystem` `collect_flare`). `import::load_battle_effects` builds a sheet from a type-0x15 entry like from a type-0x03 one. `sun0` is the stage light (section 8). `flat` is a built-in coloured quad of four fixed corners (drawn by `collect_builtin`; a `flat` covering the whole PS1 frame acts as a screen veil and covers the whole widened picture too).

#### 8.3.1 Unit drop shadows
Every visible unit whose model flags allow it casts a shadow, built by `StageScene::build_shadow` and drawn subtractively (B - F) on the floor after the scenery, depth-tested one slot in front of the floor. The footprint is the rectangle of the posed joints' x / z bounds padded by 0x80; the model's top (position + model height) is cast along the line from the stage light (`sun0`, section 8) onto the floor, giving one more hull point (offset `top y x d / (light y - top y)`, at most 0xC00; a light not above the top gives 0xC00, a light nearly straight above gives none; a vector component beyond 0x4000 falls back to straight down) unless it lies inside the rectangle. The hull's corners are rounded: each corner contributes four points of `(Bezier(A, B, C) + B) / 2`. The grey level is 255, reduced by `y x 255 / 1024` (floor 8) when the unit's feet are `y` above the floor. A hull of radius under 0x400 is a fan from the centre (grey) to the rim (0); a larger one is four bands from the rim inward with grey `3q / 2q / q / 0` (`q = grey / 4`). Casters are the battle units and the effect packs' pseudo-actor once its Shadow op set the flag; S5 op 0x22 and pack op 0x74 clear a unit's flag. `OC_STAGE_NOSHADOW=1` leaves them out.

#### 8.3.2 Cast shadows (`[Enhancements] Lighting`)
An enhancement, off with `Lighting`: no original art or rule behind it. The casters are those of 8.3.1, with their real posed meshes and weapons.

**The sun.** `game::key_light`: the `sun0` object's direction from the arena centre, else the first placed lens flare's (type 21), else the model key light of `Lighting` as seen from the stage's `zen0` camera (above, behind the camera, a little to its left; 47 degrees up). The stage light of section 8 is a point and stays untouched for 8.3.1 and the weapon glint; here the light is treated as far away, so all shadows of a stage fall the same way. Elevation is raised to at least 45 degrees with the azimuth kept (a lower sun stretches a shadow past the unit's height, into thin strips). `ocstage light all`: 11 stages take a `sun0`, 6 a flare, 83 the camera key light.

**The spell's shadow.** `render::spell_shadow`, per caster, at the middle of its body, over every light of the running `LightSet`, by each light's live level (`PointLight::live`: its peak this tick, 0 once its effect is gone, not the eased glow that lights the floor) x falloff. The levels sum to the spell's level, and as its share of the light climbs from 0.3 to 0.6, the sun counting as level 0.5 (smoothstep), the sun's shadow of that unit fades out and the spell's fades in. So a dim spell leaves the sun's shadow alone, one bright enough at the unit turns the shadow away from itself, and a unit out of reach keeps the sun's. The spell's shadow has one direction: the level-weighted mean of the lights' slopes (shadow length per unit of height, away from the light, at most 1.19 = an elevation of 40 degrees, since many spell lights sit at floor level, and scaled down within 1000 units of the unit's axis). Lights around a unit therefore cancel and a light on the unit itself leans it little, so the shadow gathers under the unit. Per unit, per tick, the share eases by 0.3 and the slope by 0.15; a new shadow starts at its slope, and one losing its light keeps it as it fades.

**The mask.** `render::ShadowPipeline` flattens every caster onto y = 0 along each light into a 2048 x 2048 RGBA target that looks straight down on x, z in +-6144: red for the sun, green for the spell's shadow. The model first grows 26 units along its normals, so limbs keep some width. Blending keeps the largest value per texel, so overlaps never darken twice. The value is the caster's share of that channel, times 1 at the floor falling to 0.4 at height 2400; an enemy's is scaled by its fade. Parts a unit hides cast nothing; the texture cut-outs apply, except on env-mapped parts.

**The floor.** A multiply-blended quad at y = 0 over the area shadows can reach, after the scenery and before the units, depth tested per fragment at (camera z / 16 - 64) / 8192: the 64 slots clear the whole-packet depth of coplanar floor layers (`bg_21`). The mask is sampled at the centre and on two fixed rings of 8 taps, 1.25 and 3.5 texels (one texel = 6 units); the wider average takes over as the mask value falls, so the edge is crisp at the feet and a little softer higher up. The multiplier is `(1 - s + knee(U)) / (1 + knee(L))`: `s` = the larger mask channel x strength (0.5 for a light object, 0.42 for the camera key), `L` = the first three spell lights at the point (the ones the floor is lit by), `U` = the same cut by the green channel, `knee` the light compression of `render/lights.h`. It reproduces the floor's own `1 + knee(L)` where nothing is in shadow. The 8.3.1 hulls are not drawn while the floor is on: every unit, grounded or flying, has only its cast shadow. They come back only where the floor is not drawn (Lighting off, or the shadow pipeline failed to start).

Shadows fall on the floor plane only: not on scenery, not on other units, and a unit does not shade itself.

### 8.4 Object screen test (flag bit 28)
Every object draw with flag bit 28 first runs a screen test and draws nothing when it fails. For a type-0x02 mesh the test takes six points fixed at load from the mesh's whole vertex array (per-axis maximum and minimum, starting from -0x7FFF / 0x7FFF): the centre `(max + min) / 2` (rounded toward zero), `(max x, 0, 0)`, `(min x, 0, 0)`, `(0, 0, max z)`, `(0, 0, min z)` and `(0, min y, 0)` (the top). They go through the object's draw transform and the GTE projection with its limits: view x / y saturate at -0x8000..0x7FFF, the depth at 0..0xFFFF, a depth of at most `H / 2` (also behind the eye) projects at the largest scale (0x1FFFF / 0x10000, about 2), and screen x / y saturate at -1024..1023. The object is **not drawn when no point has screen x in 1..351 or screen y in -31..223**: an x inside the range or a y inside the range keeps it, so only objects whose six points all lie in the corner regions are dropped (the test also fails on a MAC1 overflow flag, which these inputs never raise). Because the points are not the box corners and a point behind the eye projects to a large but finite place, a close object that covers the screen can be dropped: FATE's `boss` intro (scene 462, bg_40) is four such stage objects `nea1`..`nea4`, and in shot `i04` `nea2` (the leg) is dropped at ticks 0-19, 21-26 and ~34-67 of the shot and `nea4` at ~23-67 (PS1 capture, game frames weighted by their vsync count; OpenCross 0-19, 21-26, 33-69 and 23-69); in shot `i05` (150 ticks) `nea2` is dropped only early, at ticks 0-7, 9-10 and 13-18 (OpenCross 1-8 and 12-18), and `nea4` at 0-7 and 9-10 (OpenCross 1-8 and 12), both drawn for the rest of the shot. Every other object type with bit 28 (sheet sprites including the add + subtract pair, the flat / line sprites, the ground, models) projects only its origin, the object's view-space position (the translation of its draw transform), and draws nothing when that projection reports a GTE error: view x or y outside -0x8000..0x7FFF, depth outside 0..0xFFFF, a depth of at most `H / 2` (also behind the eye), or screen x / y outside -1024..1023 (x widened with the widescreen columns like the packet rules). The ground's colour is then not taken either. The lens flare projects its position itself and has no such test.
OpenCross: `import::mesh_cull_points` -> `assets::StagePart::cull_points`; `EmitterSystem::MeshInstance::off_screen` runs the test (widescreen columns widen the x limits about the centre column like the packet rules, `render::cull_frame`; the free camera turns it off) for the battle stage (`StageScene::draw`), the effect packs' meshes (`BattleView` effect draw), the title backdrop and the field's encounter-effect meshes.

### 8.5 The ground object (battle type 0x13)
The `ring` mesh is not drawn as a mesh object in battle. Battle init copies the drp's first type-0x12 entry and builds a type-0x13 ground object from it (0x24 bytes): +0 the vertex array, +4 the FT3 packets (count +0x10), +8 a 10 x 10 table of 0x1C-byte cell records, +0x12 flags, +0x14 colour, +0x20 the GT3 packets (count +0x1E). Every FT4 / GT4 packet becomes the record of the cell at its corner average (s16 sums of x + 0x1400 and z - 0x1400, `>> 2`, rounded toward zero, `>> 10` -> cx, cz; index `cx - 10 cz`): uv0 +0, clut +2, uv1 +4, tpage +6, uv2 +8, uv3 +0xA, colours +0xC / +0x10 / +0x14 / +0x18 (FT4 repeats its colour). **F3 / G3 packets are dropped** (1,776 of the rings' packets). Over all 95 rings: exactly 100 quads each, one per cell, corners at the grid points in the order left-top, right-top, left-bottom, right-bottom (top = larger z), y = 0, so the cell draw equals drawing the ring's quads.

The `ring` object (sprite type 19) draws it: ground +0x14 = the object colour, +0x12 bit 1 = the object is semi (blend != 0; drawn B/2 + F/2: the tpage ABR bits are cleared), bit 15 = object flag bit 12 (an alternate cell draw, not reproduced), +0x1C = the object's OT bias, **which the draw never reads**: every ground packet sorts at the ground bias (default 100; sequence ops 0x6D (target s16 @+8) / 0x6E (target 100) ramp it over s16 @+4 ticks, `from + (to - from) t / ticks`, one step at once; back to 100 when the overlay is freed). The cells take the slot from the FARTHEST corner (max SZ `>> 2 >> 2`), drop a cell only by NCLIP and the slot range 0..4095 (no GTE flag test; near cells, slot < 0x200, are cut into four sub-quads: affine only, not reproduced); the rim triangles use AVSZ3 and the flag test. The fog flag selects the depth-cued twins whatever the object's flag bit 17. Ground `+0x12 bit 0` makes the ordinary draw skip the ground: the effect overlays then draw it themselves with a rect, skipping the cells with `x >= r[0] && x < r[2] && z > r[3] && z <= r[1]` (x / z = the cell's left / top edge; battle_effects.md).

**The object's extended bits do not reach the ground.** Only colour, semi flag, flag bit 12 and bias are passed to the ground draw; the extended-object draw (ext bit 4 reversed cull, bit 5 two-sided, bit 0 UV scroll) is reached only from type-14 mesh draws. bg_80's `ring` object carries ext bit 4 (`reversed-cull` in `ocstage objects`, the only type-19 object with any ext bit); applying it culled every upward cell and rim triangle and left the clear colour where only the ring covers the floor (the black block in front of the party, Mannequeen battle).

OpenCross: `StageScene` builds the cells / rim (`ground()`, `effects::FxGround`, also `effects::fx_ground()`), draws the ring instance with `StageInstance::ground` (bias = `ground_bias()`, depth cue on, cells hidden by `hide`; cull 0 and no scroll), and provides `set_ground_skip()`, `hide_ground_rect()`, `ground_bias_ramp()` / `ground_overlay_end()`, `ground_cell_texture()`. `StagePipeline::draw_cpu` gives every cell its farthest corner as the packet centre and leaves the untextured packets out; `draw_prims` draws the overlays' baked meshes with the stage atlases.

## 9. Validation and export

`python -I tools/py/cc_stage.py validate` (~1 s) and `ocstage validate` check:

| check | result |
|---|---|
| stage drp parsed | 101 / 101 (+7 `.ctd`) |
| meshes | 1,073 (978 x 0x02, 95 x 0x12): 105,506 vertices, 102,407 faces; indices < nVerts, group table tiles the face area, vertex array ends at EOF, face count = header |
| packet code byte | = type or type\|2 in all packets |
| textured faces | tpage mode 0/1, y base 256; CLUT row exists (TIM or ctd); all UV corners land on loaded VRAM |
| TIM image rects | all 2,227 inside rows 256..511 |
| cameras | 1,029, size = 20 + 20*count |
| sequences | 347, each terminated by 0x21 (optionally one extra terminator) |
| lenz | 14 entries parse |

Loaded-image x extents (halfwords): 0..384 in 94 stages, 448..576 in 2, 448..768 in 1, 0..320 in 1. `export <bg_NN> <outdir>` writes `part_<idx>_<name>.obj` per mesh (`v x -y z r g b`, 1.0 = 0x80; `vt`; `usemtl`), `stage.mtl`, `tex_m<mode>_c<clutx>_<cluty>.png` atlases and `stage.json` (atlas origin, cameras, sequences, emitters, TIM table).

**UV convention.** `stage.json`/OBJ `vt` and `assets::StageVertex::uv` are OBJ-style (v up: `1 - v/256`). A top-down texture upload (Vulkan) must flip v again; the stage shader does (`1 - uv.y`). Forgetting it samples the mirrored atlas rows, which fall in neighbouring TIMs with other CLUTs (bg_00 `near*` walls looked like noise). The "noisy" coral/rock look of `gak*`/`wa_*` is the real texture data.

## 10. Which rooms fight on which stage

The stages have no names in the data. `occ battlefields` lists, per `bg_NN`, the number of scene records (`scenedat.bin`, byte 0x1A & 0x7F) with that stage and every room whose script has a BATTLE op (A3 / C9) landing on it, by `BattleView`'s rule: the op's battlefield operand when it is an immediate 0..99, else the scene's own bg. Battle ops with a variable id (random encounters) are not resolved. `--inc src/data/battlefield_rooms.inc` writes the room lists the Debug tab's battlefield picker shows as place names (`data/battlefields.h`). The room-prefix to place table comes from the overworld screens' location markers (`occ world-markers --inc src/data/area_names.inc`: each `wld_*` marker entity's label message (window #56, EN) and its `SET_NEXT_ROOM` target; "North" / "South" / "East" / "West" dropped, several markers on one prefix joined by " / "). A prefix no marker reaches (interiors entered from another area, special rooms) keeps its prefix.
