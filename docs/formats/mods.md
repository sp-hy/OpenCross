# Mods (loose replacement files) and the Modded art mode

RDE itself has no mod loader; mods for it are folders of loose files that replace members of the `data\*.dat` archives. This document describes how OpenCross loads them (`src/vfs/mods.*`, `src/vfs/vfs.*`): the mod folder layout, archive and single-file mods, how each loose file is matched to an archive member, art modes and priority, the voice-line layout, the texture dump / replacement system, and the engine features a mod turns on with its `mod.ini` (section 8). Everything here is OpenCross behaviour, not an RDE feature.

## 1. Folder rules

```
<GameDir>\mods\<mod name>\<replacement files, any depth>
<GameDir>\mods\<mod name>.zip | .7z | .rar
<GameDir>\mods\<archive>.dat
```

* A missing `<GameDir>\mods` is created at boot (empty; a warning is logged when the folder is read-only).
* Every sub-folder of `mods` is one mod, and so is every `.zip`, `.7z`, `.rar` and `.dat` file directly in `mods`. Its **folder or file name** (extension included, so `Pack` and `Pack.zip` are two mods) is the name shown in the Esc overlay's *Mods* tab and the `[Mods]` ini key. Other files directly in `mods` are ignored.
* A bare `.dat` is a mod of that one file, resolved like a file at a mod root: `mods\lang.dat` overlays `data\lang.dat` (section 2, rule 1).
* An archive reads like a folder (section 1.1).
* Everything below a mod folder is scanned recursively; each file is resolved on its own (section 2). Layouts seen in the wild:
  * partial path: `Chrono Revision\face\2021\00_seljyu.png` -> `hd/face/2021/00_seljyu.png`;
  * extra wrapper folders: `HD Boat\HD Boat Plus\fieldobj\player\cl_bort\cl_bort.tim` -> `cdrom/fieldobj/player/cl_bort/cl_bort.tim`;
  * flat files at the mod root: `Zeightgeist HD Backgrounds\alu_a01f.chip2` -> `hd/map/mapbin/alu_a01f.chip2`;
  * archive overlay: `Snooty AI Upscale Videos\movie.dat` -> its members replace those of `data\movie.dat`;
  * loose movie: `a01op_de.mp4` (or `.mkv`, any folder) named after a shipped `a01op_de.bk2` -> replaces that movie (section 2, rule 3).

### 1.1 Archive mods

A ZIP, 7z or RAR (4 or 5, solid included; the extension selects the file, the format is recognised by content) is read live and never unpacked: its files resolve exactly as those of a folder would, and nothing is written to disk (`src/vfs/mod_archive.*`). A file of a packed mod is an overlay file with a `member` (`OverlayFile`), and every consumer takes bytes through `Vfs::read_mod_file`, so textures, game files, voices and movies work the same as loose files. The list is built at the scan whether the mod is enabled or not.

* **ZIP** (stored or deflated members). Each member is read on its own through miniz.
* **Everything else** (7z, RAR, a ZIP with another method) can only be walked from the start. An archive of up to 256 MiB unpacked is decoded into memory at its first read and served from there. A larger one is walked for each read: fast when its members are stored separately, slow when it is solid, because every read decodes from the start of the data. Such an archive shows *May run slowly: extract it to a folder* under its name in the Mods tab (`Mod::may_be_slow`; whether it is really solid cannot be told in advance), and a read that takes over 0.5 s logs a warning once. The memory goes when the overlay stops using the archive.
* **Scan cost.** Listing a ZIP or 7z reads its directory only. A solid RAR has no directory: listing it decodes the whole archive, at every scan.
* **Wrapper folder.** When every member sits in one folder, as from zipping a mod folder, the mod starts inside it (repeatedly), unless the folder is called `voices`, `textures` or `shaders`. This puts `Pack\voices\...` at the top of the mod, where the voice lookup expects it. An archive whose stem is `voices` reads like a folder called `voices`, with no wrapper removed.
* **Limits.** A password-protected, damaged or multi-part archive shows *Can't be read* among its issues (the warning count on its row, the *Issues* section of its details). An `<archive>.dat` inside a packed mod is unmatched: unpack the mod, or put the `.dat` directly in `mods`. A movie inside an archive is read whole into memory when it starts, not streamed.
* A file held open by the game cannot be replaced or deleted until *Rescan* or a mod switch stops using it. A replaced archive (new size or time) is picked up at the next *Rescan*.

### 1.2 Text rows (`text\`)

A mod's `text\<member>` (directly in the mod's root, after a wrapper folder) holds only the rows the mod adds or changes of the `lang.dat` text member of that name, in the member's own format: `en.csv` (and the other languages: `room`, `msg`, text, tab separated), `Ex_<lang>.csv`, `btel_<lang>.csv`, `mesgen_en.csv` / `mesgen.csv`, `mess_wend.csv`, and the `.txt` tables (`sysmes.txt`, `cmnmes.txt`, `shopmenu.txt`, ...; a header row naming the key column and the language columns it sets, then its rows). Names match in any case.

* **Merge** (`import::TextMod`, every `LangTables` when it reads the member): the member as the game ships it, or as a mod's whole `lang\<member>` replaces it, then the enabled mods' rows, lowest priority first, so the first mod in the list wins a row both give. A row replaces the row with the same key or is added; in a `.txt` table only the language columns the row file has are set (the others keep theirs), matched by heading. No loading-order rule applies to a row file (its rows need not be sorted).
* **Conflicts:** a row two mods give different text is logged once (`text: <member> <key>: '<mod>' wins over '<mod>'`).
* **Mod rooms:** field text rows (`<lang>.csv`, `Ex_<lang>.csv`, `mess_wend.csv`) of a room id the mod's `[Rooms]` (section 8) lists are stored under that room's internal id, so two mods' room 1001 keep their own text; any other id is the game's own row of that id (the game's text has rows from 1000 on too: the `fin_` scenes at 1000 + map id). Battle rows (`btel_`) keep their battle ids.
* The startup log lists `mods: '<mod>' text rows for N member(s)`.

### 1.3 Table rows (`tables\`)

A mod's `tables\<table>.txt` (directly in the mod's root, after a wrapper folder) changes single fields of the records of one battle / menu table, instead of replacing the whole file, so several mods that each change a few records stack. `<table>` names the file it changes:

| table | records | file |
|---|---|---|
| `monster` | enemies, 0xB0 bytes | `battle/data/monster.bin` |
| `char`, `char20`, `char_w0` .. `char_w5` | the 51 characters of that set, 0xB0 bytes | `battle/data/<table>.bin` |
| `pgdat` | elements and techs, 0x2C bytes | `battle/data/pgdat.bin` |
| `menu_pg` | the menus' element rows: who may place it, price, menu use, auto-fill scores, 16 bytes (same ids as `pgdat`) | `battle/data/menu_pg.bin` |
| `waa` | equipment and material stats, 0x1C bytes | `battle/data/player.dat` part 4 |
| `menu_waa` | item info: who equips, price, category, 12 bytes (same ids as `waa`) | `battle/data/exdat.dat` part 5 |
| `waa_tbl` | forge recipes: units of each material, 32 bytes (same ids as `waa`) | `menu/waa_tbl.bin` |
| `scenedat` | battle scenes, 28 bytes | `battle/data/player.dat` part 0 |
| `ditem` | drop rows, 4 x u16 | `battle/data/ditem.dat` |
| `el_shop` | element shops: a list of element ids per row (32 rows) | `menu/el_shop.bin` |
| `waa_shop` | blacksmiths: a list of item ids per row (32 rows) | `menu/waa_shop.bin` |
| `trade` | trading posts: a list of goods per row (32 rows), each with a colour mask and a level sum | `menu/trade.bin` |

UTF-8 text, CR LF or LF, an optional BOM. `[<index>]` starts a record (the record's index in the table, decimal or `0x` hex); each following line is `<field>=<value>`. A field is a name from the list below or `0x<offset>:u8|u16|u32` for a byte the names do not cover (the record's byte offset). Values are decimal, `0x` hex or negative (stored in the field's width); integers are little-endian like the files. Blank lines and lines starting with `;` or `#` are skipped.

```
; tables\monster.txt
[12]
max_hp=900
atk=40
0xA6:u8=3
```

Field names (`data/table_rows.cpp`):
* `monster`, `char*`: `innate`, `growth_col`, `gender`, `max_hp` (u16), `atk`, `def`, `hit`, `evd`, `mag`, `mdef`, `status_dur`, `stamina_rate`, `weapon`, `armour`, `accessory_0` .. `accessory_3` (u16), `drop_base`, `model`, `ap`, `weapon_model`, `level_mask_0` .. `level_mask_7` (u16), `cell_0` .. `cell_47` (u16, the listed grid cells), `drop_row`, `gold` (u16), `hit_med`, `hit_heavy`, `star_growth`; `char*` also `equips_like` (a character: whose equipment and elements a character mods add takes, below);
* `pgdat`: `flags0`, `colour_bit`, `level`, `mode`, `power`, `status_pct`, `variance`, `hits`, `status_lo`, `status_hi` (u32);
* `menu_pg`: `eligible_lo` (u32), `eligible_hi` (u16; one bit per character id), `price` (u16), `menu_flags`, `use_flags`, `fill_score_0`, `fill_score_1`, `equip_add`, `equip_remove` (below);
* `waa`: `tier`, `class` (the whole byte: class and the sweep bit), `mode`, `colour`, `power`, `mag`, `acc`, `var`, `flags`, `slot_mask` (u16), `mask_lo`, `mask_hi`, `status_lo`, `status_hi` (u32);
* `menu_waa`: `equip_lo`, `equip_hi` (u32), `price10` (u16, the price / 10), `cat`, `extra`, `equip_add`, `equip_remove` (below);
* `waa_tbl`: `mat_0` .. `mat_31` (units of material item 0..31 the forge takes);
* `scenedat`: `enemy_0` .. `enemy_2`, `count_0` .. `count_2`;
* `ditem`: `slot_0` .. `slot_3` (u16).
* `el_shop`, `waa_shop`, `trade` (list tables): `add=<entry>`, `remove=<entry>`, `clear=1` (below).

* **Merge** (`data::TableRows`, when the tables load at launch): the table as the game ships it, or as a mod's whole file replaces it, then the enabled mods' rows, lowest priority first, so the first mod in the list wins a field both set.
* **Records by name.** A header that is a name (`[my_spark]`: a lower-case letter, then lower-case letters, digits and `_`) adds a record to `monster`, `pgdat` (with `menu_pg`), `waa` (with `menu_waa`), `scenedat`, `ditem`, `el_shop`, `waa_shop`, `trade` (rows, below) or `char` (a character: `char20` and `char_w0`..`char_w5` share its names, section 8 `[Characters]`); the other tables have a fixed size. A name is one record across every mod: a second mod naming it changes that record field by field, as for the game's own records. `base=<index>` starts a new record as a copy of that record (the first mod in the list that gives a base decides; the copy comes before any field). The named records follow the table's own records, mod by mod in priority order, each mod's names listed in the table's own-id section (section 8: `[Elements]` for `pgdat`, `[Items]` for `waa`, `[Characters]` for `char`, `[Monsters]` / `[Formations]` for `monster` / `scenedat`, `[ElementShops]` / `[Smiths]` / `[TradingPosts]` for the shops and posts) first, by its own id, then the rest of its names in name order; `menu_pg` gives a name the same id as `pgdat` and grows with it (a grown row starts with every character eligible and the rest 0, and a record's pgdat `base` is its menu_pg base too unless its menu_pg rows give one), and `menu_waa` and `waa_tbl` the same as `waa`. These ids are the engine's: a mod's data names the records, and its scripts use the ids its `[Elements]` / `[Items]` gives them. A reference that does not fit its field is a problem, except in a formation's enemy slots (below). Element ids end at 16383 (a grid cell keeps its element in 14 bits): a `pgdat` name past it gets no record, a problem.
* **Items by name:** an item a mod adds (`[star_blade]` in `tables\waa.txt`, its price and who equips it under the same header in `tables\menu_waa.txt`) gets an id after the game's 256 (equipment and forge materials are one table: the kind is `menu_waa`'s `cat`). A drop slot, a blacksmith list or a character's starting gear names it (`slot_1=@waa:star_blade`, `add=@waa:star_blade`, `weapon=@waa:star_blade`). Its name and description rows use the mod's own item id (`text\sysmes.txt` `0x00<id>`, `text\waa_spec.txt` `<id x 3 + line>`; a name starts with its icon character, as the game's do: the lists draw the icon from it); its forge recipe is the same header in `tables\waa_tbl.txt` (`mat_3=2`; a `base=` copy starts with its base's recipe, a record without a base with none; a blacksmith list that names an item without a recipe shows it, but it can't be forged). Item ids end at 511 (an equipment word past it is an element or a key item): a `waa` name past it gets no record, a problem. A weapon it adds may bring its own model: `cdrom\battle\wepon\<name>.bin` in the mod (a weapon pack, `docs/formats/model.md`) is shown as that pack's first part, in battle and on the menus, by whoever equips it, held on the wearer's weapon mount; without one it shows the part of the wearer's own pack its tier names, as the game's weapons do (only a pack the mod adds counts: an item named like one of the game's packs, `[sword]`, keeps its tier's part).
* **List tables** (`el_shop`, `waa_shop`): a shop row is a list, so a row adds and removes entries instead of setting fields: `add=<id>` appends an entry the row doesn't hold yet, `remove=<id>` takes every copy out, `clear=1` empties the row before the mod's own adds. The enabled mods apply lowest priority first, so two mods' additions to one shop both land and the first mod in the list decides what it removes. A shop by name (`[hub_shop]`, `base=<row>` to start from a copy of a row) follows the table's 32 rows; its scripts open it by the id the mod's `[ElementShops]` / `[Smiths]` / `[TradingPosts]` gives it (section 8).
* **Trading posts** (`trade`): a post's entries are keyed by their goods (an item id or `@waa:<name>`). `add=<goods> colour=<mask> levels=<sum>` adds the goods to the post, or, when the post already has them, sets only the words given (`add=7 levels=4` makes Eyeball cheaper and keeps its colour); a new entry needs `levels=` (the level sum of Elements it costs; `colour=` the colour bits it accepts, 0 or left out = any). `remove=<goods>` takes the goods' entry out, `clear=1` empties the post as for the shops. A post holds at most 16 entries (more are logged and dropped). `[bazaar]` with `base=<post>` adds a post.
* **Monsters and formations by name:** a monster a mod adds (`[big_boss]` in `tables\monster.txt`) gets an id after the game's 222; a formation slot naming it (`enemy_0=@monster:big_boss`) holds it even when the id doesn't fit the slot's byte (the engine keeps it beside the record; 0xFF stays an empty slot, so a reference to the added monster with id 255 is a problem and leaves the slot as it was). Its battle model is its own by name too when the mod ships one: `cdrom\battle\monster\<name>\<name>.obj` with its texture (`<name>.ltd` / `.ltc`), `at0.prd` beside it and, for a weapon, `<name>.bin` (a weapon pack; part = the weapon item's tier, as for the game's monsters); without the `.obj` it uses the model its `model` byte names (a `base=` copy keeps its base's). Only a file the mod adds counts: a name the game's monster folders already use (`[komodo]`) keeps its `model` byte's model. The Bestiary shows the model the battle uses; battle scripts asking for the model number still read the `model` byte. A formation a mod adds (`[boss_fight]` in `tables\scenedat.txt`) gets a scene id after the game's 513 and its battle script by name: `cdrom\battle\event\<name>.pac` in the mod (the game's formations find theirs by record). Its battle text rows (`text\btel_<lang>.csv`) use the mod's own formation id.
* **References:** any value may be `@<table>:<name>` or `@<table>:<name>+<number>`, the id of a named record plus a number (a grid cell's flag bits): `cell_3=@pgdat:my_spark+0x4000`.
* **Conflicts:** a field two mods set to different values is logged (`tables: <table> [<index>] 0x<offset>: '<mod>' wins over '<mod>'`); a line that cannot be read, or a record or field the table does not have, is logged as a warning and skipped.
* The startup log lists `tables: <table> adds N named record(s) from <id>` and `tables: '<mod>' <table>: N field(s)` per mod and table.
* **New elements.** Besides records by name, a mod's whole `pgdat.bin` longer than the game's 527 records adds elements and techs from id 527 up (`battle_data.md` section 5, **A mod's records**). What such an element is comes from its record alone: byte +0x01 bit 1 makes it a tech, and the flag bytes +0x00 / +0x01 give its kind (attack, summon, support, healing, consumable, trap, or none; **Element kinds** there), which places it in the element list's Attack first and Heal first orders (`rules/menus.md` section 5) and decides whether New Game+ carries it (every kind but summons and none, `save.md` section 14). A `flags0` row on a game record changes that record's kind the same way.

## 2. Resolution (once per scan, case-insensitive, component-wise)

1. **Archive overlay.** A file named `<archive>.dat`, where `data\<archive>.dat` is one of the archives OpenCross reads (`cdrom cdrom2 hd lang font ui movie`) and the file starts with the ZIP signature `PK\3\4`, is a set of member replacements, not a new archive. Each of its members is resolved by rule 2 as the path `<archive>/<member>` (`cdrom2.dat` members as `cdrom/<member>`) and read in place from the ZIP, with nothing unpacked; every member it does not hold still comes from the shipped archive, so the file may hold one member or all of them. The members behave like loose files: they count in the mod's files and conflicts, the first active mod in the list wins each one, several mods' copies of the same `.dat` combine, and a `cdrom.dat` member wins over the `cdrom2` copy. A member that cannot be read falls back to the game's copy. A `.dat` not matching this rule is resolved as an ordinary file by rule 2.
2. **Member.** The candidates are all shipped members with the same file name. Members are named by the path the game reads, `<archive>/<member>`, with `cdrom2` members counted as `cdrom/` (callers always ask for `cdrom/...`; the mod file then wins over both the cdrom2 HD override and the disc file). For each candidate, count how many trailing path components it shares with the mod file's path (inside the mod folder). The candidates with the longest shared run win:
   * exactly one: **matched**. Leading folders of the mod path that do not occur (wrappers such as `HD Boat Plus`) are ignored; a bare file name works when the name is unique (`alu_a01f.chip2`). Below an archive folder (rule 4), a path whose folders contradict the member (a folder it names that is not among the member's, in that order: `cdrom\fieldobj\player\dario\dario.obj` against the game's `battle/monster/dario/dario.obj`) is **added** instead; a path that only leaves folders out (`cdrom\alu_a01f.bin`, `cdrom\map\alu_a01f.bin` for `map/mapbin/alu_a01f.bin`) still matches;
   * several: **ambiguous**, not loaded (for example `00_seljyu.png` alone fits both `hd/face/1999/` and `hd/face/2021/`; add the folder), unless the path names an archive folder (rule 4) and spells a folder the game ships nothing in: then it is **added** (a new monster's `cdrom\battle\monster\<name>\at0.prd`, a name every monster folder has);
   * none: rule 4.
3. **Movie.** An `.mp4` or `.mkv` file whose stem equals a shipped `.bk2` member's stem is a movie replacement, kept as `movie/<name>.mp4|.mkv` whatever its folder (H.264 / HEVC, or any other codec the bundled decoder opens). The movie player looks for `movie/<name>_<lang>` then `movie/<name>`, trying a loose `.mp4`, a loose `.mkv`, then the archive's `.bk2`, so a loose file wins over the shipped Bink movie and over a `.bk2` in a mod's `movie.dat`. Rule 3 does not apply inside a `movie.dat`: an `.mp4` there is unmatched.
4. **New member.** A file that rule 2 matches with nothing is **added** when its path names an archive, and is then read exactly like a replacement (overlay, priority, conflicts, game data):
   * below a folder named after one of the archives above: the first such folder starts the member path, `cdrom2` counting as `cdrom` (`My Mod\Rooms\cdrom\map\mapbin\newroom.bin` -> `cdrom/map/mapbin/newroom.bin`);
   * a member of a mod's `<archive>.dat` (rule 1): `<archive>/<member>`; an `.mp4` / `.mkv` there stays unmatched (rule 3);
   * any file of a mod **folder** named after an archive, the loose-file layout of `mods\cdrom\...`: `mods\cdrom\flux\ui.bin` -> `cdrom/flux/ui.bin`.

   Anything else is **unmatched**, not loaded (for example alternates such as `02_gill alt1.png`, readme files). A file that matches a shipped member by name (rule 2) is never added, so a new file needs a name the game does not use. `Vfs::list` still lists only the shipped archive. The game finds most files by number through `cdrom/cdrom.fnd` (`docs/architecture.md` 3.6): a mod's own `cdrom.fnd` (and `cdrom2.fnd` for disc 2) can point a shipped number at another file. A **new room** is not a record: the mod lists it in its `mod.ini` `[Rooms]` (section 8) under an id of its own from 1000 up, and its files are found by name (a map jump to it loads its `.bin` + `.ctd`, though `RoomView::rooms` lists only the shipped rooms). **Mods stack:** what a mod adds is known by name, and the numbers a mod uses for it are its own (two mods built apart may both call their first room 1001), so mods never fight over ids; text a mod adds or changes is merged row by row (section 1.2) instead of one mod's file replacing another's.

The startup log lists per mod `mods: '<name>' (enabled, load on modded): N matched, D game data, A archive(s), T texture(s), M model(s), V voice(s), W added, U unmatched, B ambiguous` (matched and game data include the added files), followed by up to 12 added / unmatched / ambiguous paths each (a `.dat` member as `<rel>/<member>`); `mods: K active mod(s), F file(s), T texture(s), M model(s)` is logged each time the overlay is built.

## 3. Load on, priority, overlay

**Game data.** A member under `lang/`, `cdrom/battle/data/`, `cdrom/battle/event/`, `cdrom/battle/mes/` or `cdrom/prog/`, one of `cdrom/menu/el_shop.bin`, `waa_shop.bin`, `trade.bin`, `waa_tbl.bin` and `keyitem.dat`, or the base sound banks `cdrom/sound/effect/common/effect00.dat` and `cdrom/sound/wave/wave0000.dat`, is **game data** (`vfs::is_game_data`, `Mod::data`). Everything else follows *Load on* and swaps live: art and the rest of the sound, which takes effect the next time it is read, so a song already playing keeps playing. That includes room files: their scripts and art share one file, and `cdrom2` holds art versions of them. Game data ignores *Load on*: it is active in every art mode. Much of it is read once at boot, so the overlay keeps what the first `ModManager::apply` installed: the enabled mods and order at launch, until the next launch. A switch never changes it, which keeps tables, menus and scripts from different mods apart. The Mods tab says so in the details of a mod with game data and shows *Restart required* while the enabled game-data mods or their order differ from the launch's; a mod with neither art member files nor textures shows `All`, fixed, as its Load on. Priority and conflicts work as for art, in any art mode.

* Each mod has **Load on** = `Modded` (default) | `SD` | `HD` | `All` (ini: `modded|sd|hd|all`; `original` reads as `sd`, anything unknown as `modded`): the art modes in which its files are active. Art mode `Modded` = HD art (cdrom2 override on, RDE's HD assets) plus OpenCross's own improvements (`Vfs::enhanced()`) plus the mods set to Modded or All. `HD` and `SD` (original art) load only the mods set to that mode or All, so with the defaults HD and SD stay stock.
* **Priority** = list order (top first). For each target the first enabled, active mod in the list wins (loose files and `.dat` members alike). The Mods tab counts, among enabled mods that share an art mode, the files a mod wins over the mods below it (its details) and the ones a mod above replaces (*N files replaced by a mod above* among its issues).
* Lookup order of `Vfs::read` / `read_disc` / `exists`: overlay file (loose, or a member of a mod's `.dat`) -> (cdrom: cdrom2 when the HD rule says so, `docs/formats/rde_archives.md`) -> shipped archive. `list` always lists the shipped archive.
* Overlay changes are a pure art swap. `apply_art_mode` rebuilds the overlay; when its content changed (HD <-> Modded, a Mods tab edit), field room art / models and battle unit models are rebuilt even if HD stays HD (`set_art_mode(hd, force)`), and the path-keyed texture caches of the dialogue portraits, main menu, shops and party screen use `Vfs::cache_key` (path + overlay generation), so the next draw loads the mod file; the window skin of the field dialogue and the key-item list (`hd/window/wNN.png`, or the PS1 sheet in original art) is read again when the overlay generation it was read with has changed, so a mod's frame shows in those windows after a switch too, the default frame (`w04`, loaded at boot) included. A movie already playing keeps its file. A mod's loose movie (`movie/<name>.mp4|.mkv`) is not read into memory: `Vfs::loose_file(path)` returns the overlay's file on disk and the movie decoder streams it through a file-backed reader; archive members, those of a packed mod or a mod's `.dat` included, are read whole (`docs/formats/movies.md`).

## 4. Settings (`opencross.ini`)

```
; comments are whole lines only (; or #); the reader does not strip trailing comments
[Video]
; ArtMode: hd | original | modded
ArtMode=modded

[Mods]
; one line per mod, in priority order (top = wins): <folder or file name>=<enabled 1|0>,<modded|sd|hd|all>
Chrono Revision=1,modded
HD Boat=1,all
Zeightgeist HD Backgrounds=0,modded
```

A scripted run (`[Debug] Script`) or any run started with `--config` tests the game as shipped: every mod is off for the whole run, also through a route `art` command, and the ini's choices stay as they are; `[Debug] ScriptMods=1` keeps the enabled mods instead (a route that tests a mod). Mods missing from `[Mods]` are appended in name order with `1,modded`; entries whose mod is gone are dropped on the next save. F6 cycles SD -> HD -> Modded; the Esc overlay's art-mode setting has the same three values; the route command `art modded` selects it. The `Dump*` category keys (section 7) share the `[Mods]` section with the mods; they are not mod names, and the obsolete `DumpTextures` / `ReplaceTextures` keys are ignored and dropped.

**Mods tab (Esc overlay).** A list on the left with two tabs and the selected row's details on the right, split by a draggable divider; narrower than the width at which the settings tabs use two columns, the list stacks above the details (the divider between them, the restart notice on a line of its own). *Mods*: per mod a grip, the enable checkbox, its name (the `mod.ini` Name, else the folder) with a cog when it has a `mod.ini` that sets or names features and a warning sign with its issue count, and the *Load on* combo (green while it loads in the current art mode; game data shows `All`, fixed). ## 5. Voices (field layout + battle lines)

Voice lines are MP3 files in a mod folder's `voices` folder, played when a dialogue page is shown. The field layout is described in 5.1, so existing voice packs in that layout work unchanged. The battle layout (5.2) is OpenCross's own. With `[Game] DialogueLog` on, a logged line keeps the paths (below `voices`) of the files its pages played, and the log window plays them again on confirm, looked up afresh in the enabled mods (`rules/menus.md` 17.7).

### 5.1 Field dialogue

```
<GameDir>\mods\<pack>\voices\<scene>\<dialog>-<page>-<character>.mp3        e.g.  voices\123\5-0-serge.mp3
<GameDir>\mods\voices\<scene>\<dialog>-<page>-<character>.mp3                shared location (the folder `voices` is itself a "mod")
```

| field | meaning | OpenCross value |
|---|---|---|
| `scene` | the **lang.dat room id** (row index of `tools/py/data/text_room_ids.csv`, 0..565; the field map id, +1000 in the `fin_` variants; a room a mod adds uses its map id) | `FieldWorld::room_id_` |
| `dialog` | the **message index inside the room** (the E0 / E3 / E4 word operand = message block record index) | the `message` argument of `FieldWorld::open_dialogue` |
| `page` | 0-based `{bpage}` page; a line is requested when a page is shown (page 0 when the window opens) | `DialogueBox::page_index()` |
| `character` | lowercase name of the **speaker character id** (the id the script gives the window; E3 / E4 = the speaking entity's character). Names come from a 83-entry table: 0 `serge`, 1 `kid`, 2 `guile` ... 19 `glenn` ... 43-48 `pip`, 49 `lynx` ... 82 `orcha`; speaker 0 / none is named `npc` | `ents_[speaker].char_id` of the E3 / E4 entity (`voice_char_name`) |

Reading chosen so that existing packs work unchanged:

* Speaker id 0 is `npc` in existing packs, yet their examples name `serge`. OpenCross tries **in order**: `npc` for speaker id 0 or none, else the table name; then `serge` for id 0; then the character named by the line's own `{NAME%}` tag. The first existing file wins.
* A speaker id past the table (>= 83) is written as the number.
* **E0 lines (no speaker) use the previous speaker.** After the names above, OpenCross tries the **previous speaker of the same room**: `VoicePlayer` keeps the last window speaker id > 0 per lang.dat room (`FieldVoiceNames`, reset when the room id changes; a room's first E0 line has none). Test: `test_voice`.
* **`fin_` rooms.** `scene` is the lang.dat room id, which for the ending rooms is 1000 + the map id (`fin_06` = 1459 ... `fin_14` = 1544; see the csv). `FieldWorld::room_id_` (`import::room_id_from_name`) already is that id for every `fin_*` room, so `voices\1459\...` resolves as is. `fin_19` is listed under two ids (501 = its slot in the disc-1 list, 1501 = the ending id); it always reads text and voices as scene 501 + 1000 = 1501, so its voice scene candidates are `1501` first, then `501` (`field_voice_scenes`).
* Existing packs cover only the base text (no per-speaker variants: EN / JP); OpenCross plays for every language.

### 5.2 Battle dialogue (OpenCross)

```
<GameDir>\mods\<pack>\voices\battle\<battle id>\<msg>-<page>-<unit>.mp3        e.g.  voices\battle\7\2-0-serge.mp3
```

* `battle id` = the **scene id** of the battle (`evt<id>.pac`; `BattleView::scene_id_`). RDE reads `btel_<lang>.csv` rows through a remap (`btel_battle_id` in `battle_view_script.cpp`, for example 4 -> 0x199); the voice name uses the **un-remapped** scene id, so a pack follows the battle, not the table row.
* `msg` = the message index of the script op E0 (`ScriptMsgReq::msg`, the key of the btel table). `page` = 0-based `{bpage}` page.
* `unit` = the name of the unit whose entity script issued the E0 op (`ScriptMsgReq::unit`; a scene-level issuer falls back to the first PC), lowercase, with spaces and the characters `\ / : * ? " < > |` removed (`Dead Ahead` -> `deadahead`). That entity is not necessarily the speaker (evt386's message 0 is issued by Serge's entity slot but is Radius' line; the PS1 battle window has no speaker), so the lookup tries the unit form first and then the speaker-less `<msg>-<page>.mp3` (`voices\battle\386\0-0.mp3`). Packs should use the speaker-less form unless the unit matters.
* Played when the window shows a page (page 0 when it opens), stopped when the window closes or a new line starts.

### 5.3 Lookup, formats, settings

* The player searches the **enabled mods in priority order** ("Load on" is ignored: voices are not art): for each, `<mod>\voices\<scene>\...` and, for a mod folder literally called `voices`, `<mod>\<scene>\...`; a packed mod's lines are found by name in its list and decoded from memory. The first existing file wins. Files below `voices` are not archive members: the Mods tab counts a pack's `voices\**\*.mp3` (and every `.mp3` of a mod folder called `voices`) as voice files (`Mod::voices`, *voice lines* in its details), not as "unmatched". Other files below `voices`, and `.mp3` files elsewhere (the player looks only at `<mod>\voices`), stay "unmatched".
* **MP3 only** (any bit rate / sample rate, mono or stereo; decoded to 48 kHz stereo) through Windows Media Foundation, on a worker thread, the whole line before it starts.
* A page plays when it is first shown; a new page or line stops the previous one; closing the window stops it. A missing file is logged once per path at debug level (`voice: not found voices/<path>`).
* `opencross.ini`: `[Audio] Voices=1` (default on) and `[Audio] VoiceVolume=100` (0..100, the voice bus gain; Master applies too). Both are rows of the Esc General tab, Audio section. The voice bus is described in `docs/formats/audio.md`.

## 6. Textures: what can be replaced

Loose-file mods replace archive *members* (sections 1-2). Many textures are not members: they are decoded out of containers and VRAM images (a battle stage's atlases come from `battle/bg/bg_NN.prd` + `.ctd` by colour mode and CLUT row; the title backdrop from `title.ltd`; effect sprite sheets from the effect packs). `src/render/texture_registry.*` names each of these with a **canonical path** and offers two hooks that every upload site calls: `dump(key, image)` and `replace(key, image)`.

Replacement is always on (a texture mod is switched by its own row in the list) and nothing is dumped while playing. An *active* mod (enabled, Load on matches the art mode, priority = list order, like member files) that contains `textures\<canonical path>` has that PNG decoded (libspng; other formats stb_image; any size) and used instead of the original. Decoded replacements are kept in memory, most recently used first, up to 2 GiB: a file used again (the same tile in the next room, a field character's art) is not read or decoded again. An entry is keyed by the mod file, its archive member and the file's write time, so a rewritten PNG is decoded afresh; entries outlive mod overlay changes, so switching back to Modded finds the images already decoded. The Mods tab's *Textures* button opens a popover with "This session: N dumped, M replaced" and the dump (section 7).

### 6.1 Folder layout (canonical paths; lower case, `/`)

Two naming rules. **Path-named**: the texture is cut from one member file, so its member / group id is in the path. **Content-named**: the texture is cut from a per-scene VRAM page and repeats across scenes, so it is named by an 8-hex-digit FNV-1a tag (`hash8`) of its size + RGBA pixels: identical images are ONE file (bulk dumps stay small) and a replacement applies everywhere the image is used.

| Category (first folder) | Source | Path | Naming |
|---|---|---|---|
| `battle_stage` | the tile library of `battle/bg/bg_NN.prd` + `.ctd` (section 6.2): one PNG per distinct texel rect the stage's faces sample | `battle_stage/bg_NN/tile_<NN>_<hash8>.png` | path + content hash |
| `title` | the title scene (`title.prd` + `title.ltd`), same tile library | `title/tile_<NN>_<hash8>.png` | path + content hash |
| `tiles` | **global tile replacements** only (never dumped): `tiles/<hash8>.png` replaces that tile in EVERY stage / title / room mesh / effect mesh that uses it | `tiles/<hash8>.png` | content |
| `effects` | effect sprite sheets (frames stacked vertically in one atlas, width = widest sprite): battle packs, the particle library, battle.prd's resident packs and every room's `.prd` sheets | `effects/<sheet name>/<tag>.png` | content (per sheet name) |

The `yamaneko` models (`battle/player/yamaneko`, `battle/monster/yamaneko`), which have no status-screen TIM, dump no main texture or eye strip: in the Modded art mode they draw from `sel_yama`'s character textures (legacy `yamaneko` files still load where a mod has none of `sel_yama`'s); in the original art mode the battle players draw their 1x disc battle texture (128 x 256).

* `model/...`, `room_model/...` and `effect_model/...` files are plain cut-outs (alpha 0 / 255). The PS1 semi-transparency bit (STP) of each texel lives in the decoded texture's alpha in the game (`kStpAlpha` in `src/import/tim.h`) and is NOT in the file: a replacement's alpha is coverage only (< 128 = transparent), and each covered texel takes the STP of the original (`render::model_restore_stp`: the original's flag when all its texels share it, else the flag of the original texel under it). Room-model and effect-model names still hash the decoded pixels, STP included.
* **Not covered:** whole `.tim` / `.png` / `.chip2` members (replace them by member path), room layers (composed per frame from `chip2` / PS1 tile sheets: replace the `.chip2`), the actor shadow blob (`systim.bin`), fonts and UI sheets, the encounter-effect meshes, the status-menu model in the original art mode (HD art is covered), and in battle effects the packets a hand-written effect draws straight from a window of the pack's VRAM (`FxPrim::TexSrc::Vram`: scrolling and copied pages, the env-map page) or from the stage's env page.
* **Effect models.** The tiles are cut from the pages as the pack loads them. An effect that copies art into a model's page while it plays (the eye frames of the last boss's death) changes those tiles: the page is cut again, and a tile whose pixels changed is looked up under its new name. A pack model that is a copy of a battle unit drawn with that unit's cdrom2 mesh and texture (HD and Modded art: the figure of Serge's flying tech) is not tiled there; it follows the unit's character texture. Its dumped tiles are the original art's page and apply in the original art mode.
* `model/...` is dumped from RDE's HD file set (cdrom2 first), the art the game shows by default, so a path never holds two versions. The room dump imports every room's `.bin` / `.ctd` / `.prd` headlessly (`import::load_room`) with the HD file set only (cdrom2 holds every room; its `.ctd` pages and models differ from the disc's): it holds what the Modded art mode draws.

### 6.2 Tiles (battle stages, title, room meshes, effect meshes)

The PS1 scenes sample (colour mode, CLUT) atlases of a VRAM area: one stage is about 7 images that are all the squares of the scene glued together with the same art repeated, which is hopeless to repaint. The importer therefore cuts them into **tiles** (`render::bake_object_textures`, `src/render/stage_tiles.*`, pure CPU, run by the loaders and by the headless dump), and the tile is what you dump and replace:

1. **Collect.** Every face's texel rect (its corners' u / v bounds, in the atlas of its colour mode + CLUT) is collected stage-wide. Rects that **overlap** are merged; rects that merely touch are NOT (neighbouring squares stay separate tiles). A part drawn by a UV-scroll emitter (op 36) contributes its **texture window** (off_u, off_v, win_w, win_h of the op; the GPU wraps every texel of the mesh inside it, so it is the only art the mesh can show, e.g. bg_00's sea shimmer `nea7`); a window of 0 means the whole 256 x 256 page. The window's tile is the image the scroll slides over.
2. **Cut.** Each rect is cut from its atlas **already decoded through its own CLUT**: a plain RGBA PNG, no palette, colour 0 = alpha 0.
3. **De-duplicate.** Tiles whose decoded pixels are *exactly* equal (size + RGBA incl. alpha, FNV-1a `hash8`) are ONE tile. Only exact duplicates merge: the same art through another CLUT, or shifted / cropped by one pixel, is a different tile.
4. **Name.** `tile_<NN>_<hash8>.png`: NN = first-use order in the stage (objects in drp order) for browsing, `hash8` = the content hash, so an identical tile has the same hash in every stage that uses it. No manifest is written. Only meshes the stage's emitters actually spawn contribute tiles. Room meshes and effect meshes use `room_mesh/tile_<hash8>.png` and `effect_mesh/tile_<hash8>.png` only.
5. **Draw.** Every object (part) still samples ONE texture: its tiles shelf-packed (power-of-two width) with a 1-texel edge-extended gutter, UVs remapped (`StageSubMesh::object_texture`), one descriptor set per object. A vertex used from two atlases is duplicated at the end of the part's vertex list. A morph (op-37 pair) is drawn only when base and target have the same vertex count, so a duplicate appended to one side would silently turn the morph off; in the shipped data the bake duplicates no vertex in any part of any stage or the title (no face shares a vertex between two atlases), and `test_texture_registry` fails if a data or bake change breaks that. The raw atlases stay for the effect polygons. The picture is the raw atlases' picture (see *Texel-exact nearest sampling* below).
6. **Transparency is unchanged.** Colour 0 stays alpha 0 (cut out; the bilinear bleed runs on the object image), everything else is opaque; semi-transparency stays per packet / sub-mesh (`StageSubMesh::semi` + the tpage ABR).

**Replacement** (at load, `apply_tile_textures`, any size). The first match wins in this order: `mods/<mod>/textures/battle_stage/bg_05/tile_*_<hash8>.png` (matched by the hash only; the order number may differ or be dropped, and the file may be renamed freely as long as it ends with `<hash8>.png` after the `tile_` prefix), then the global `mods/<mod>/textures/tiles/<hash8>.png`, which replaces the tile in every stage / title / room mesh / effect mesh. An object that contains a replaced tile is **re-composed at the largest scale among its tiles** (replacement size / tile size; un-replaced tiles count 1x and are enlarged nearest-neighbour), and UVs follow (normalised; `uv_scale` = texel size at the new scale). Nothing replaced = the original look. A re-composed part also gets seam strips (`StagePart::seams`, `render::build_tile_seams`): tiles upscaled one by one disagree along shared mesh edges, so with `[Enhancements] EdgeBlend` the stage pipeline cross-fades the two faces along each such edge on screen.

**Texel-exact nearest sampling.** With nearest sampling (`[Video] Filter=nearest` in the game, `ocbattleview --orig`; the room meshes always) a baked face shows exactly the texels it shows from the raw atlas: the two draws are bit-identical. A normalised coordinate interpolated on the object image and one interpolated on the atlas round differently, and stage geometry puts many pixel centres exactly on a texel boundary, where that rounding picks the texel (on an atlas whose width is not a power of two, such as the 1152-texel battle atlases, even the atlas draw decided those pixels by rounding noise). The draw therefore never rounds a normalised coordinate: the fragment shader takes the **packet texel coordinate** (`StageVertex::uv_raw` plus the scroll phase, wrapped inside the op-36 window for a scrolled object; the bake and the re-compose never change it, so it interpolates alike in both draws), picks texel `floor(t + 1/2)` and reads it from the bound image at `page origin + texel * texel size` (`uv - uv_raw * uv_scale` and `uv_scale`, constant over a face). A pixel exactly on a boundary takes the higher texel. On an image larger than the original (a replaced tile, a whole-atlas file) the sample point is the fragment's own place inside that texel, kept half an image pixel away from the texel's edges, so a 4x replacement shows its 4 x 4 pixels per texel and never a neighbouring texel. `StagePipeline` does this in `stage.frag` (scroll flag 4, set by every nearest draw: stage instances, the ground cells, morphs, objects drawn from the atlases, effect polygons through `tile_lookup`); the room meshes go through `ParticleBatch::set_texels` (`RoomMeshTri::texel_u / texel_v / texels`, `particle.frag`). Not texel-picked, and unchanged: every bilinear draw (HD and Modded art, `Filter=bilinear`), the `EdgeBlend` seam strips, sub-meshes that show a copy of the picture, untextured faces.

**Threaded loading.** A battle stage's decode, tile bake, tile replacements (PNG decode, several tiles at once through `parallel_for`), transparent-texel bleed and texture upload run on a worker thread (`StageScene::prepare`, `prepare_stage_textures`); the staged battle load reports `Wait` until it finishes, so a large texture mod does not stall frames. Uploads off the render thread go through one persistent 32 MiB staging buffer (`GpuContext::band_staging`).

**Overlay cells and effect polygons** (`effects::FxGroundPrim` / `StagePrim`, drawn by `StagePipeline::draw_prims`) address the raw atlases with PS1 packet texels. Each corner texel is located through `StageAsset::tile_map` (`render::tile_lookup`: atlas texel -> merged rect -> tile -> the first object texture holding it -> composed texel at its current scale) and the packet is drawn from that object texture, so a spell's cracks and patches show the replaced tiles exactly like the normal ground. A packet whose corners do not lie in one rect that stage faces sample keeps the raw atlas (logged once per power of two: "effect polygon(s) sample texels no stage face uses").

**Effect meshes** (`effect_mesh`). A battle effect pack's own type-0x02 meshes and the resident `battle.prd` ones are two more baked assets, under one content-named group, so one pack is a handful of files (Golem's summon: 14 tiles, its trees, hill, leaves and ground apart) and a tile shared by packs is one file. `game::bake_fx_pack_meshes` / `bake_fx_resident_meshes` (`src/game/battle/fx_mesh_tiles.*`) run the bake with `render::TileUses`, because the emitters that draw these meshes are not in the mesh asset:

* **Every part is baked**, whether an emitter names it or not (the hand-written effects spawn meshes by name).
* **Scroll windows.** The op-36 windows come from the emitter definitions that can name the mesh while the pack plays (op 05 with sprite type 14 or 19 and an op 36 in the same emitter): the pack's own, the resident packs' and the particle library's; for the resident meshes the resident packs' and the library's. A scrolled part gets ONE rect per texture page: the bounds of its faces' texels and of every such window, so the same tile serves the part drawn through any of them and drawn without a scroll. An object scrolled through a window the bake was not told of (an element pack's emitter on a resident mesh) is drawn from the raw atlases with the UVs it had there (`render::tiles_hold_window`, `StageInstance::atlas`, `StageObjectTexture::atlas_uv`), after the other instances of its draw call, like a morphing object; a tile replacement does not reach it, a whole-atlas file does. No shipped pack needs this.
* **Direct-colour sub-meshes** (a 15-bit page: they show a copy of the picture, not texels) stay on their atlas and are not tiles.
* **A page that reaches past the pack's VRAM area** (seven packs, most of them meshes a ground effect redraws): the rect reaches off the atlas and its tile holds what the sampler shows there, the atlas's edge texels repeated, so the face keeps its picture.
* **Draw order.** Opaque runs filed at one depth keep the order they had on the atlases (`StageMesh::Sub::order`), which decides which of two faces at the same depth shows. The same holds for every baked asset (battle stage, title).
* **Morphs.** No part of any pack gets a duplicated vertex, so every op-37 pair keeps its vertex count; `test_texture_registry` bakes every pack and fails on a broken pair, on a triangle that shows other texels than before, and on tile names that change between two bakes.
* **When.** The resident meshes are baked at the battle load, a pack's at its first cast of the battle (`BattleView::fx_gpu_resident` / `fx_gpu_step`, one step of the pack build per frame of the charge, `battle_effects.md` section 9), on the render thread; the baked asset stays with the pack in `BattleFxLibrary`. A pack's bake takes 2 to 6 ms in a Release build. The atlases of a baked pack are uploaded only for the sub-meshes left on them and when an object is first drawn from them (`StageAsset::atlases_on_demand`, `StagePipeline::load_atlases`), so the meshes of a pack reach the GPU about as fast as the atlases did or faster.
* **Whole-atlas files.** Before the tiles, an effect mesh texture was replaced as the whole atlas, `effect_mesh/<hash8>.png` (the pack's VRAM strip through one CLUT). Such a file still works: a tile with no file of its own is cut from the replacement of the atlas it comes from, at that image's scale (`apply_tile_textures` with `atlas_files`), and the atlas is uploaded replaced for the objects drawn from it. A tile's own file wins. The dump writes the atlases only with `--raw`.
* **The picture without a mod.** With nearest sampling it is the raw atlases' picture, pixel for pixel (*Texel-exact nearest sampling* above). With the bilinear filter a face's edge no longer blends with the unrelated art next to it in the atlas.
* `OC_NO_BAKE` skips the bake itself (`render::bake_object_textures` returns at once), so the battle stage, the effect meshes, the title and the room meshes are all drawn from the raw atlases: the reference picture of a before / after comparison.

Names in code: `render::tile_path` / `dump_tiles` (stage tiles), `render::stage_group_key` (the whole-atlas names of the content-named groups: the effect meshes' older files), `render::raw_atlas_key` (`--raw`), `render::model_texture_key` (`ModelAsset::source` = the member stem, or `@room_model` / `@effect_model` for the tiled models: `render::model_tiles`, `dump_model_tiles`, `resolve_model_tiles`), `game::fx_pack_models` (an effect pack's models without a GPU), `effects::effect_sheet_key`.

### 6.3 Replacement rules

* The PNG may have **any size**. Tiles and effect sheets are sampled with normalised UVs, so a 2x / 4x upscale of the dumped file lines up with no other change (keep the aspect ratio and layout; for effect sheets the frames are stacked, so scale the whole sheet uniformly). Different proportions are simply stretched.
* Transparent texels (alpha 0) get the colour of their opaque neighbours at upload (the bilinear-fringe bleed that the originals get).
* The mod file is found by its path below a `textures` folder whose next component is a category (`battle_stage`, `title`, `tiles`, `effects`, `effect_mesh`, `effect_model`, `room_mesh`, `room_model`, `model`); any wrapper folder above `textures` is ignored, the match is case-insensitive. Other files below a `textures` folder are resolved as archive members. Textures count in the mod's details (*textures*; voice files as *voice lines*) and take part in conflicts (the first enabled mod wins a path, like members).

### 6.4 Live rebuild

`apply_art_mode` rebuilds the overlay (a Mods tab toggle, priority or Load-on edit, or an art-mode switch that changes the overlay, changes `Vfs::generation()`), and field room art / models and battle unit models follow immediately (`set_art_mode(hd, force)`). Models (`model`, `room_model`) follow that forced rebuild (`MeshPipeline::create_model` consults the registry). **Effect models follow at the pack's next cast:** the forced rebuild drops the GPU copy of every effect pack that has them (`BattleView::FxGpu::art_dependent`) except the pack playing at that moment, which keeps its copy to its end, and `fx_load_models` cuts, replaces (`render::resolve_model_tiles`) and uploads again when the pack is cast next. The PNG decode and the page composition run at that load, on the thread that starts the cast, like the effect sheets'; decoded images stay in the cache of section 6.

**Tiles follow the same trigger without a reload.** The scenes that draw baked tiles (the running battle's `StageScene`, its effect packs' and resident meshes through `BattleView::fx_apply_mesh_tiles`, the `TitleBackdrop`, the field's `RoomMeshes`) poll `texture_registry::generation()` once per frame. When it changed they re-run `apply_tile_textures`, which recomposes every object image from the **pristine tiles** (`StageObjectTexture::base_slots` / `base_uv`; never from the previously composed image, so nothing accumulates and switching a mod off restores the original image, slots and UVs bit for bit), then re-uploads (`StagePipeline::reload_textures`, or `RoomMeshes::refresh_tiles`). The old GPU textures, sets and buffer are retired by idling the device first: a one-frame hitch at the toggle, no scene reload. The title's manta ray and turtle follow the same poll: `TitleBackdrop::reload_model_textures` drops their replacement images, resolves them again from the models' own pages and rebuilds their GPU copies; their motion lives in the emitter objects, so the swim carries on.

## 7. Dumping textures

**Dump all textures** (button in the Mods tab, the main way) runs the full headless dump (`src/game/battle/texture_dump.*`, the same code as `occ dump-textures all`) on a **worker thread** into `<GameDir>\dump\textures\`. It never touches Vulkan (only decoded images), runs at below-normal priority, and reads the shipped archives through its own VFS (no mods applied, so it always dumps originals). The tab shows a Cancel button, a progress bar and "<phase> n / total, F files" (phases: battle stages, title backdrop, effect packs, rooms, models, weapons); a one-line summary (files per phase, skipped items, seconds) is shown when it ends and written to the log ("texture dump done: ...").

**Category checkboxes** next to the button (`[Mods] DumpStages` / `DumpTitle` / `DumpRooms` / `DumpModels` / `DumpWeapons` / `DumpEffects`; defaults 1 / 1 / 1 / 1 / 1 / **0**): *Battle stages* (3D battle scenes), *Title* (the title scene), *Rooms (3D meshes + models)* (`room_mesh`, `room_model`), *Models* (battle / field unit models, `model`), *Weapons* (every part of every `battle/wepon/*.bin` pack), *Effects (sheets + meshes)* (`effects`, `effect_mesh`, `effect_model`: the sprite sheets, the mesh tiles and the summon and tech models of the effect packs; off by default). The button writes only the checked ones (disabled when none is). Changing a box saves the ini but rebuilds nothing. *Models at 1x* (`[Mods] DumpModelSource`, default 0; only with *Models*) writes every model texture that is dumped as RDE's 4x image (the character textures, 6.1.1, and the field characters' `clut0`) at its 1x size instead: the HD file set's own 1x page and eye strip, the pixel art RDE's 4x images were upscaled from, in the layout the HD meshes use (not the disc's page, whose atlas differs). The names are the same, so an upscale of them goes into a mod as it is; a replacement may be any size. Room effect sheets belong to Effects, so with only *Effects* checked the room pass still loads every room but writes just the sheets.

**Dev tool (no game):**

```
opencross occ [-g <GameDir>] dump-textures [stages|title|effects|rooms|models|weapons|all] [--raw] [--source] [--packs TEXT] <outdir>
```

The same job, blocking, into `<outdir>`; the names are the checkboxes (none named = all); it prints progress every 5 s, then per-phase file counts and the time. `--raw` additionally writes the raw (mode, CLUT) atlases of stages / title / room meshes / effect meshes under `raw/...` (debugging; `raw` is not a replaceable category; the content-named groups' atlases are `raw/room_mesh/<hash8>.png` and `raw/effect_mesh/<hash8>.png`). `--packs TEXT` dumps only the battle effect packs whose file path contains TEXT (`golem.prd`, `syoukan`); at debug level the log names every pack's mesh tiles and model tiles.

**Modder's workflow.** Tick *Battle stages* / *Title* / *Rooms* and press **Dump all textures**. Open `dump\textures\battle_stage\bg_05\`, find the tile by eye, paint it in any editor (alpha 0 = see-through; keep the layout; any scale factor, same aspect) and save it as `mods\<mod>\textures\battle_stage\bg_05\tile_<NN>_<hash8>.png` (or `textures\tiles\<hash8>.png` to change it everywhere). Enable the mod (Load on Modded / All) and toggle it in the Mods tab: a running battle, the title or the room picks it up at once (6.4). An effect works the same way: tick *Effects*, or run `occ dump-textures --packs golem.prd <outdir>` for one pack, and save the painted tile as `mods\<mod>\textures\effect_mesh\tile_<hash8>.png`. Copy a dumped tree, or part of it, into `mods\<mod name>\textures\...`.

### 7.1 Exporting models (glTF)

**Export all models** (button in the same Textures popover, under *Dump all textures*) writes every model as glTF 2.0 binary (`.glb`) into `<GameDir>\dump\models\` on a worker thread (`src/game/model_export.*`, the same code as `occ export-models`, `docs/tools.md`). Like the texture dump it reads the shipped archives through its own VFS (no mods applied) and runs at below-normal priority; the popover shows Cancel, a progress bar and "<art> models n / total, F files", then a one-line summary (files, MB, items skipped, seconds; also in the log as "model export done: ..."). It writes both art sets:

| Folder | Meshes and textures |
|---|---|
| `classic\` | the disc's models (`cdrom/`), textured with their decoded PS1 pages |
| `hd\` | the HD file set (`cdrom2/` first, model.md section 12) with RDE's 4x images where the model has one (field players' `hd/` TIMs, the battle players' Status-screen TIM, the menu models' TIM); other textures are the HD set's 1x pages |

Under each, a file per model at `<member stem>.glb`: `fieldobj/player/<dir>/<name>.glb` (field models: internal clips and their `fieldobj/ex` pack), `battle/player/<dir>/<name>.glb` and `battle/monster/<dir>/<name>.glb` (internal clips and `at0.prd`), `menu/player/<name>.glb` (Status-screen models with their own clips; the battle model's clips fit the same skeleton) and `battle/wepon/<pack>/part<n>.glb` (every part of every weapon pack, monsters' included). A full export writes 858 files (429 per set: 56 field, 52 battle player, 148 monster and 51 Status-screen models, 122 weapon parts), about 290 MB (`classic\` 100 MB, `hd\` 190 MB; a model 0.1 to 1.3 MB), in about three minutes on a Debug build.

**Layout** (the names are stable, so a file maps back onto the game's skeleton and clips):

- **Axes and units.** The scene's first node `root` turns model space (+y down) into glTF's (+y up) with a half turn about x, and scales by 0.001 (a battle character about 1.1 m, a field one about 2.1 m). Everything below it is in model units.
- **Joints.** `joint_00` ... in skeleton order, parented as in S2 (model.md section 4), each with the model's rest rotation (the quaternion of `Rz * Ry * Rx`) and rest translation; `extras.bone` = the real bone number. The used attach points are empty child nodes `attach_<kk>` of their joints (model.md section 5, `kk` = the attach index); the used weapon mounts are `mount_0` / `mount_1` (attach point position + the record's offset, its ZYX rotation). A weapon file's `mesh_00` re-parented onto a character's `mount_0` sits where the game draws it.
- **Meshes.** One node `mesh_<nn>` per construct (`nn` = construct index = shading entry), mesh `construct_<nn>` with `extras.shading` = the entry's `[r, g, b, flags]`, one primitive per material run. Skinned constructs are scene-root nodes with skin `skeleton`, whose joint list is every joint node in order (so `JOINTS_0` values are the model's joint numbers) and whose inverse bind matrices are the inverse of `root` times each joint's rest transform; their positions and normals are the rest pose in glTF space. Each vertex keeps its one or two joints with their weights (`JOINTS_0` / `WEIGHTS_0`; 16-byte vertices have two). The game holds a local position per joint where glTF has one bind position: a one-joint vertex poses exactly as in the game, a two-joint vertex moves up to about 3 model units away from the game's position, under 1 in most models (the two records of a 16-byte vertex give rest positions that differ by that much). Weapon meshes are rigid: child nodes of `root`, positions in model units.
- **Faces.** Triangles, quads split as in the engine (model.md section 3.3), wound so that the side the game draws is glTF's front face (counter-clockwise); one-sided. `NORMAL` is the VDDM normal turned by its joint's rest rotation (weapons: the importer's built normals). `TEXCOORD_0` is the engine's UVs (origin top left). `COLOR_0` only where corners carry a packet colour other than the neutral 0x80 (weapon meshes), stored as `min(255, 2 x colour)` so 0x80 is 1.0. A primitive with split quads lists them in `extras.quads`: the numbers of its triangles that are a quad's first half (the next triangle is the second).
- **Materials.** `KHR_materials_unlit` (the models are drawn flat), metallic 0, roughness 1. Textured: `baseColorTexture`, `alphaMode` MASK at 0.5 (colour 0x0000 is transparent); a semi-transparent construct (shading flag bit 1): BLEND with alpha 0.5 and `extras.blend` = `average`, `add`, `subtract` or `add_quarter` (its ABR 0..3). Images are embedded PNGs, one per texture the faces use (`clut<k>` = CLUT row k), with the STP bit dropped as in the texture dump (alpha 0 or 255). Samplers: nearest in `classic\`, linear in `hd\`, clamped. The closed-eye strip is not exported.
- **Animations.** One per clip, named `clip_<xx>` with `xx` the hex id the game's scripts start it with: internal (S4) clip k has id k (`clip_0a` = clip 10), external clip k (`at0.prd`, `fieldobj/ex`) id 0x80 + k (`clip_83` = at0 clip 3); `extras` = `clip` (the id), `source` (`s4`, `at0`, `ex`), `index`, `frames`. Keyframe k is at k / 15 s (`asset.extras.keyframes_per_second`). Rotations are one quaternion per keyframe; a step of more than 60 degrees on any axis gets extra samples between, interpolated per axis as the engine does (model.md section 6.3: the long way round between 180 and 270 degrees), so quaternion interpolation follows the game. Translations are linear. A joint the clip holds still has one STEP key, or no channel when that is its rest pose. A pack entry made for another joint count (an empty clip) is left out. The game wraps a looping clip from its last keyframe to its first; a glTF clip ends at its last keyframe.
- `asset.extras`: `kind` (`field`, `battle`, `weapon`), `source` (the member stem), `art` (`classic` / `hd`).

### 7.2 Replacing models (glTF)

A mod replaces one model with a glTF binary at the path the export writes it to (7.1), under a `models` folder:

```
<GameDir>\mods\<mod>\[<wrapper>\]models\<classic|hd>\<member stem>.glb
```

`hd\` files are used when the model is read with the HD file set (art modes HD and Modded), `classic\` files in the original art; the member stems are the export's: `fieldobj\player\<dir>\<name>.glb` (a field model), `battle\player\<dir>\<name>.glb` and `battle\monster\<dir>\<name>.glb` (a battle model, party or enemy), `menu\player\<name>.glb` (a Status-screen model, which the HD models in fields also draw); one file for all three uses of a character is `character\<name>.glb` (7.3). Weapon part files are not read. Names match in any case. A `models` file follows the mod's *Load on* (Modded by default) and its priority like any other mod file (sections 3 and 4): the first enabled mod in the list that loads in the current art mode wins a model, and a model replaced by a mod above counts among the lower mod's conflicts. The Mods tab's details count a mod's models; the startup log adds `M model(s)` to each mod's line and to `mods: K active mod(s), ...`.

**The model keeps its skeleton.** The game's own clips drive the replacement (the file's animations are not read), and everything the game reads from the model besides its meshes and textures stays the original's: the skeleton, clips and animation sequences, attach points and weapon mounts (`attach_NN`, `mount_N`), the shading entries (a construct's part flags, which scripts show and hide), the extent the effects scale by, and everything the scripts, collision and the floor shadow use. The joints are matched by node name, `joint_00` ... one per joint of the model's skeleton; other nodes (the export's `root`, `attach_NN`, `mount_N`, a modeller's armature object) are free. A file is **refused**, and the model drawn as shipped, when a joint is missing (`joint_05 is missing (the model has 22 joints)`), the file has one the model does not (`joint_30 is not a joint of the model (it has joint_00 to joint_21)`), two nodes have the same joint name, a joint hangs under another joint than the model's parent (its nearest `joint_NN` ancestor; `joint_02 hangs under joint_00, the model's under joint_01`), a skin lists a node that is not a `joint_NN`, a construct number is 16 or more, an image cannot be decoded, or the file is not a readable GLB with triangles. The reason goes to the log (`model mod: <file> not used for <stem>: <reason>`) and to the mod's *Issues* in the Mods tab (`N model(s) not used`, each `<path in the mod>: not used, <reason>`) until the next *Rescan*; a used file logs `model mod: <file> replaces <stem> (<art>): V vertices, T triangles, I image(s)`.

**What is read.**

- **Shape.** Every node with a mesh. A skinned node (`skin`) is posed in the file's rest pose: each vertex by its `JOINTS_0` / `WEIGHTS_0` (and `_1`) with the skin's joints (their node transforms down from the scene root) and inverse bind matrices; a node without a skin rides its nearest `joint_NN` ancestor (joint 0 when it has none). The result is turned back into model space by the export's convention (`root`'s half turn and 0.001 scale undone, whatever the file's own root holds), so the replacement is drawn at rest exactly as the file shows it at rest: moving or scaling a joint node of the file without rebinding moves or scales the vertices it carries. The engine skins a vertex with at most two joints (model.md section 4): a vertex with three or four keeps its two heaviest, in the file's order, with their weights renormalised (the log counts them); each kept joint gets the vertex's position relative to that joint's rest transform. Primitives other than triangles are skipped.
- **Constructs.** A node named `mesh_NN` becomes construct NN (its shading entry, part flags and the scripts' part numbers are the model's construct NN); any other mesh node joins construct 0. A construct the file does not have is drawn empty. Faces keep the file's order, wound back to the engine's side; a primitive's `extras.quads` (written by the export) lists its triangles that start one of the engine's split quads, culled as a whole as the game does; without it every face is a triangle.
- **Normals.** `NORMAL` turned by the vertex's rest skinning; missing normals are the mean of the vertex's face normals. The normal is stored in the space of the joint that turns it: the second joint of a two-joint vertex (as the game's vertices have it), else the only one.
- **Textures.** A material's `baseColorTexture` image, embedded (a buffer view or a `data:` URI) or a file next to the `.glb` (a relative `uri`; inside a packed mod the member next to it), PNG or any format the texture mods read, any size. An image named as the export names them (`clut<k>`, `overlay<k>`) stands for that texture of the model: when its pixels are the exported ones it is ignored, so an unchanged file keeps the model's HD image, eye blinks and texture mods; otherwise it is drawn in place of the texture (both art sets' images), the eye blinks pasted over it, with the semi-transparency bits (STP) of the original texel under each texel as for a texture replacement (6.3). Any other image is a texture of its own. Texture mods do not apply to a replacement's images. A material without a texture draws its `baseColorFactor` colour flat. `COLOR_0` multiplies the texel like a weapon's packet colour (1.0 = 0x80).
- **Blending.** `alphaMode` `BLEND` makes the construct semi-transparent with `extras.blend` (`average`, `add`, `subtract`, `add_quarter`; `average` when absent), the first such material of the construct deciding; its texels then blend as the game's semi-transparent texels do: a named image keeps the original's STP bits (all of its opaque texels when the original has none), an image of its own has every opaque texel semi-transparent. Otherwise texels with alpha below 0.5 are transparent and the rest opaque (`MASK` and `OPAQUE` alike); samplers and the unlit / PBR factors are not read (the engine samples as it does for every model).

**Round trip.** A file exported (7.1) and put back unchanged draws as the model: faces, quads, materials and one-joint vertices are the same (`occ export-models --verify` reads every exported file back as a replacement and reports `import check` lines: vertex error under 0.001 units); a two-joint vertex moves by the export's bind-position difference (under 1 unit, the `two-joint vertex error` of the check).

### 7.3 One model for every use (glTF)

A mod can give a character one file for the Status screen, battle and the field at once, made on the character's Status-screen model's skeleton:

```
<GameDir>\mods\<mod>\[<wrapper>\]models\<classic|hd>\character\<name>.glb
```

`<name>` is the Status-screen model's file name, the export's `menu\player\<name>.glb` (`selju` for Serge, `kid`, `guill` ...; every one of the 51, Pip's forms and Serge's Lynx body included), so an exported Status-screen model, edited and saved under `character\`, is such a file. It is read exactly as a `menu\player\<name>.glb` replacement (7.2: its joints, meshes, constructs, normals, textures and blending, and the same refusals) and follows the mod's *Load on* and priority like every `models` file. Each use takes, in this order, its own file (7.2), the all-uses file, the shipped model:

| Use | Drawn with |
|---|---|
| Status screen | `menu\player\<name>.glb`, else `character\<name>.glb`, else the shipped model |
| Battle: the character's battle model (`battle\player\<dir>\<file>`, the model whose file name is `<name>`), whoever fights with it | its `battle\player\<dir>\<file>.glb`, else `character\<name>.glb` on the battle skeleton (below), else the shipped model |
| Field with the HD models in fields (`[Video] LegacyFieldModels` off, `architecture.md`) | the Status-screen model the HD models in fields draw, worn as on the Status screen (so a `menu\player` file wins here too) |
| Field with the legacy field models (`LegacyFieldModels` on) | the character's own field model: its `fieldobj\player\<dir>\<file>.glb`, else `character\<name>.glb` posed by the field model as the HD models in fields pose the Status-screen model (the same rig, size, part flags and hidden props), else the shipped model |

**Battle.** Every battle model and its Status-screen model share one skeleton (the same joints, parents and rest pose, in both art sets: `occ menu-rigs --battle`, `docs/tools.md`), so the file's joints are the battle model's own and the battle clips (internal and `at0`) drive it directly: the log says `model mod: <file> replaces battle/player/<dir>/<file> (<art>): the Status-screen model's skeleton is the battle model's`. Should a battle model's skeleton differ from its Status-screen model's (a mod replacing the shipped model files), the joints are paired as the HD models in fields pair a field model with its menu model (the same joints and parents pair joint for joint; otherwise the automatic matcher, and a joint without a partner rides its nearest paired ancestor's partner) and every vertex is bound once, at its rest place, onto its paired battle joints; when no usable pairing exists the file is not used for battle (logged and listed among the mod's issues as `not used for battle/player/<dir>/<file>, the battle model's skeleton (N joints) does not pair with the Status-screen model's (M joints)`) and the battle model is drawn as shipped. The battle model keeps everything but its meshes and textures: skeleton, clips and sequences, attach points and weapon mounts (where the weapon, thrown objects and effects are placed), the shading entries (the file's construct NN takes the battle model's entry NN, its part flags and the scripts' part numbers), the extent effects scale by, and what targeting, collision and the shadow use. It draws the textures the file gives the Status-screen model (the Status-screen model's images where the file keeps them), not the battle model's own: no eye blinks of the battle model, and texture mods of the battle model do not apply.

## 8. Engine features (`mod.ini`)

Some OpenCross features change the game's rules, so they are off in the game as shipped and a mod turns them on. A mod does that with a `mod.ini` at its root: in a folder mod `mods\<mod>\mod.ini`, in a packed mod at the top after the wrapper folder (section 1.1). The name is matched case-insensitively. A `mod.ini` deeper in the mod is an ordinary file (unmatched). A mod without one changes no feature.

```
; comments are whole lines (; or #)
[Mod]
Name=Party Swap
Version=1.0
Author=Someone
; features this mod's own field scripts use (fieldscript.md 6.12) without turning them on for the whole game
Requires=PartySwap

[PartySwap]
Enabled=1
KeepLineup=1
Reserve=3

; the room ids this mod's scripts and text use: id = file stem (cdrom/map/mapbin/<stem>.bin / .prd / .ctd)
[Rooms]
1001=flux1001
1002=flux1002
; another mod's room this mod links to (by its stem)
1500=bigmod_cave

; the element ids this mod's scripts and text use: id = record name (tables\pgdat.txt)
[Elements]
527=my_spark

; the element shop / blacksmith ids this mod's scripts open (FE 5E / FE 68): id = row name
[ElementShops]
32=hub_shop
[Smiths]
32=hub_smith
[TradingPosts]
32=bazaar

; the monster and formation ids this mod's scripts and text use (a field script starts formation n as battle 0x200 + n)
[Monsters]
222=big_boss
[Formations]
513=boss_fight

; the item ids (equipment and materials) this mod's scripts and text use (a field script gives item n as item id 0x800 + n)
[Items]
256=star_blade

; the key items this mod adds or uses (a field script gives key item n as item id 0x400 + n)
[KeyItems]
65=sky_key

; the characters this mod's scripts and text name (records it or another mod adds by name to char)
[Characters]
51=alice

; the saved variables this mod's scripts use: handle = variable name
[Variables]
0x800=run_depth
0x802=best_depth
```

* **`[Variables]`**: the saved variables this mod's field scripts use, `<handle>=<name>` (hex with `0x`, or decimal; names as for records: a lower-case letter, then lower-case letters, digits and `_`). The game's variable handles end at 0x7FE (`docs/formats/fieldscript.md` section 4), so a mod's handles are the even values 0x800 to 0xFFE: 1024 variables, read as signed 16-bit values by every op that takes a variable, and reached bit by bit by 71 / 72 / 73 (operand `handle << 4 | bit`, 0x8000..0xFFEF). **The handles are the mod's own** and **the name is the variable**: a script's handle means the variable the `[Variables]` of the running room's owner (as for `[Rooms]`) gives it; two mods naming the same variable share it, whatever handle each gives it. A handle the owner does not list reads 0 and drops writes (logged once per room). The lists are read at launch: a controlled run's `reload` keeps them. The game's variables never reach this range, and a game room nobody edits has no mod variables. Every mod variable is saved by name, as long as it is not 0 (`docs/formats/save.md` 16); a new game (and New Game+) starts them at 0. A value whose name no enabled mod has stays in the save, so a mod switched off and on again finds its values. An odd handle, one outside the range, a value that is not a name, a handle named twice and a name given two handles are problems.

* **`[Items]`**: the item ids (equipment and forge materials, records a mod adds by name to `waa` / `menu_waa`, section 1.3) this mod's scripts and text use, `<id>=<name>`. The game's items are 0..255, so ids run from 256 to 2047 (0x7FF). A field script gives, takes and counts item n with item id 0x800 + n (BB / B4 / D5, `docs/formats/fieldscript.md`), and `{itemwork}` text names it the same way; the id means the item the `[Items]` of the running room's owner gives it (as for `[Elements]`), and an unlisted id (or one naming no record) names none. A mod's item names (`text\sysmes.txt` `0x00<id>`) and descriptions (`text\waa_spec.txt` `<id x 3 + line>`) are stored under the items they name. Saves keep the names (`docs/formats/save.md` 16): RDE and the PS1 game see such an item as an empty stack or slot.
* **`[KeyItems]`**: the key items this mod adds or uses, `<id>=<name>`. A key item has no table record: its name here adds it (a name two mods give is one key item). The game's key items are 1..64, so ids run from 65 to 1023 (0x3FF); the key items mods add follow the game's 64, mod by mod in priority order, each mod's in id order. A field script gives, takes and tests key item n with item id 0x400 + n (BB / B4 / D5, `{itemwork}`), through the running room's owner as for `[Elements]`; using one in the field writes variable 0x2A = 0x400 + the owner's own id for it (0 when it lists none). The mod's key item names (`text\sysmes.txt` `0x18<id>`) and descriptions (`text\keyitem.txt` `<id x 3 + line>`) are stored under the key items they name; the menu's picture is `hd\menu\keyitem\<name>.png`. Saves keep the owned ones by name (`docs/formats/save.md` 16).
* **`[Characters]`**: the character ids this mod's scripts and text use for characters mods add by name (records of `char`, section 1.3: the other character sets `char20` and `char_w0`..`char_w5` share its names, and a set a mod's rows don't name copies the character's base there, as does its Lv 99 row), `<id>=<name>`. The game's character records are 0..50 (0..43 the playable characters, then Pip's forms and battle-only bodies), so ids run from 51 to 122 (0x7A): scripts and text name a character in 7 bits (an entity reference 0x80 + id, where 0xFB..0xFF are this entity and the party slots; a name code), so one mod names up to 72 characters and any number of mods add more. Inside the engine the added characters follow the game's records, mod by mod in priority order, with no limit. **The ids are the mod's own**: every field-script character operand (7B / 7D / 94 / 95 / 96 / 97 / E5 / E6 / E8, 0E SETUP_PC, D9 / DB, FE 36..3E, FE 4A, FE 52, FE 5D / FE 60, FE 73 / 74 / 79, FE 7C / 7D, FE CC / CD, an entity reference 0x80 + id) and, in a room a mod owns, a text name code mean the character the `[Characters]` of the running room's owner gives the id (as for `[Elements]`); an id the owner does not list names nobody, and the game's ids (and the game's rooms' text) keep their meaning. Ids written back to a script (98 / 99 / 9A, FE CD) are the owner's own ids (0xFF when it lists none). A new character starts as a copy of its base (`base=`; its model byte with it, so it looks like its base until it has art of its own; its battle model is its own when the mod ships `cdrom\battle\player\<name>\<name>.obj` with its `.ltc` and `at0.prd` beside it, worn while its model byte is its record's, so a D9 disguise still shows; the same goes for its field model `cdrom\fieldobj\player\<name>\<name>.obj` with `<name>.tim` beside it, `cdrom\fieldobj\ex\<name>.bin` and `hd\fieldobj\player\<name>\<name>.tim`, its face `hd\face\<set>\<name>.png` on the party screen and its portrait strip `hd\menu\playtim\<set>\<name>.png` in the main menu, its status-screen model `cdrom\menu\player\<name>.ome` (with `hd\menu\player\<name>.tim`), `<set>` being 2021 or 1999; its face also shows in the blacksmith's party strip, which scrolls a row with L2 / R2 once mods add characters (the speed keys or the pad's triggers, which then leave the game's speed alone), and in dialogue when it speaks as a party member or a script sets SET_DIALOG_FACE (9E) to 0x100 + its id, read as the other character operands; only files the mod adds count, so a name the game's folders already use keeps its model byte's art), recruited by the scripts like any other; its name is `text\sysmes.txt` `0x01<id>` and its status-screen profile `text\ome.txt` `<id>` (shown while it wears its own body, else its body's), both stored under the character they name (give every character its own rows: the game's names run to `0x0140`, so an added character without one can show the game's row under its engine id). The party screen grid, the roster lists and the element shop's character pick grow past the game's 44. Who can equip an item (`menu_waa`) and place an element (`menu_pg`) follows the character's `equips_like` (`char.txt`, a character id or `@char:<name>`; the first mod in the list that gives one), else its base, followed to a game character; a row's `equip_add=<character>` / `equip_remove=<character>` (repeatable, any character, the game's by number) lets that character equip or place the record or not, whatever its bits, the first mod in the list winning a character two mods name differently. These fields write no record byte, so RDE sees the game's bits. Saves keep every added character by name (`docs/formats/save.md` 16): RDE and the PS1 game see a party seat holding one as empty, and when one leads, the party's game characters moved up (Serge alone when it has none), as RDE plays no save without a leader; OpenCross reads the real seats back from the side file. A save made before a mod added a character holds nothing for it: the load gives it a new game's record at the save's star count.
* **`[Monsters]`**, **`[Formations]`**: the monster and formation ids this mod's scripts and text use, `<id>=<name>` (records a mod adds by name to `monster` / `scenedat`, section 1.3). Monster ids run from 222 to 16383; formation ids from 513 to 32255, and a field script starts formation n with battle id 0x200 + n (A3), resolved through the running room's owner as for `[Elements]`; an id in the added range the owner does not list is logged and starts the engine's formation of that number. The debug tools and a route's `request battle` use the engine's ids. A mod's monster names (`text\sysmes.txt` `0x19<id>`) and battle text rows (`text\btel_<lang>.csv`, by formation id) are stored under the records they name.
* **`[ElementShops]`**, **`[Smiths]`**, **`[TradingPosts]`**: the element shop, blacksmith and trading post ids this mod's scripts open (FE 5E / FE 68 / FE 67), `<id>=<name>` (rows a mod adds by name to `el_shop` / `waa_shop` / `trade`, section 1.3); the game's shops are rows 0..31, so ids run from 32 to 32767. As for `[Elements]`, an id means the row the running room's owner lists; the game's rows keep their numbers and an unlisted id past them opens an empty shop. The blacksmith the Smith Spirit opens (variable 0x4A) resolves the same way. A route's `request elementshop` / `weaponshop` / `trading` uses the engine's rows.
* **`[Elements]`**: the element ids this mod's scripts and text use for records mods add by name (section 1.3), `<id>=<name>`: its own and any other mod's it uses. The game's element records end at 526, so ids run from 527 to 16383 (0x3FFF). **The ids are the mod's own**: a field script's element item id (from 0x1000, `docs/formats/fieldscript.md`) means the element the `[Elements]` of the running room's owner gives it (section 8, `[Rooms]`); an id inside the element table itself (the game's, or records a whole-file `pgdat.bin` adds) is that element, and an id past it the owner does not list names none. A mod's `text\sysmes.txt` rows of its element ids (names `0x17<id>`, help lines `0x1A<id x 3 + line>`) are stored under the elements they name. Saves keep the names (`docs/formats/save.md` 16). An id outside the range, a value that is not a record name, an id named twice and a name no mod adds are problems.
* **`[Mod]`**: `Name`, `Version`, `Author` (shown in the log and the Mods tab) and `Requires`, a comma-separated list of feature sections. Any other `[Mod]` key is a problem.
* **`[Rooms]`**: the room ids this mod uses, `<id>=<stem>`: its own new rooms, and any other mod's room it links to. Every room id the game uses is below 1000, so ids run from 1000 to 32767 (0x7FFF, the largest literal room id a field script can write). The stem names the room's files under `cdrom/map/mapbin/` (no folder, no extension; matched in lower case); the room's own `.prd` is used. A mod room takes no `cdrom.fnd` record. An id outside the range, a stem with a folder or an extension, and an id named twice are problems. **The ids are the mod's own** (`src/game/mod_rooms.h`): the stem is the room's identity, and an id means the room the `[Rooms]` of the room's **owner** gives it, the owner being the mod whose `.bin` of the running room is loaded (a game room a mod edits included; a game room nobody edits knows only ids below 1000). So a map jump (5A, DC) or a room model source (FE D0) to 1001 reaches the owner's 1001; MAP_ID (variable 6) reads the room's id in its owner's list and PREVIOUS_MAP_ID (variable 8) the previous room's id in the same list (32767 when the list has none). Two mods both using 1001 for different rooms is no conflict. A room patched by another mod (its `.bin` replaced) runs that mod's ids, so a patch lists the rooms its scripts jump to too. Inside the engine each mod room has an internal id from 0x10000 (never saved, never shown to a script). OpenCross saves made in a mod room keep its stem (`.ocsav` version 2) and Continue finds the room by it; a card save keeps only the location word, read as the first mod in the list that uses that id. A listed room whose `.bin` is missing is logged (`field: mod room ...`). The debug teleport lists the mod rooms with their owner.
* **Feature sections**: every other section names a feature of the build's table (`src/core/features.cpp`; the field script's `GET_FEATURE_LEVEL` ids are the same table, `fieldscript.md` 6.12). Its keys are that feature's settings, whole numbers in the feature's range (`on` / `off`, `true` / `false`, `yes` / `no` read as 1 / 0). A feature with settings has `Enabled` first. Sections and keys compare case-insensitively; a repeated section adds to the first.
* **What the build cannot honour** is counted on the mod's row in the Mods tab (the warning sign), listed in its details (*Issues*) and written to the log (`features: '<mod>': ...`): a section or a `Requires` entry the build has no feature for (*needs a newer OpenCross*), a key the feature does not have, a value that is not a number (ignored) or out of range (clamped), and the lines the parser did not understand (*mod.ini problems*).
* **Resolution** (`features::resolve`, once at launch, in `App::init_vfs`): every feature starts at its defaults, then the enabled mods with a `mod.ini` apply their values, the first mod in the list winning each key (a key two mods set differently is logged as a conflict with the winner), then the player's `[Features]` overrides in `opencross.ini` (`<Feature>.<Setting>=<value>`, `config.md` 2.4), which win over every mod. *Load on* does not apply: features are not art. Like game data, the result stays as it is until the next launch: the Mods tab lists the features a mod sets or names in its details, and shows *Restart required* while the resolved features differ from the launch's (a switch and its undo cancel out). A scripted run (`[Debug] Script`) has no mods (unless `[Debug] ScriptMods=1`): its features are then the `[Features]` lines of the route's own ini, so a route that tests a feature turns it on there.
* **Saves.** A feature never stores anything a save without it cannot load, so a mod that turns one on can be removed at any time.
* **Field-script ops.** A mod's own scripts can query a feature (`GET_FEATURE_LEVEL`) and, for features that have them, change it at run time with their extension ops; the `mod.ini` gives the starting values.
* **Two kinds, and the Mods tab.** An **addon** works on the game as shipped (party swap, the party screen tweaks): the Mods tab's *Engine features* page offers its toggle and settings, and the player's choice wins over every mod. Where a mod sets a value the page says so ("Set by <mod>."); where the player's value replaces it, "Overriding <mod>", and a click on that drops the player's value. A **mod kit** does nothing without a mod's own scripts or data (the mod UI ops, model sources): the player cannot switch it, and the page lists it with the enabled mods that use it (set its section or name it in `Requires`); the unused ones are behind *Show unused*. A mod kit has no settings: its `mod.ini` section takes no keys (a key is an issue), and `[Features]` lines for it in `opencross.ini` do nothing (its page says so and offers to remove them). A feature with no section (the extension range itself) is not listed. Each feature's kind is the `player` flag of its row in the table (an addon has settings, a mod kit none); `about` is the page's description of it.

### 8.1 The randomizer

`game/randomizer.*` (the plan), `app/app_randomizer.cpp` (the game's reads). The Mods tab has a page of its own for it, **Randomizer**, beside the mod list and *Engine features* (which does not list it): the list pane holds the five switches, the detail pane the seed (typed, or *New seed* for a random one), the spread slider, and what the plan in force moves. Changing a switch on the page drops a stored legacy `Randomizer.Enabled` line, first storing the switches it had turned off. The values are those of any addon (a mod's `[Randomizer]`, the player's `[Features] Randomizer.<Setting>` winning), but the game follows a change at once.

* **A pure function.** Every placement is computed from `Seed`, the settings and stable ids of the game's data: a treasure's flag key (`architecture.md` 4.7), a ditem row and slot, a shop row and index, a scene. Nothing is stored in any save, so the randomizer can be switched on or off, or a save loaded, at any time: an opened chest stays opened (the game's own flag); switched off, everything not yet collected holds its own thing again, and what was received stays. The same seed and settings give the same game on every machine with the same game data (mods that change rooms or tables change the data). Changing the seed in the middle of a game can give some things twice and leave others out of reach; the page warns.
* **Pools.** Each pool is shuffled on its own and is a permutation: every thing in it still exists exactly once, so forge recipes and the record checklists keep working. `Items` moves the items of the chests and pickups, the items of the kill drops and steals, and the smiths' stock; `Elements` the elements of the chests and pickups (summons included), of the drops and steals, and the element shops' stock. Items stay items and elements stay elements. Never moved: key items, a pickup that also gives a key item (the Star Fragment, the Memento Pendant and the Chrono Cross pickups stay whole), a give whose id the room's script does not hold as a literal of its own (`script::ScanEvent::value_sites`; a literal two treasures share leaves both), the trading post, character techs. The drop and steal pools hold the rows some enemy record rolls on.
* **Balance** (`Spread`). An entry's rank is the mean of its value percentile (the price, `menu_waa` for items and `menu_pg` for elements, times the copies a give adds) and its stage percentile; with one of the two unknown the other alone, with neither the entry keeps its thing unless `Spread` is 100. A stage is an area's: the percentile of the mean max HP of its own normal encounters' enemies among the areas with encounters, or, for an area without them, the percentile of the lowest story value its rooms set (story anchors alone mislead: a place revisited late sets a late value). An area is a room prefix and its world letter (`alu_a`). With `Spread` below 100 a thing moves less than a window of 4 % + 0.96 % x `Spread` of the ranked entries away from its rank (`Spread` 0: about the 4 % of nearest value and stage); at 100 it is a plain shuffle. A shop row never lists one thing twice: a repeat trades with the nearest later entry of another row.
* **Encounter groups** (`Enemies`). The normal groups are the scenes reached only through an encounter id (A3 with an id below 0x200, the variant roll; `rules/battle.md` section 1.1), never as a scene started directly (C9, or A3 from 0x200), and without the boss bit: bosses and scripted battles never move. A group's home is the area that fields it most; groups rank by their home's mean HP. Where a moved group lands it is tuned to the area it replaces (`rules/battle.md` section 13).
* **Starting gear and elements** (`StartGear`, `StartElements`; New Game only, when field op FE 3F builds the fresh game; not New Game+). Each piece of `char.bin`'s starting equipment becomes a piece of the same kind (weapon, armour, accessory) with a price that the character may equip, each grid element of the starting grids an element the element shops sell, of the same level, that the character may equip; the pick comes from a window around the piece's own value (the whole list at `Spread` 100).
* **Where the game reads it.** Chests and pickups: when a room is read, before its INIT runs (`FieldWorld::set_script_patch`), the plan rewrites the literal words of the room's moved treasures in the script code (the chest routine stores the id in a room variable that its message, its 99 stock test and its give all read, so all three agree; a word that no longer holds the thing it expects is left alone). Shops: `ShopData::stock_map`, applied to every element shop and smith row as the shop reads it. Battles: the field encounter's scene, its tuning and the drop table (`BattleOptions::drops`, `enemy_tuning`). So shops, drops and encounters follow a change at once, chests from the next room entered, starting gear at the next New Game. The plan is built the first time a read needs it: it reads the room-script scan, which it waits for (about 20 s in a Debug build, the first time only).
* **Records.** While it is on, the record pages' collection (`rules/menus.md` section 17) still records the enemies met and beaten but no loot.
* **The spoiler list**: the plan can list where everything went (`Plan::spoiler`); the game never writes it, only the dev tool `occ randomize` does (`docs/tools.md`).

## 9. Shader looks (matcaps and colour grades)

A mod can add looks to the Graphics tab's shader settings (`config.md` section 2.5.1):

```
<GameDir>\mods\<pack>\shaders\matcaps\<name>.png    a matcap for the Matcap character style
<GameDir>\mods\<pack>\shaders\luts\<name>.png       a colour-grade LUT for Grade
```

* **Matcap.** The shading of a sphere seen from the front: the pixel at (x, y) is the colour a surface whose normal is (2x / width - 1, 2y / height - 1) gets, x along the screen's right, y down (along the character's down), z toward the viewer. The other styles are lit from the upper left and in front, at (-0.35, -0.70, 0.55) in those axes; a matcap lit from there shades like them. Any size; it is sampled bilinearly. The character's colour is multiplied by 1.6 times the matcap's, so a matcap averaging about 0.6 keeps the PS1 brightness.
* **LUT.** N squares of N x N pixels side by side (width N x N, height N; 256 x 16 and 1024 x 32 are common): within a square red grows to the right and green downwards, and blue grows square by square. Any other shape is not used and logs a warning.
* `<name>` is the file name without `.png`, in lower case; it is what the settings show and what `[Shaders] Matcap` and `Grade` store. The built-in names (`clay metal ink`, `off film warm cold faded`) cannot be replaced, and between mods the first one in the list wins a name.
* Like a mod's engine features they do not follow "load on": an enabled mod's looks are offered in every art mode. They are loaded at launch and after every change of the mod list; scripted and `--config` runs load none.
