# Movies: which FMV a field script plays (op 7E / D4), file names, play range

This document covers how the field-script movie ops (`7E U` PLAY_MOVIE, `D4 U x` PLAY_MOVIE_SKIPPABLE; `7F` WAIT_MOVIE only waits for the end) choose a movie, how the movie number maps to a file in the remastered `movie.dat` archive (Bink 2, `.bk2`), which rows play only part of a file, and how OpenCross plays, ends and pauses a movie. `ocmovie table` lists everything below from the game data.

## 1. The operand is a table row, not a movie number
`7E U` and `D4 U x` read **row = low byte of U** and index a table in `field.prg`: disc 1 holds rows 0..23, disc 2 holds the following 13 rows (the same array continues). Row layout (0x18 bytes):

| off | field | meaning |
|---|---|---|
| +0 | start | frame offset used by some rows (section 4) |
| +4 | 1 | |
| +8 | end | frame count: the file's own frame numbers (STR frames = Bink frames except in four movies, section 10.6; 15 fps, `ending_s` 30 fps) |
| +0xC | mode | 0, or 3 / 4 for the two ending_s rows (disc 2 rows 11 / 12): the staff-roll layout (section 4) |
| +0x10 | **movie number** | |
| +0x14 | volume | 0x7F full, 0x6E on row 0, 0x50 / 0 on a few rows |

The operand is not the movie number. Rows 1..15 happen to be the identity, but row 0 is number 19 (the opening `newop`) and rows 16..23 map as 16 -> number 0 `a07b_ite`, 17 -> 16 `b17opkid`, 18 -> 17, 19 -> 18, 20..23 -> numbers 7 / 5 / 15 / 16 again. The title room (`opening.bin`) plays `D4 #0` on disc 1 = the opening FMV `a01op` (the logo scene appears when it ends or is skipped) and `D4 #1` on disc 2 = `titleb`. OpenCross: all rows are in `src/game/disc_index.cpp` (`DiscIndex::movie_row`).

## 2. Number to file
The movie's file index is **6035 + number** in the `.fnd` of the disc in the drive (`cdrom.fnd` disc 1, `cdrom2.fnd` disc 2; the record is `c:\movie\<name>.stv`, a PS1 movie stream, section 10; on the discs themselves OpenCross reads it as `cdrom/movie/<name>.stv`). The disc is variable 0x42 (disc - 1) / the DiscCheck (`FieldWorld::disc()`). Disc 1 rows address the 20 disc-1 records (numbers 0..19), disc 2 rows the 11 disc-2 records. A record that is not `c:\movie\...` plays nothing.

Name to archive member: `movie/<name>.bk2`, except the three per-language movies: `newop` -> `a01op_<lang>`, `b28end` -> `b28end_<lang>`, `final` -> `final_<lang>`, suffix `en fr it de es jp`. `movie.dat` holds 46 members (stored, not compressed): the 6 languages of those three, `ending_s`, `title`, `titleb` and the other `a..` / `b..` movies. OpenCross: for each stem, `<name>_<lang>` is tried before `<name>`, and at each stem a mod's loose `.mp4` / `.mkv` before the `.bk2` (`movie::resolve_member`); the language comes from the config, so a mod may localise any movie.

## 4. Play range
Table frame numbers are the file's own 1-based frame numbers, at its own rate (15 fps, 30 for `ending_s`; never rescaled): playback starts at `max(start, 1)` and stops when frame `end` (clamped to the file's frame count) is reached, so frames `start .. end - 1` are shown. A row without a range has end = the frame count: its last frame is not shown either. Only some rows give a range:
- disc 1 row 20: start = 1 + 0x131 = 306 (not the row's own start field), end = row end (489);
- rows 21 and 23: start = 1 + row start = 1 (the beginning), end = row end (90 / 258, shorter than the file);
- row 22: start = 1 + 0x118 = 281, end = row end - 10 (417);
- disc 2 row 12: start 1, end = row end (8130 of `ending_s`'s 8951 frames). Every other row plays the whole file.

The PS1's movie loop leaves once its frame counter (the number of the frame it last took from the stream) reaches end - 2: 2278 on the Japanese `newop` (row 0), 8128 on disc 2 row 12, so the last frame or two before `end` differ by at most two movie frames from the range above.

OpenCross: `DiscIndex::movie_range` returns the range; `movie::Player::open(..., start, end)` turns it into 0-based decoder frames `[start - 1, last - 1)`, `last` = `end` clamped to the container's frame count (`Decoder::frame_count`; 0 = the frame count), decodes and drops the frames and audio before `start` (clock and audio start there) and stops at `last - 1` (audio is cut at the same time). A mod movie that replaces a ranged row must keep the original's frame numbering.

**Volume.** RDE starts every row's Bink sound at `vol / 127` of its movie volume; OpenCross scales the movie's sound by the row's `vol / 127` on top of the movie bus (`Mixer::movie_start(level)`): 110 for the opening, 80 for `final` and the two `ending_s` rows, **0** for disc 2 rows 2 (`b28end`) and 3 (`final`), which play without sound.

**The music keeps playing.** Neither the PS1 nor RDE stops the field's song for a movie: the PS1 movie loop suspends the music only while the CD stream runs dry (a stall, not the movie), and RDE replaces the stream routines with Bink and never touches the music. A script that wants silence stops the song itself (`88 FF` or an `FE 1D` fade before the `7E`). The true ending relies on it: opa_b04f (entrance 2) starts song 7, fades it in over 90 frames and plays disc 2 row 2 (`b28end`, whose Bink track is digital silence) under it, then fades the song out after `7F`. OpenCross leaves the BGM alone while a movie plays (`App::start_movie`); only the pause screen holds it (`Mixer::hold`).

**The staff roll (disc 2 rows 11 / 12, modes 3 / 4).** `ending` entrance 1 plays row 11 (the whole `ending_s`, last frame 8951); `opa_a04f`, `opa_b04f` and `ryu_b28i` play row 12 (last frame 8130). Both show the movie in a small panel and a credits strip that scrolls up beside it. RDE (the reference; frame grabs of the whole roll, the layout is the same in every frame):
- Picture = the 4:3 fit of the window (height min(h, w * 3 / 4), centred), without the crop bands. **Movie panel**: x 0.48 .. 0.97, y 0.46 .. 0.95 of it (0.49 of the picture each way, the whole 640 x 480 movie scaled into it); black elsewhere.
- **Strip** image: `hd/staff/staff24.png` in Japanese, `hd/staff/staff24us.png` in every other language (English, French, Italian, German, Spanish), 144 x 8950 RGB, white names and lilac headings on black, content rows 225 .. 8691. It is drawn on RDE's 1280 x 960 canvas over the game viewport (`render::overlay_fit`: 8/960 bands, the rows squashed by 944/960 x 928/960): x 0 .. 0.45 of the canvas width (576 units, 4 per strip pixel), y canvas 0 .. 960, i.e. window y 0.0083 .. 0.9589 of the picture. The area shows span = 144 * 3 / (8950 * 4 * 0.45) of the strip's height, 240 rows. Linear filtering, the movie's alpha (1 while it plays). The strip, the panel and their placement are the same in both art modes: RDE draws the PNG with original art too, so OpenCross's Classic mode uses it as well. The two PNGs are exactly the strips the discs stream with the movie (section 10): `staff24.png` = the Japanese disc's, `staff24us.png` = the USA disc's. Played from the discs (no `hd.dat`), the strip comes from the stream itself: row A for row 11 (the same picture as the PNG of the disc's region), row B for row 12 (section 10.5), whatever the language setting; it is drawn in the same place and scrolls by the formula below with last = the strip's row count + 1 (8951) on both rows, since row B is already laid out for the shorter roll.
- **Scroll**: the strip row at the top of the area, as a fraction of the strip's height, is top = (span * 0.52 + 1) * F / last - span, F = Bink's frame number while frame F - 1 is shown, last = the row's last frame (8951 / 8130). At frame 0 the strip's first row sits at the bottom edge; at the last frame the strip's end stands 0.52 of the span above the bottom, past the last credit. Row 12 therefore scrolls 8951 / 8130 = 1.10 times as fast as row 11, about 1.01 strip rows per frame on row 11.
- The PS1 (DuckStation, Japanese disc 2) builds the same picture in 24-bit colour on a 208-line display: the strip rows come from the STR's data sectors (0x1B0 bytes = 144 pixels each), row A of each strip sector in mode 3 (row 11) and row B in mode 4 (row 12; row A is read past), kept in a 272-row ring that moves one row per movie frame while the stream has rows buffered (on disc 2 row 12 the strip row at the top of the picture is the ring's count of rows shown minus 215 throughout the roll, and that count trails the movie frame by 6 to 29), one row per display line over the left 144 of 320 pixels (0.45); the movie panel stands higher than RDE's, x 0.47 .. 0.97, y 0.36 .. 0.87 of the 320 x 240 output. RDE's data has no STR, and its PNG rows are those strip rows (the same picture in a DuckStation grab, which scales the 224 lines to 240), so OpenCross uses the PNG and RDE's layout in every art mode.

OpenCross: `App::start_movie` switches a mode 3 / 4 row to the layout (`movie::Player::set_staff_roll`, the strip from `movie::staff_strip_member(language)`); `Player::draw` puts the movie in the panel and the strip (`staff_strip_top`, clipped to the strip's rows) on the overlay canvas. The held last frame (section 6) keeps the strip where that frame left it and treats it like the panel: it is held, faded and cut with the panel at the same alpha, and inside the strip's quad the strip's own opaque texels (black behind the names) replace the black veil, so the scene behind darkens no more there than elsewhere. At a natural end the strip is already past its last credit, so only the panel shows. A skip mid-roll is OpenCross's own (section 8: RDE ignores the buttons over a `7E` row, so the staff roll always plays to its end); the strip then stays and goes with the panel. After row 11 the room plays `final` and moves to its entrance 2, the THE END screen, where RDE fades its end card in (`text.md` section 7.10). RDE picks the layout by size (a movie smaller than its 1280 x 960 render size, which only `ending_s` is); OpenCross by the row's mode, so a mod's upscaled `ending_s` keeps it. Route `staff_roll` (`set var 42 1`, `load ending 1`).

## 5. Decoder and file access (OpenCross)
Bink 2 is decoded with librempeg (built locally by `scripts\build-librempeg.ps1`, commit pinned in CREDITS.md); audio is pulled from the same stream. YUV->RGBA runs on the decoder worker thread; the frame texture is created at the movie's own size.

**Disc movie streams.** Without `movie.dat` (disc mode), `movie::resolve_member` falls back, after a mod's `.mp4` / `.mkv` / `.bk2`, to the disc's stream `cdrom/movie/<name>.stv` (`a01op` is the discs' `newop`; every other name is the record's own). `Decoder::open` with a member ending in `.stv` reads it without librempeg, and never whole: `Player::open` hands it `Vfs::open_reader(member)`, which on the discs reads only the sectors asked for (`DiscBackend::open_reader`), so a movie plays from an optical drive as it is read (`ending_s` is about 92 MB). `import::StrStream` reads the stream front to back in blocks of 32 sectors (section 10): `open` reads the first 256 sectors on their own (picture size of the first frame, frame rate from the spacing of the first frames, whether there is audio and a strip) and the last 256 (frame count = the highest frame number there); `next` hands out the audio groups and the assembled frames in stream order, reading up to 2048 sectors past the item it returns (at most two blocks a call), and the strip rows pile up as the stream goes by. On all 62 streams of both regions' discs these give the same size, rate and frame count as an index of the whole file. `import::mdec_decode` decodes each frame (section 10.3) straight to RGBA, and each group's two ADPCM payloads decode with the SPU decoder (`audio::adpcm_decode_block`, the history carried per channel) to 44,100 Hz stereo, resampled to 48 kHz like the Bink sound. One `step()` decodes the audio groups stored before the next frame, then the frame; frame index = frame number - 1, time = index / fps (15, or 30 for `ending_s`), frame count = the highest frame number. A frame that does not decode repeats the previous picture (none does on either region's discs). The 320 x 224 frames fill the same 4:3 picture as the Bink files (`Decoder::display_width` / `display_height` = 4x the width by 3x the width, the picture's shape on screen; the texture keeps the frame size). Play ranges and the clock are the same as for Bink, with one difference in `App::start_movie`: a row without a range still ends at the row's end field, which is the stream's frame count on every row except the Japanese `newop` (end 2280, stream 2705), so its 420 black frames after the opening are not shown. The staff roll takes its strip from the stream (section 4): a stream whose first sectors hold a strip sector carries one per frame, so its strip is the frame count high (8950 rows in `ending_s`); `Decoder::staff_strip` gives the rows read so far with the rest black, and the player uploads the texture again every 32 new rows. The roll shows rows up to about 1.4% of the frame number ahead of the frame on screen (125 rows by the end of `ending_s`), well inside the 400 rows the read-ahead holds. Measured on `a07a_jka` (Japanese disc 1, frame index 100): mean absolute RGB error 2.1 against RDE's Bink frame box-downscaled to 320 x 224 (librempeg's own `mdec` decoder: 2.2; the two STR decodes differ by 0.6 on average, at most 8, from rounding); `ocmovie info` gives the same length and RMS per 10 s as the Bink track (-20.0 / -11.8 / -12.5 / -21.5 dBFS against -20.0 / -11.8 / -12.5 / -21.6).

- **Streams.** The first video and first audio stream are used; a movie without audio plays against the wall clock. Frame time = decode index / frame rate (`avg_frame_rate`, else `r_frame_rate`, else 15), not the container timestamps. Video decodes with automatic codec threading.
- **Mod codecs.** Besides Bink (`.bk2`), mods may supply HEVC or H.264 in `.mp4` / `.mkv` (any codec librempeg decodes; the file name is the container hint). Accepted pixel formats: YUV 4:2:0 / 4:2:2 / 4:4:4 8-bit, full-range 4:2:0 (YUVJ), 4:2:0 with alpha (alpha plane copied to RGBA alpha), 4:2:0 10-bit (shifted to 8); anything else logs an error and drops the frame.
- **Colour.** Bink is always full-range BT.601. Other codecs follow the stream tags: JPEG range = full, else limited; BT.709 / BT.2020 NCL = Rec. 709, untagged = Rec. 709 from 720 lines up, else Rec. 601.
- **Audio.** Float samples (packed or planar) only; mono is duplicated to stereo, channels above two are ignored, and the stream is resampled by linear interpolation to 48 kHz stereo float (`Decoder::kAudioRate`).
- **Pacing.** The player keeps up to 8 decoded frames and about 1 s of audio ahead. The clock starts once the first frame and 0.25 s of audio are ready; it then follows the mixer's consumed movie sample count (never going backwards) and switches to the wall clock once the audio is drained. The movie ends when the decoder is drained, the queue is empty, one frame period has passed and the audio has played out. A movie that cannot be opened is skipped and the script continues.

**Mod movies stream from disk.** A `movie/<name>.bk2` supplied by a mod is a loose file (often hundreds of MB, e.g. 1280x960 or 1920x1440 upscales). `Player::open` asks `Vfs::loose_file(member)`; when the overlay resolves the member to a file on disk, `Decoder::open_file` reads it through a buffered, seekable file AVIO (no whole-file read, no start stall, no RAM copy). Archive members (`movie.dat`) go through `Vfs::open_reader` + `Decoder::open`, read whole into a memory AVIO; only a disc movie stream is read in parts. The member name is resolved with `exists()` (overlay first), localized `_<lang>` before plain, so `a01op_en.bk2` etc. are found.

**The Extras theatre** (`rules/menus.md` section 17.8.2) plays a movie through its first table row that plays it whole, on the row's own disc (`App::open_movie`, the same opening as a script's request): range, volume and the staff roll's layout as above, no held last frame; the field neither runs nor plays music meanwhile, and the movie skips and pauses as in section 8.

`FieldWorld::play_movie` logs a warning when a second movie is requested while the first is still requested or playing.

The retail player has two playback loops, picked by 7E's high operand byte or the low two bits of D4's flags; every 7E and D4 in the data picks loop 0, and OpenCross has one loop and ignores the selector. The loop 1 runs the field's frame driver once per movie frame with the field picture off: the logic half runs (entity scripts, movement and triggers, the screen fade, camera scroll), the picture half does not (animation requests, background layers, models and shadows, effects, dialogue windows); the movie's own room sequence (`mo1?` / `mo2?`, `room_effects.md`) runs alongside. Every one of the 48 `7E` / `D4` ops in the scripts is followed directly by `7F WAIT_MOVIE`, so the calling script stands still; only other entities' scripts and a running fade advance. OpenCross ticks only the room sequences during playback (`FieldWorld::movie_tick`).

## 6. Movie end: hold or fade the last frame over the resumed field
Retail PS1: the movie loop of op 7E / D4 fades during the last 8 frames, then rebuilds the field display and the script continues in the same frame: no black gap, no load between the movie and the next scene. What the field shows then depends on **flag 8** of the movie flags (below). With it the field's screen fade (slot 0, `fieldscript.md` A8) restarts from black and runs back to the picture over 0x60 ticks (linear, two ticks a field frame), whatever it was before the movie, and the fade direction is back to the picture; the movie's last frame fades out over it. Without it the screen fade is left as the movie found it: a FADE 1 before a `7E` keeps the field black after the movie, and a room change behind it starts from black. PS1 captures (DuckStation, Japanese discs; the slot-0 fade value and the mean luma of every field frame): jac_b20i's win branches without and with Kid (FADE 1, `D4 #16,#8`; the branch with Kid then has a `FADE 0,#30`, which does nothing) both go from the movie's white last frame to the field at full brightness over the 0x60 ticks and are never black; in the branch with Kid the `7E #7` before it (FADE 1 before and after it) ends with the screen still black. des_b06f's exit (FADE 1,#90, `7E #11`, 5A to wld_b01) stays black from the movie's last frame until wld_b01's entry fade-in, and so does the ending room's staff roll (entrance 1: FADE 1,#0, `7E #11`, `7E #0`, 5A to its entrance 2) through both movies and the wait between them. The same scenes with the flags word changed while the movie plays swap the two behaviours (jac_b20i with 0 stays black, des_b06f with 8 fades in), and a flag-8 movie that starts over the visible field still restarts the fade from black.

RDE (the reference) plays the movie with Bink and decides at the end frame by **flag 8** of the movie flags: `D4` takes them from its second operand (every `D4` in the data has `#8` or `#520`), `7E` sets them to 0; either op ORs in 8 while a `DC` movie-end jump is recorded (`fieldscript.md` DC). The movie stops at its end frame, the field script continues at once (7F returns) and the field runs and draws behind the last movie frame, which stays on top:
- **flag 8 clear: hold.** The last frame stays opaque for 10 frames (the end frame and 9 more), then disappears in one cut.
- **flag 8 set: fade.** The last frame is drawn at alpha `(160 - n) / 160` in the n-th frame after the end frame (n = 0..159, about 2.7 s), then disappears.

Measured in RDE (frame series with the movie state, mean luma of each captured frame): crn_b16i `D4 #6,#8` (`b22fujyo`) fades over 160 frames at 60 Hz; under it the field of crn_b16i is already running its own fade-in from black (the field's luma behind the frame rises from about 7 at n = 56 to 21 at n = 108) and the following dialogue opens as the fade ends. opn_a05i `7E #3` (`a03kidfb`, whose last frame is white) is held opaque for 10 frames while the script's map jump loads the next room behind it, then cuts to that room's black entry. The title room's cold-boot `D4 #0,#520` (`a01op`) fades like crn_b16i. Behind the frame RDE runs the original's screen fade unchanged (its guest RAM holds the same slot-0 fade as the PS1): after jac_b20i's `D4 #16,#8` without Kid the fade restarts from black and is back at the picture 0x60 ticks after the end frame, and the screen reaches the field's own brightness when the frame's 160-frame fade ends; after des_b06f's `7E #11` the fade stays black, so the held frame cuts to black after its 10 frames and wld_b01 fades in from black once loaded.

OpenCross: `FieldWorld::play_movie` sets `MovieRequest::fade` from the op's flags (`D4`'s second operand, 0 for `7E`) and a recorded movie jump; the New Game movie (`FlowMachine`, the title's `D4 #2,#520`) passes 0x208. `App::end_movie` calls `FieldWorld::movie_finished`, which with `MovieRequest::fade` starts the screen fade from black over 0x60 ticks (`fade_in_from_black`) and otherwise leaves it alone, and keeps the last decoded frame (`movie::Player::close(true, fade)`, `held()`); `draw_held()` draws it over the finished frame and `step_held(dt)` runs `movie::held_frame_alpha` (10-frame hold or 160-frame fade, 60 frames a second; a longer frame, e.g. a room load, counts as one) from the frame the movie ended in. A `DC` jump recorded before the movie is taken in `FieldWorld::movie_finished`: PREVIOUS_MAP_ID = the room register, the register = the target, and the room switches with no fade-out, so the held frame fades over the new room's entry. This applies to every FMV (title opening, 7E / D4 from scripts, skipped or finished). Routes: `title_fade`, `movie_jump`, `movie_opn`, `lynx_no_kid` (flag 8: the field comes back from black), `movie_black` (a `7E` after a FADE 1 stays black into the next room).

## 7. The title script (`opening.bin`) and the New Game movie
The second operand of every `D4` here is `#520` (0x208), the wipe / flag word; the first is the table row.
- UPDATE script (runs on entering the room): `OPFE1D #20,#0` (music fade, 20 frames), `WAIT 20`, `PLAY_SONG #255` (stop), then by `$ROOM_PARAM`: 0 -> `D4 #1` (row 1 `title`) unless var 0x42 == 1 (disc 2) where `D4 #0` plays; param 1 -> `D4 #1` only when var 0x42 != 0; param 2 / 3 -> the same `D4 #1` / `D4 #0` pair after `SET_0 $3E`. Row 1 `title` is the title loop / logo FMV played when the title room is re-entered (after game over / reset); row 0 (`a01op`) is the cold-boot opening.
- After the logo scene: `OPFE1D #20,#0`, `FADE 1,#32`, `WAIT 32`, layers 0 / 1 off, `PLAY_SONG #255`, `WAIT_SONG`, then the menu / name entry (`OPEN_MENU`, `RENAME_CHARACTER #0`, `OPEN_MENU`, `WAIT 24` each).
- **New Game tail**: `ADD_TO_PARTY #0`, `#1`, `RAND_MOD $4,#14` -> `ARRAY8_GET 0x310` -> `ADD_TO_PARTY` (third member), each followed by `COMMIT_PARTY_MODEL`; `MAP_JUMP_DC #22,#0` (records the jump; it is taken when the movie ends); then `D4 #2,#520` (`a02koryu`, skippable) + `WAIT_MOVIE` + `STOP_EXEC`. The fly-in to Fort Dragonia plays over the title room with no further fade or music op (music was already stopped), and `opn_a01i` loads when it ends.
- OpenCross: `FlowMachine::on_name` returns `FlowAction{movie_row = 2, load_room}`; `App::apply_flow_action` requests the row (`FieldWorld::play_movie(2, 0x208)`), starts it at once and keeps the room load (`deferred_flow`) until the movie ends or is skipped (a missing file loads the room immediately). The load is the DC jump: PREVIOUS_MAP_ID = the title room's register 8 (left by its FE 2F), so `opn_a01i` starts with variable 0x08 = 8, as the New Game+ start from the ending room does. Routes `newgame`, `ngplus_title`.

## 8. Skipping and pausing an FMV
RDE skips a movie whose flags have bit 0x200 (the `D4 ... #520` movies: the title room's and opa_a04f / opa_b04f row 8) on the press of any pad button: the d-pad, Circle, Cross, Triangle, Square, L1, R1, L2, R2, L3, R3, Select and Start all end the cold-boot `D4 #0,#520` (the movie flag drops about 0.9 s after the press); Start does not pause it. A movie without 0x200 (every other `D4`, which carry `#8`, and every `7E`, whose flags are 0) ignores the buttons and plays to the end (crn_b16i `D4 #6,#8` ran its full 51 s under 17 Circle presses).

OpenCross lets every movie be skipped (`architecture.md` section 13). The skip keys (`movie_skip_edge`, `src/app/app_sim.cpp`) are the PS1 buttons OpenCross does not use for anything else over a movie: the Up / Down / Left / Right, Ok, Cancel, Item, Menu, SelectLeft and SelectRight keys of both keyboard sets, K (Select), and the pad's d-pad, face buttons, shoulders and Back. Start / Space opens the pause screen instead (below); the speed keys (F1 / F2, the pad triggers = L2 / R2), the stick clicks (L3 / R3, hotkeys), Esc and keys outside the sets do not skip.

The PS1 and RDE have no pause during a movie, so the pause is an OpenCross feature:
- Start / P while a movie plays opens the RDE pause screen over the held frame (`App::pause_modal`, `src/app/app_sim.cpp`): `movie::Player::set_paused(true)` makes `update()` do nothing (the wall clock stops, no frame is picked, the on-screen frame stays and `draw()` shows it through the CRT ramp filter), and `Mixer::hold(true)` stops the movie PCM ring and its clock (`movie_frames_played`, the audio clock the player follows) and silences the music and voice buses. The decoder thread fills its ready queue and waits. Resuming (Start / P / B / X) continues frame and sound exactly where they stopped.
- Skip while paused is not possible: the pause screen is modal and swallows every button. Resume first, then skip. Esc still opens the settings window, which pauses the host as before.

## 10. PS1 movie streams (`c:\movie\<name>.stv` on the discs)
The PS1 discs hold the movies as interleaved sector streams: file records 6035.. of the disc's `.fnd` (section 2), 20 on disc 1, 11 on disc 2. They are not standard XA movies: every sector is a Mode 2 **form 1** data sector (subheader file 0, channel 0, submode 0x08, coding 0; the last sector of a stream has submode 0x89 = data + end of record + end of file), and the audio is SPU ADPCM carried in data sectors, not XA ADPCM. All sector kinds are told apart by a header in the 2048-byte user data, so the subheader is never needed.

### 10.1 Sector header (user data 0x00..0x1F, little-endian)
| off | size | video sector | audio sector | staff strip sector |
|---|---|---|---|---|
| 0x00 | u16 | 0x0160 | 0x0160 | 0x0160 |
| 0x02 | u8 | 1 | channel: 0 left, 1 right | 3 |
| 0x03 | u8 | 0x80 + (disc - 1) | disc - 1 | disc - 1 |
| 0x04 | u16 | chunk number in the frame, 0-based | = channel | 0 |
| 0x06 | u16 | chunks per frame (8; 3 in `ending_s`) | 2 | 1 |
| 0x08 | u32 / u16 | frame number, 1-based | group counter (u16; ignore) | counter (u16; ignore) |
| 0x0C | u32 | frame bitstream size in bytes (at most chunks x 2016) | filler | filler |
| 0x10 | u16 x 2 | width, height (320 x 224; `ending_s` 160 x 112) | filler | filler |
| 0x14 | 8 bytes | copy of the bitstream's 8-byte header (10.3) | filler | filler |
| 0x1C | u32 | 0 | filler | filler |

The type is byte 0x03 bit 7 (video) and byte 0x02; the low bits of byte 0x03 carry the disc number, so disc 2 streams read `60 01 01 81` (video) / `60 01 00 01` (audio). Filler is 0xFF (disc 1 audio sectors also hold u16 0 and u32 2016 at 0x0A / 0x0C; nothing reads them). One more type exists: `60 01 02 00`, a pair of audio-end sectors (channel 0 and 1) in place of the audio of the last group of the Japanese `newop` only; it carries no sound.

### 10.2 Interleave, frame rate, end
- **15 fps movies** (all but `ending_s`): groups of 10 sectors, one frame each: `L R V0 V1 .. V7` (left audio, right audio, 8 video chunks). Every frame takes 8 video sectors whatever its size; the chunks after the bitstream end are 0xFF filler.
- **`ending_s`** (30 fps): groups of 10 sectors, two frames each: `L R S V0 V1 V2 S V0 V1 V2` (S = staff strip sector, one before each frame).
- The stream is read at double CD speed: 150 sectors a second, so a group lasts 1/15 s; frame rate = 150 / sectors per frame (10 or 5). Audio: one L + R pair of 2940 samples each per group = 44,100 Hz.
- **End**: the stream ends with its file (record size / the last sector's end-of-file submode); the last video frame carries the highest frame number. The frame count of each movie is in 10.6.

### 10.3 Video bitstream (one frame = chunks 0..n-1 of the frame, payload 2016 bytes from user data 0x20, cut to the frame size)
Standard PlayStation MDEC "version 2" frames, the same in every movie: 8-byte header u16 MDEC length (the size of the run-length stream the frame expands to; not needed), u16 0x3800, u16 quantiser (1..15 in these discs), u16 version = 2; then the bitstream, read as little-endian 16-bit words with the bits taken from the most significant end. Macroblocks of 16 x 16 pixels in column order (top to bottom, then the next column; 20 x 14 for 320 x 224), each six 8 x 8 blocks in the order Cr, Cb, Y top-left, Y top-right, Y bottom-left, Y bottom-right. Per block: a 10-bit signed DC value, then MPEG-1 intra AC run / level codes (the MPEG-1 DCT coefficient table), escape = `000001` + 6-bit run + 10-bit signed level, end of block = `10`. Dequantisation: DC = value x 2 (10-bit precision, independent of the quantiser), AC = (level x quantiser x matrix + 4) / 8 rounded toward zero, with the MPEG-1 default intra matrix (at the coefficient's natural position, after the zigzag scan); then the 8 x 8 inverse DCT (f = 1/4 sum C(u) C(v) F cos cos, C(0) = 1/sqrt 2), luma + 128. The result is full-range YCbCr 4:2:0, BT.601 (R = Y + 1.402 Cr, G = Y - 0.344 Cb - 0.714 Cr, B = Y + 1.772 Cb), each chroma sample covering 2 x 2 pixels.

### 10.4 Audio sectors
User data 0x20..0x7F is 0xFF. At 0x80 a 0x50-byte block: `AKAO`, u32 group index (0-based), 8 zero bytes, u32 remaining bytes (falls by 1680 per group), u32 0, u32 0x11, u32 0x1000 (the SPU pitch for 44,100 Hz), u32 1680 (payload size), zeros. Payload at 0xD0: 1680 bytes = 105 SPU ADPCM blocks of 16 bytes (byte 0 = predictor << 4 | shift, byte 1 = flags, 14 bytes of 4-bit samples, low nibble first, 28 samples); the flags are 2 in every block and 3 in the last (SPU loop markers; decoding ignores them). 0x760..0x7FF: ten silent filler blocks (`00 03 00 ..`). Decoding: the PS1 SPU's five predictors, the history carried across sectors of the same channel. Left = channel 0, right = channel 1; both sectors of a group share the AKAO block. The audio of a group is stored just before that group's frame(s).

### 10.5 Staff strip sectors (`ending_s` only)
User data 0x20: two rows of 0x1B0 bytes, 144 pixels of 24-bit RGB each; 0x380.. is 0xFF. Row A of the 8950 strip sectors, in order, forms the 144 x 8950 strip of the whole roll (disc 2 row 11); it is pixel-identical to RDE's `staff24.png` on the Japanese disc and to `staff24us.png` on the USA disc, so the USA strip is in English. Row B is the same credits laid out for the shorter roll (disc 2 row 12, last frame 8130): its content ends about 830 rows earlier and stands 8951 / 8130 = 1.10 times faster through the frames. The PS1 shows row A for row 11 and row B for row 12 (section 4).

### 10.7 Cooked (2048-byte) images
Nothing a movie needs is lost in a 2048-byte `.iso`: video, audio and strip sectors are all form 1, their headers are in the user data, and the whole disc (all four images) has no form 2 sectors apart from four empty ones in the system area (sectors 12..15). Movies play with sound from a cooked image.

### 10.8 Decoding with librempeg
librempeg's `mdec` decoder decodes these frames exactly as they are (every frame of every movie, both regions, no errors; pictures match the Bink frames), and its `adpcm_psx` decoder decodes the audio when it is given one packet of 3360 bytes per group = left payload then right payload, as stereo with block_align 3360 (it matches a reference SPU ADPCM decode: correlation 1.0, 2940 samples per channel per group, only rounding differences). Its `psxstr` demuxer is not enough on its own:
- raw 2352-byte input: it sorts sectors by subheader submode, and every sector here is "data", so audio sectors are taken as video chunks; the stream's first sector (audio) sets the picture size to 65535 x 65535 and the decoder fails to open;
- 2048-byte input: it knows the Chrono Cross audio type bytes and decodes disc 1 movies completely (video, and audio with the `fastaudio` parser enabled), but on disc 2 the video type `60 01 01 81` is not recognised (probing fails; forced, video would be taken as audio), strip sectors and the `newop` end sectors are taken as audio, and the frame rate is fixed at 15 fps (wrong for `ending_s`).
OpenCross therefore does not use librempeg for these streams: it demuxes them itself (10.1 / 10.2, `import::StrStream`), decodes the MDEC frames with its own decoder (10.3, `import::mdec_decode`) and the audio with the SPU ADPCM decoder the music already uses (section 5); the librempeg build stays Bink / HEVC / H.264 only.
