# Multiplayer presence and chat

OpenCross's optional multiplayer shows other players' parties walking in the same field room and carries room and global chat. It is an OpenCross feature, not an RDE one: off by default (`[Multiplayer] Enabled`, `config.md`), and purely cosmetic. Remote parties are never entities of the room: they run no scripts, touch no story variable, flag, save or RNG, collide with nothing and cannot be talked to. Runs with `--config` and `OC_QUIET` runs never connect.

There is one server implementation, the Cloudflare Worker in `server/cloudflare/`. The public deployment is the Master server, `wss://opencross-multiplayer.sphy.workers.dev/ws`, fixed in the client. Anyone can run the same Worker on their own machine with `npx wrangler dev`, or deploy it to their own Cloudflare account, and choose "Local / other" with that address (`[Multiplayer] Server=other`, `ServerUrl`; section 6).

## 1. Transport

One WebSocket per client, `wss://` (Master, or another server online) or `ws://` (a server on this machine), path `/ws`. Every message is one UTF-8 JSON text frame holding an object whose `t` member names the message. Unknown members are ignored and unknown `t` values are dropped, so either side may add members without breaking the other. Numbers are integers unless stated.

The client connects when multiplayer is enabled and reconnects after a drop with a back-off of 2, 4, 8, 16, then every 30 s; a `welcome` starts the back-off over. The server closes a connection that sends nothing for 60 s; the client sends `ping` after 20 s without sending anything, and drops and remakes a connection that has received nothing for 75 s. After `error` `banned` or `version` it stops reconnecting until multiplayer is switched off and on, or the server address changes.

## 2. Identity

Each install makes a random 128-bit player id on first use and keeps it in `[Multiplayer] PlayerId` (32 lower-case hex digits). The client sends it only in `hello`. The server never repeats it: other clients know a player by `pid`, the first 16 hex digits of the SHA-256 of the id's 32 hex characters, so knowing someone's `pid` does not let a client claim their id.

Names are labels, not identities. Nothing proves a Steam name, and two players may show the same one. The name a client sends is, in order: `[Multiplayer] Name` when set, else the Steam display name (from the Steam connection when `[Game] Steam` is on, else the one Steam stored on this machine for the current user), else `Player`.

## 3. Client to server

|---|---|---|

Anything before it closes the connection. |

| `room` | `room` | The field room the player is in (the room file name, such as `alu_a01f`), or `""` when not in a field room (title, world map, movie, ending). Sent after `welcome` and on every change. |
| `party` | `models` | The party's field model per slot, leader first: up to 3 integers, the model byte each party actor shows (the filled slots up to the first empty one). Sent after `welcome` and whenever it changes. |
| `pres` | `x`, `y`, `z`, `f`, `c`, `m`, `s`, `seq` | The leader's state (section 5). |
| `chat` | `scope` (`room` or `global`), `text` | A chat line. |
| `pm`, `challenge`, `challenge_cancel`, `challenge_reply`, `pvp_end` | | Private messages and battle challenges, section 8. |
| `pvp_side`, `pvp_cmd`, `pvp_hash`, `pvp_resume` | | The battle link, section 8.4. |
| `ping` | | Keep-alive. |

## 4. Server to client

| `t` | Members | Meaning |
|---|---|---|
| `welcome` | `pid`, `admin` (true when `hello` carried the right admin token), `limits` (`chat_len`, `name_len`, `pres_hz`, `chat_per_10s`) | `hello` accepted. |
| `peers` | `room`, `list` | Answer to `room`: everyone already in it. Each entry has `pid`, `name`, `star`, `pvp`, `models`, and `pres` (the last `pres` object, or `null`). |
| `join` | `pid`, `name`, `star`, `pvp`, `models`, `pres` | A player entered your room. |
| `leave` | `pid` | A player left your room or disconnected. |
| `profile` | `pid`, `name`, `star`, `pvp` | A player in your room changed name, Star Level or `pvp` flag. |
| `party` | `pid`, `models` | A player in your room changed party. |
| `pres` | `pid` and the `pres` members | A player in your room moved. |
| `occupancy` | `others` | How many other players are in your room; sent with `peers` and on every `join` / `leave`. |
| `chat` | `scope`, `pid`, `name`, `text`, `ts` (Unix ms), `admin` (present and true when the sender's `hello` carried the right admin token) | A chat line; `room` lines only reach players in the sender's room at the time. `scope` `pm`: section 8.1. |
| `challenge`, `challenge_end`, `pvp_start` | | Battle challenges, section 8.2. |
| `pvp_side`, `pvp_cmd`, `pvp_hash`, `pvp_away`, `pvp_back`, `pvp_resumed`, `pvp_gone` | | The battle link, section 8.4. |
| `error` | `code`, `msg` | `code`: `rate` (message dropped by a rate limit), `bad` (malformed), `offline` (section 8.1), `version` (protocol too old: the client shows `msg` and stops reconnecting), `banned` (the connection is then closed and the client stops reconnecting). |
| `pong` | | Answer to `ping`. |

The server trims `name` to `name_len` (24) code points and `text` to `chat_len` (200), strips control characters, and drops an empty result. Chat is plain text: the client never interprets links or markup.

## 5. Presence

`pres` describes only the party leader, in the field's own units: `x`, `y`, `z` the position in world units (rounded), `f` the facing (4096 = one turn), `c` the field clip the leader plays (`game::FieldClip`), `m` 1 while it moves, and `s` the player's state:

| `s` | State | How others draw the party |
|---|---|---|
| 0 | In the field, free to move | Walking. |
| 1 | In a battle | Standing still, with crossed swords by the name. |
| 2 | In a menu, shop or the pause screen | Standing still, with a menu icon by the name. |
| 3 | In an event (a script holds the controls, dialogue is open, a fade or a room change runs) | Standing still. |
| 4 | Typing in the chat (its input line is open in free play) | Standing still, with a speech-bubble icon by the name. |

`seq` counts up by one per message, so a receiver drops one that arrives out of order.

To save traffic the client sends `pres` only while `occupancy` says someone else is in the room, at most 10 times a second, and only when a member other than `seq` has changed; a stop (the last message with `m` 0) is always sent. The server keeps each player's last `pres` in the current room and hands it to whoever joins the room, so a player who stands still is still drawn; leaving a room forgets it, so a `join` never carries the previous room's spot. A client reports its room only once its leader stands in it, so its first pose is a real spot of that room.

The local side reports the party leader (the entity of party slot 0) as it stands after the field tick: its position rounded to whole units, its facing, `c` the clip id it plays when that is a field clip below 0x80 (else 1, standing), `m` while it moved on the tick. `s` is what the field can tell: 1 while a battle is being set up, 2 while a script screen (main menu, shop, name entry, save) is requested or open, 3 while a movie plays or the controls are not free (a script holds them, a message window is open, a fade or a room change runs), else 0. The pad's own main menu and the pause screen are the host's to report. `party` sends the model byte each slot's entity shows (a disguise shows), or the character record's model byte for a slot whose entity is not bound.

Each client works out the rest itself, on its own field ticks (`game::RemoteParties`, `src/game/remote_parties.*`):

- **Leader.** Every received pose is stamped with the local tick it arrived on. The leader is shown 9 ticks (150 ms) late, interpolated between the two poses around that moment, the facing the short way round; past the newest pose it holds there (no extrapolation). A pose that arrives after a stop (the one before had `m` 0, and more than 9 ticks have passed) gets the previous pose repeated 9 ticks before it, so the move plays over the delay instead of jumping. A pose more than 400 units from the one before (a room entry, a teleport) is shown at once and the followers regroup behind it. The height is the sender's.
- **Followers.** A follower is placed in the party V behind the remote leader (128 units away, an eighth of a turn to either side of straight behind, facing the leader's way: the formation the field gives a party on room entry), at the half V or on the leader's spot when the V spot has no floor within 64 units of the leader's height, on its first tick with a model and after each arrival or snap. After that it moves by the field's follow rules (`rules/field_actors.md` section 4.2) over rings of the remote members' own paths: slot 1 follows the leader over the leader's path, slot 2 follows slot 1 over slot 1's path (each path a point per move of more than half a unit, at most 0x80 points). Nearer than 80 units to the leader it steps 5 units straight away from it, facing it; within 200 units of the member it follows it stands; else it heads for the newest point of the path within 50 units of it (the newest point when there is none, or when the one found is within the step) at the follower speed: (0x50 - 16 per slot) / 16 units a tick walking, plus 0x48 running past 230 units, 0xF0 from 351. It takes the walk-mesh height under its spot when that floor is within 64 units of the path's height, else the path's.
- **Arrival.** A party that arrives, or jumps (a snap), is drawn once its spot has held 30 ticks (0.5 s) without another jump and its player has had the controls since (`s` 0, 2 or 4), or after 300 ticks (5 s) of an event: a room's entrance moves and scripted walk-in play out unseen and the party appears where it ends up, while a player standing through a long scene still shows.
- **Size.** Every member takes the local leader's model scale (the room's scripts size the party), each by its own model's field size.
- **Animation.** The leader plays the walk clip, or the run clip when its clip is the run clip, while it moves on the tick or its shown pose has `m` 1 (a late pose leaves it waiting a few ticks; the walk cycle runs on instead of restarting). A follower walks or runs as its follow rule says. A member standing plays the stand clip with the party actors' idle timers. In a menu or an event (`s` 2, 3, 4) the leader stands. Each member's light eases toward the zone colour of its triangle and its shadow toward the party actors' strength (0 on water and stairs), as a party actor's do.
- **Drawing.** Members are drawn as party actors are (the same mesh pipeline state, art mode, HD textures, `[Shaders]` character shading and floor shadows: the blob, or with `[Enhancements] Lighting` the silhouette, its plane eased as a party actor's, in the mask tiles the room's actors leave free), never as room entities: no script, no collision, no trigger, no talk, no culling. A party in a battle (`s` 1) stands where it was. With the `[Multiplayer]` options: none with `ShowPlayers` off; at most `MaxParties`, those whose leaders are nearest the camera's target (the entity the scroll follows) on the ground plane; with `Translucent` each member at half opacity (only its nearest surface shows) and its shadow at half strength.
- **Models.** A model byte is loaded through the field's character-model cache on a worker thread; nothing waits for it. A party is drawn once its leader's model is ready; a follower whose model is not ready yet, or never will be, is left out, and a leader that cannot be loaded hides the party. A room change or an art switch places every member again; the models only remote parties used leave the cache then, unless a party still in the room shows them.
- **Labels.** After each draw the field gives a label point per drawn party: 64 units above the leader's head (attach point 1; 256 units above the feet for a model without it), projected into the window's field picture, with the party's `pid`, name and state; the host draws the name, Star Level and state icon there. The local leader gets the same point (`FieldWorld::local_label()`), for the player's own chat bubbles. The points are placed only while the host asks for them (`RemoteDrawOptions::labels`, on while connected). A point outside the visible picture gives no label.

## 6. The server

`server/cloudflare/` holds the Worker (TypeScript), `wrangler.toml` and a README. All connections go to one Durable Object that keeps the rooms and presence in memory (no chat is kept: a player sees only the lines sent while connected), using the WebSocket hibernation API. It stores the ban list and the away records of section 8.4. Each connection's own state (name, room, last `pres`, rate counters, its pending challenge with the card, its battle and the battle link's counters) lives in the socket's attachment, so a hibernation keeps it; the admin lockout counters and the challenge cooldowns are memory only and are forgotten when the object hibernates or restarts (a cooldown that lifts early).

- At most 4 open connections per IP address (more are refused with HTTP 429). After 10 wrong admin tokens from one address in 10 minutes, through the admin endpoints or `hello`, every admin attempt from it is refused for that long (HTTP 429; a `hello` simply gets no admin mark). Admin tokens are compared as SHA-256 digests in constant time. Presence numbers are clamped to the 32-bit signed range before they are passed on.
- Rate limits, per connection: `pres` 15 a second (more are dropped silently), `chat` and `pm` together 5 in any 10 s (more get `error` `rate`), the battle link's `pvp_side`, `pvp_cmd`, `pvp_hash` and `pvp_resume` together 30 a second (more get `error` `rate`), other messages 10 a second. A frame longer than 4096 characters gets `error` `bad`, except a `pvp_side` of up to 16384.
- Worker variables: `IDLE_MS` (the 60 s idle limit), `CHALLENGE_MS` (the 30 s a challenge waits for its answer), `PVP_OPENING_STAMINA` (`opening_stamina` in `pvp_start`, tenths, default 35, held to 0..70) and `AWAY_MS` (the 30 s a battle member who disconnected has to come back, section 8.4). The protocol test sets all four.
- Bans: by player id and by IP address, kept in the Durable Object's storage. The admin endpoint `POST /admin/ban` and `POST /admin/unban` take `{"pid": ...}` or `{"ip": ...}` and need `Authorization: Bearer <ADMIN_TOKEN>` (a Worker secret); `GET /admin/players` lists the connected players with their `pid`, name, room and IP.
- On this machine: `cd server/cloudflare; npm install; npx wrangler dev` serves `ws://127.0.0.1:8787/ws`, the default `ServerUrl`. Deploying: `npx wrangler deploy` from the operator's own Cloudflare account.

## 7. Client side

The client trusts no server further than it needs: it keeps at most 64 remote parties per room, drops any message whose `pid` (also `to`, `from`, `opponent`, `first` and the battle id of section 8) is not 1 to 32 letters and digits, takes the battle link's messages only for the battle it is in and checks them as section 8.4 says (a `pid` is stored in the ini's mute list), refuses JSON nested deeper than 64 or with more than 256 members in one object, handles no message from a connection it has already given up, and sends `[Multiplayer] AdminToken` only to the Master server.

Mutes are the player's own: `[Multiplayer] Muted` lists `pid`s whose chat lines are hidden, and whose parties too when `MuteHidesParty` is on. Nothing about a mute is sent to the server.

The local state `s` is the field's own (0 free, 3 in an event), raised to 1 during a field battle and to 2 under the main menu, a shop, the pause screen, the key-item list, the party and monster screens, a name entry or the settings window. A room change clears the table of remote parties, the occupancy and the room chat; the server's `peers` and `occupancy` fill them again.

The chat panel sits at the bottom left, drawn with ImGui like the settings window. T opens its input line (Enter is the game's confirm key); while it is open the game gets no keys, Enter sends the line and closes it, Esc closes it without sending. A tickbox by the input line sends to `global` instead of `room`; Tab switches it while typing. With `[Multiplayer] HideGlobalChat` on, `global` lines are not shown and the tickbox is gone (only room and private lines). Lines show as `[R] name: text` or `[G] name: text`, an admin's name in bold red, oldest first by the server's `ts`; a line refused with `error` `rate` leaves a grey notice. Private lines and challenges: section 8. `[Multiplayer] Chat` decides what shows while not typing: the last 8 lines (`always`), each line for 10 s after it arrives with a fade over its last 2 s (`new`), or nothing (`hidden`). There is no on-screen keyboard; on a Steam Deck the Steam keyboard (Steam + X) types into the line. The labels over remote leaders give the name, a star and the Star Level, with a menu icon (state 2) or a speech-bubble icon (state 4, typing); they are not drawn while the local player is in a battle, a menu or a movie. With `[Multiplayer] ChatBubbles` on, a `room` line also shows in a speech bubble over the speaker's party: the newest line of each player, for 4 s plus 0.05 s per byte of text (at most 9 s), fading over its last 0.6 s, wrapped at 14 font heights and cut to 120 bytes. The player's own lines, which the server echoes back, show over the local leader. Muted players get no bubble; `global` lines never do. Bubbles follow the same points as the labels and show when the labels could (`ShowLabels` off keeps the bubbles). Player text uses a font with Latin, Greek, Cyrillic, Japanese and common symbols; other characters show as `?`.

## 8. Private messages and battle challenges

Additions to sections 3 and 4. Every player has a `pvp` flag (`[Multiplayer] Challenges`, on by default) sent in `hello` and `profile` and relayed in `peers`, `join` and `profile`; a player with it off cannot be challenged.

### 8.1 Private messages

| Direction | `t` | Members | Meaning |
|---|---|---|---|
| client to server | `pm` | `to` (pid), `text` | A line for one player, wherever they are. Counts against the chat rate limit. |
| server to client | `chat` with `scope` `pm` | `pid`, `name`, `text`, `ts`, `admin`, plus `to` and `to_name` | Sent to the recipient and echoed to the sender; `to` / `to_name` name the recipient, so the sender's copy reads as their own line to that player. |
| server to client | `error` `offline` | `msg` | The `to` player is not connected. |

The server cleans `text` as a chat line's, refuses (`error` `bad`) a `to` that is not a `pid` or is the sender's own, and answers `error` `offline` with `msg` and `pid` (the `to` it could not reach) when that player has no connection. A player connected more than once gets the line on every connection, and so does the sender's echo.

The client keeps private lines in a scope of their own (not cleared by a room change), drops a `pm` line that is neither from nor to its own `pid`. The chat panel shows a private line as `[PM] name: text` (the sender's echo as `[PM] to to_name: text`) in pink, and an `offline` or `rate` refusal of a private line as a grey notice. The open input line has three targets: Room, Global and PM to one player, shown as "To name" before the field. Tab cycles Room and Global, and from PM goes back to them; Esc clears a PM target first and closes the line on a second press. PM is chosen from the player menu (8.3), the Message button of the Multiplayer tab, or by clicking the name of a private line in the open panel (a reply; a click on a room or global line's name opens the player menu instead).

### 8.2 Challenges

A challenge carries a party card: `star`, and `members`, up to 3 objects of `char` (character id), `name`, `hp` (max HP), `atk`, `def`, `mag`, `mdef`, `elements` (elements allocated on the grid). Each challenge also carries `ver` and `data`. `ver` is `<version>+<build>`: OpenCross's version number and the build identity, the first 16 hex digits of the SHA-256 of the running `opencross.exe`, so two games match only when they run the very same exe (a battle runs in lockstep on both, so its code must be identical). `data` is the battle data fingerprint (lower-case hex, at most 128 digits): a hash of the battle tables as loaded, after mods, with the versus rules version, so a gameplay mod or another game data version refuses the battle while texture, voice and shader mods do not; empty only before the tables are loaded.

The client builds its card from the loaded game (`game::party_card`, `game_session.h`): the party in slot order, the Star Level of the save, and per member the name the menus show, the Status screen's max HP, ATK, DEF, MAG and MDEF (the record's values plus the gear, `GameState::stats`, `rules/menus.md` section 4, at most 999) and the number of open grid cells holding an element (ids 1 to 0x7F; tech cells and shut cells do not count). The server and the client both hold a received card to that shape: at most 3 members, `name` cut to 24 code points, `char` 0..255, `hp` 0..9999, `atk` `def` `mag` `mdef` 0..999, `elements` 0..99, `star` 0..999; the server refuses (`error` `bad`) a card that is not an object, has more than 3 members or a member without the numbers.

| Direction | `t` | Members | Meaning |
|---|---|---|---|
| client to server | `challenge` | `to`, `card`, `ver`, `data` | Challenge a player. One outgoing challenge per player at a time. |
| client to server | `challenge_cancel` | | Withdraw the outgoing challenge. |
| client to server | `challenge_reply` | `from`, `accept` (bool), `reason` (`declined`, `busy`, `timeout`, `off`), and with `accept`: `card`, `ver`, `data` | Answer a challenge. |
| server to client | `challenge` | `from`, `name`, `star`, `card`, `expires` (ms left) | Someone challenges you. |
| server to client | `challenge_end` | `pid` (the other player), `reason` (`declined`, `busy`, `timeout`, `off`, `cancelled`, `left`, `version`, `data`, `cooldown`, `pending`) | The challenge is over without a battle; sent to whichever side is still waiting. |
| server to client | `pvp_start` | `battle` (id, 16 hex digits), `seed` (32-bit unsigned), `first` (pid of the side that moves first), `opponent` (pid), `name`, `star`, `card`, `opening_stamina` (the first side's stamina on its opening turn, tenths: 35 = 3.5) | The challenge was accepted: both players get it, each with the other's card. |
| client to server | `pvp_end` | `battle`, `result` (`won`, `lost`, `draw`, `aborted`, `desync`) | The battle is over on this side: the server stops counting this player as in the battle (section 8.4 for the opponent). The battle's own messages: section 8.4. |

The server checks a challenge before it forwards it, and answers a refusal with `challenge_end` to the challenger (`pid` the target): `bad` (an `error`) for a `to` that is not a `pid`, the challenger's own `pid`, a bad card or `data`; `pending` when the challenger already has a challenge pending, sent or received (`busy` when the challenger is in a battle); `left` when the target is not connected; `off` when the challenger or the target has `pvp` off; `busy` when the target has a challenge pending, sent or received, or is in a battle; `cooldown` when the challenger challenged the same player in the last 10 s (a refused challenge does not count). A forwarded challenge expires after 30 s (`timeout` to both; `expires` in the forwarded message is the time it has). `challenge_cancel` ends the sender's pending challenge with `cancelled` to the target. A `challenge_reply` for no pending challenge (it expired, or was withdrawn) is ignored; a decline ends it with the `reason` given (`declined` for an unknown one) to the challenger only. On `accept` the server compares `ver` and, when both are non-empty, `data`, and ends the challenge with `version` or `data` to both when they differ; otherwise it draws the battle id, the seed (`crypto.getRandomValues`) and the first side (one random bit) itself and sends `pvp_start` to both, and counts both as in that battle until `pvp_end`. A `pvp_end` with another battle's id is ignored; a bad `result` is `error` `bad`. A player who disconnects ends the challenge they sent with `left` to its target and, when no other connection of theirs is left, the ones sent to them with `left` to their challengers; a battle they are in waits for them (section 8.4).

The challenges are kept in the challenger's socket attachment, so a hibernation keeps them; the 30 s are ended by the object's alarm (set for the earliest expiry) and checked again on every challenge message. The 10 s cooldowns are memory only: a hibernation forgets them, so a challenge may come back sooner.

A client answers `busy` by itself when a challenge arrives while its player is not free in a field room (state other than 0 or 4, so typing in the chat still counts as free, or no room), already has a challenge pending either way, or is in a battle, and `off` when challenges are off. The challenged player sees a popup at the top of the screen, "name ★N wants to battle you", with the challenger's card, Accept / Decline (keys Y / N; on a pad the d-pad picks one, Decline at first, the confirm button presses it and the cancel button declines; all taken from the game only while the popup shows) and the seconds left (`expires`, at most 60 s); when they run out the client answers `timeout` itself. The challenger sees "Waiting for name…" with the seconds left and Cancel, and gives the challenge up 5 s after the server's 30 when no answer came; an accept waits 10 s for its `pvp_start`. Every end the player did not choose leaves a grey notice in the chat panel ("name declined your challenge", "name is busy", "name didn't respond", "name isn't taking challenges", "name withdrew the challenge", "name left", "Your OpenCross version differs from name's", "Your game data differs from name's", "Wait a moment before challenging name again", "You already have a challenge pending", "The challenge from name timed out"). After `pvp_start` each game sends its side (section 8.4) and shows the versus screen (both cards side by side, "You go first" or "name goes first") for 3 seconds and until the other side has come ("Waiting for name...", at most 15 s more), then the versus battle starts from the field (`rules/versus.md`; side A is the `first` player, the seed and `opening_stamina` are the message's, both sides as exchanged) and runs over the battle link; its end sends `pvp_end` with the player's result. The card is only shown: the battle is built from the exchanged sides. A battle that cannot start (the player is no longer free in the field, a side cannot be made or read, the other side never came) shows "The battle could not start" and sends `pvp_end` `aborted` at once. A battle starting (or leaving field play) withdraws the player's own pending challenge with `challenge_cancel` and answers an incoming one `busy`; a `pvp_start` that arrives then is ended at once with `pvp_end` `aborted`.

### 8.3 The player menu

Clicking a player's name label in the field or their name in an open chat panel opens a small menu for that player at the pointer: their name and Star Level, Message (the input line opens in PM mode to them), Challenge to battle (greyed when either side has challenges off, either is busy, or a challenge is pending; a tooltip says why) and Mute / Unmute. A click outside it or Esc closes it. A label shows the hand pointer and a lighter box under the mouse; labels are clickable whenever they are drawn and no ImGui window is under the pointer. The mouse pointer is hidden only in the fullscreen modes after 3 s without mouse input, so moving the mouse shows it again; pad and keyboard play is unchanged. The Multiplayer tab's player list has the same Message, Challenge and Mute buttons on each row; Message and Challenge close the settings window. "Busy" for the local player is the field's own state: not free in a field room, or under a game menu, shop or other screen (the settings window itself does not count); for a remote player it is their last `pres` state other than 0. A player who is not in the room (a name in the global or private chat) is challenged without these checks; the server decides.

### 8.4 The battle link

After `pvp_start` the two games exchange their sides and then every command of the battle through the server, which relays each game's messages to the other in order and never runs the battle itself. Every message carries `battle` (the id of `pvp_start`); the server accepts one only from a member of that battle, on the connection that holds it (`error` `bad` for a malformed id, another battle's id, or a sender outside the battle).

| Direction | `t` | Members | Meaning |
|---|---|---|---|
| client to server | `pvp_side` | `battle`, `side` | This game's side, once: `encode_versus_side` (`rules/versus.md` section 3) in padded standard base64, at most 12288 characters. A second one is `error` `bad`. |
| client to server | `pvp_cmd` | `battle`, `seq`, `cmd`, `hash`, `ack` | A command of this game's player that its rules applied. |
| client to server | `pvp_hash` | `battle`, `seq`, `hash`, `ack` | The state check after a command of the other game that this game applied. |
| client to server | `pvp_resume` | `battle`, `ack` | After a reconnect: this game still holds the battle. |
| server to client | `pvp_side`, `pvp_cmd`, `pvp_hash` | as sent, without `ack`, plus `n` | The opponent's message. |
| server to client | `pvp_away` | `battle`, `ms` | The opponent's connection closed; it has `ms` (30000) to come back. |
| server to client | `pvp_back` | `battle` | The opponent resumed. |
| server to client | `pvp_resumed` | `battle`, `seq`, `side` | The answer to `pvp_resume`: the last `seq` the server took from this game and whether it holds its side; every relayed message the game has not acknowledged follows, in order. |
| server to client | `pvp_gone` | `battle`, `reason` | The battle ended outside its rules: `left` (the opponent stayed away: this game wins, and the server counts it out of the battle), `aborted` (the opponent's game ended it without a result), `forfeit` (to a resume after the away time: this game lost), `closed` (to a resume: the server no longer holds the battle). |

**Sides.** Each game sends its side right after `pvp_start`, as its party stands then (the party, the summon stars and the Dopplegang pool as `encode_versus_side` writes them, names included). Both games stay on the versus screen until the other side has come, then build both sides from the exchanged bytes (their own read back from what they sent) and start the battle from the seed. A side of a real three-member party is about 0.9 KB (861 bytes, 1148 base64 characters, for a save at Star Level 20; the built-in test parties 1035 and 1106 bytes), but each of a member's two names may take 256 bytes, so a side can pass the 4096-character frame limit: a `pvp_side` frame may be up to 16384 characters and the client sends at most 9216 bytes.

**Order.** `seq` counts the commands both games applied, from 1, whichever side gave them. A game sends exactly one message per command it applies, `pvp_cmd` for its own and `pvp_hash` for the other game's, so the `seq` of one game's messages goes up by one each time: the server refuses (`error` `bad`, nothing relayed) a `pvp_cmd` or `pvp_hash` whose `seq` is not the sender's previous one plus one. A game applies the other game's command only as the next of its own stream (`seq` one above its count) and only while the other side acts (the turn side, or the side that owes a Dopplegang pick, `rules/versus.md` section 2); a command out of that order ends the battle with no result. Surrender (Run) and the timeout End Turn travel as commands.

**Commands.** `cmd` is the command as signed decimal integers separated by single spaces: kind, actor, target, cell, form, timeout (0 or 1), swap_in, then the attack chain's strengths. The kinds are 0 Attack, 1 Element, 2 Defend, 3 Run, 4 Swap, 5 End Turn, 6 Focus, 7 Element menu, 8 Form; units are the rules' (side A 0..2, side B 3..5). The server checks only that shape (at most 64 characters); the client refuses a value out of its field (kind 0..8, actor 0..5, target -1..8, cell -1..79, form -1..255, timeout 0..1, swap_in -1..255, at most 4 strengths 0..2), which ends the battle with no result, and its rules judge the rest: a command they refuse ends the battle with no result.

**State checks.** `hash` is the battle's state hash after the command, 16 lower-case hex digits. A game compares the `hash` of a `pvp_cmd` with its own hash after it applied that command, and a `pvp_hash` with the hash it had after its own command of that `seq`. A difference ends the battle with no result on that game ("No result" plate), logged with the `seq` and both hashes; its `pvp_end` `desync` then ends it on the other (`pvp_gone` `aborted`).

**Relay numbers.** Every message the server passes on (`pvp_side`, `pvp_cmd`, `pvp_hash`) carries `n`, counting up by one per recipient and battle. A game drops one whose `n` is not above the last it took (a repeat after a resume) and ends the battle with no result when one skips a number or cannot be read. `ack` is the last `n` the game took; the server keeps each member's messages above its `ack` (at most 256) to send again on a resume.

**Pacing.** A game queues its battle messages and sends at most 20 a second; the server takes at most 30 a second per connection for `pvp_side`, `pvp_cmd`, `pvp_hash` and `pvp_resume` together (more get `error` `rate` and are dropped), apart from the other limits.

**Turn timer and silence.** The 60-second turn timer is each game's own: the game whose turn ran out sends the End Turn with its timeout flag itself. A game waiting for the other side to act, both players connected, counts the other game gone after 90 s without any message from it: the other side forfeits on this game (Victory), which reports `pvp_end` `won`.

**Disconnects.** When the connection that holds a battle closes while the opponent still holds it, the server keeps an away record of the member (its `seq`, its last `n`, whether it sent its side, its unacknowledged messages), tells the opponent `pvp_away`, and relays the opponent's further messages into the record. A `pvp_resume` from the same player (the same `pid`, on any of its connections; a connection that still holds the battle is closed and the battle moves to the new one) within the time gets `pvp_resumed`, the messages above its `ack`, and the opponent gets `pvp_back`. When the time runs out the opponent gets `pvp_gone` `left` and leaves the battle; the record is kept 10 minutes more, so that a late `pvp_resume` hears `forfeit`. An away record whose messages pass 256 or 96 KB forfeits at once. When both members are gone the battle is dropped, and a resume hears `closed`. The client keeps the battle over a dropped connection: it reconnects every 2 s, sends `pvp_resume` after the `welcome`, sends nothing of the battle until `pvp_resumed`, then sends again everything above the server's `seq` (and its side when the server lacks it); a message it no longer holds (it keeps the last 1024 sent) ends the battle with no result. During a battle the client pings after 5 s without sending and drops a connection that received nothing for 15 s. The battle's banner reads "Waiting for name... N" while the opponent is away and "Reconnecting... N" while this game's own connection is down, N the seconds left of the 30; a game whose own connection stays down 35 s ends the battle as lost (Defeat). A game that was closed or restarted no longer holds the battle, cannot resume, and is forfeited.

**Results.** Each game sends `pvp_end` when its battle ends: `won`, `lost`, `draw`, `aborted` (no result) or `desync` (the state checks differed). A `pvp_end` frees its sender only; the other member stays in the battle until its own `pvp_end`, its forfeit or its disconnect. An `aborted` or `desync` result sends `pvp_gone` `aborted` to an opponent that still holds the battle, and removes the away record of an opponent that is away. A forfeit frees the winner at once.

**Hibernation.** Each connection's link counters are in its socket attachment (a few dozen bytes, well under the 2048-byte limit); the away records are in the object's storage under `away:<pid>` (opponent, deadline, counters, unacknowledged messages), deleted when the member resumes, the battle ends or the forfeit is 10 minutes old, and the alarm fires at their deadlines. A hibernation therefore keeps a disconnected member's place, its outbox and its deadline. The unacknowledged messages of a connected member are kept in memory only: a hibernation forgets them, so a resume after one delivers only what was relayed since; if that leaves a gap in `n` the game ends the battle with no result. The object hibernates only after several seconds without a message, which in a battle means both games are waiting on a player (each acknowledges what it takes with its next message).
